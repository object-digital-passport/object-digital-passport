## ВАЖНО: деплойменты 0.x, эталонная линия v0.6 и путь к v1

Этот репозиторий описывает линию протокола **v0.X**. На этапе **0.X** правила контракта ещё могут меняться.

Коротко:

- **Деплоймент** — один адрес контракта (**один экземпляр реестра**).
- Ваш `creatorId` и паспортные записи относятся **только** к этому деплойменту.
- Новый деплоймент — даже в рамках новой линии 0.X — **не переносит** старые записи; тот же кошелёк в новом реестре может получить **другой** `creatorId`.
- **Эта спецификация описывает эталонную *ветку* v0.6** в этом репозитории (редизайн модели хранения — см. `docs/REQUIREMENTS_FIELDS_V0.6.md`): упакованный on-chain `**CONTRACT_VERSION` = 6** (разбиение по EIP-170: линкуемая `**ODPPassportLib`**, опциональные спутники — см. §14). Модель 0.6 хранит **неизменяемую on-chain карточку** (`title`, `authorName`, `shortDescription`, `domain`), якорит блок идентификации через `**anchorsHash`** + `**anchorTypesMask`**, и заменяет все перезаписываемые поля текущего состояния на **append-only события паспорта**. Другие адреса = отдельные реестры; сопоставляйте **сеть + контракт + ABI** + `**CONTRACT_VERSION`**.

Если вам нужен сценарий **«один кошелёк + один долгоживущий `creatorId`»** как канонический через все поколения протокола, ориентируйтесь на будущий стабильный **v1**, который может явно описать миграцию или двойное чтение.

### Мульти-контрактная архитектура (нормативная сводка)

Эталонный стек **намеренно разделён**:

- `**ObjectDigitalPassport.sol`** — **основной реестр** (паспорта, профили, proof, поверхность governance в ABI).
- `**ODPPassportLib.sol`** — **отдельно деплоимая линкуемая библиотека**, несущая тяжёлую **pure**-логику валидации/форматирования, чтобы контракт реестра оставался в пределах лимита создания **24 КиБ (EIP-170)** (общий `**error EC`** с реестром).
- `**ODPWalletDocumentAnchor.sol`** (опциональный **спутник**) — `attestExternalDocument` / `getExternalDocumentAttestation` на уровне кошелька вынесены из байткода основного реестра (**EIP-170**); конструктор спутника принимает адрес основного реестра и переиспользует его реестр создателей для контроля доступа.
- `**ODPCounterfeitConcern.sol`** (опциональный **спутник**) — `**raiseCounterfeitConcern` / `clearCounterfeitConcern` / `getCounterfeitConcern`** только для профилей `**P`** и `**M`**; конструктор фиксирует один основной реестр; хранилище **не** на монолите, чтобы сохранить запас по EIP-170.

Деплой: сначала **библиотека**, затем **реестр** (с метаданными линковки), затем при необходимости **якорь документов** / **спутник для подделок** — см. скрипты деплоя в репозитории.

### Взгляд вперёд: эталонная линия → стабильный v1 (намерение дизайна)

Эталонная реализация **v0.6** в этом репозитории и эта спецификация сформулированы так, чтобы будущий **стабильный v1** мог задать ясный **прямой** путь, не создавая видимости тихой интероперабельности между реестрами 0.x:

- В on-chain записях при минте фиксируется упакованный `**contractVersion`** (`SPEC_MAJOR * 16 + SPEC_MINOR`, каждое значение **< 16**). **Эталон этой ветки минтит байт `6`.** Прочие деплойменты 0.x на других адресах **не** взаимозаменяемы; **периферийные** контракты (спутники) подключаются конфигурацией.
- Правила для `**passportId`** (строка Passport ID; в legacy ABI то же поле может называться `**humanId`**), `**creatorId`** и версионирования `**passport.json`** нацелены на достаточную стабильность, чтобы **v1** мог описать **миграцию или двойное чтение** (например, инструменты, верифицирующие старые деплои параллельно с реестром v1), а не размытую смену полей.
- **v1** здесь не специфицирован; при выходе он явно определит **миграцию**, **мост** или **заморозку** реестров 0.x. До этого момента абзац фиксирует **инженерное намерение**, а не обещание in-place-апгрейда для конкретного деплоя.

### On-chain возможности эталона (v0.6)

Ниже описан **эталонный стек этого репозитория (v0.6)**. При минте фиксируется `**CONTRACT_VERSION` = 6** (байт `**6`**). Таблица структуры `Passport` в §8 нормативна для этой линии деплоя.

**Нормативные возможности** (та же семья реестров; **v0.6** минтит байт **6**):

- `**owner`** (изначально совпадает с `creator`) и `**transferPassport`**; опционально `**delegateCreatorPublishing`** / `**revokeCreatorPublishing**` (агент публикации на весь аккаунт эмитента для `**updatePassportUrls**`)
- **Агент минта (делегированный минт):** агент вызывает `**requestMintAgentRole(principalCreatorId)`**, принципал вызывает `**confirmMintAgentRole(agent)`**; затем `**mintDigital` / `mintPhysical` / `mint*ViaExtension**` принимают в конце `**mintOnBehalfOfCreatorId**` (id профиля принципала либо `**""**` для самоминта). On-chain `**Passport.creator**` и `**owner**` — кошелёк принципала; `**Passport.mintAgent**` — `**address(0)**`, если минтил сам принципал, иначе кошелёк **делегата**. Месячные лимиты минта (**C** / **B**) списываются с кошелька **принципала**. Состояние ожидания: `**mintAgentDelegationPending(keccak256(abi.encodePacked(principalCreatorId, agent)))`**; активный делегат: `**mintAgentForCreator(creatorId)`**. Жизненный цикл: событие `**MintAgentUpdate`** (`kind`: 0=запрос, 1=отмена, 2=активирован, 3=снят). `**revokeMintAgentRole**` (принципал), `**renounceMintAgentRole(principalCreatorId)**` (агент), `**cancelMintAgentRequest(principalCreatorId)**` (агент, только для ожидающих).
- `**revokePassport`** (создатель или адрес `**governance**`) с `**revocationReasonHash`**
- **On-chain карточка** при минте: `**title`**, `**authorName`**, `**shortDescription`**, `**domain`** — неизменяема, без пути редактирования (опечатка = отзыв + перевыпуск), ОБЯЗАНА совпадать с теми же полями `passport.json` байт-в-байт
- **Якоря идентификации**: on-chain `**anchorsHash`** (SHA-256 канонического массива `anchors` в `passport.json`) + `**anchorTypesMask`** (битовый набор типов якорей, §9); один основной `**imageHash`** / `**imageUrl`** on-chain — дополнительные фото — это якоря `photo` внутри `anchors[]`
- **Append-only события**: `**recordPassportEvent(passportId, kind, value, note, attachmentHash, attachmentUrl)`** (статус / местонахождение / права / состояние / повреждение / реставрация / произвольное) — заменяет перезаписываемые сеттеры текущего состояния v0.5 и обновители aux/NDPP-обязательств
- **Аудит P-affiliation**: `**getPAffiliationAudit`**, `**detachPAffiliation`** (родитель P); метки времени join / detach
- **Компактные revert**: ошибки через `**error EC(uint16 code)`** — расшифровка по исходнику задеплоенного контракта (строковые сообщения убраны ради размера байткода). Эталонный `**ObjectDigitalPassport`** деплоится **с линкуемой библиотекой** `**ODPPassportLib`** (общий `**error EC`**), чтобы байткод создания реестра оставался в пределах 24 КиБ (EIP-170); сначала библиотека, затем контракт (см. скрипты деплоя в репозитории). Локальные тесты Hardhat могут использовать `**allowUnlimitedContractSize`**; перед mainnet-деплоем проверьте вывод `**[ODP] EIP-170:`** после `compile`.

**Претензия к подделке / institutional concern (v0.4):** спутник `**ODPCounterfeitConcern`** (не на основном реестре). Семантика и `**NET.counterfeitConcern`** — в этой спецификации и в указателях [`../../../docs/V0.4.md`](../../../../docs/V0.4.md) / [`RELEASE_v0.4.md`](RELEASE_v0.4.md). Кошельки `**P`** и `**M`** могут вызывать `**raiseCounterfeitConcern(passportId, reasonHash)`** (`reasonHash` обязан быть ненулевым); только **тот же** `proverCreatorId` может вызвать `**clearCounterfeitConcern`**. `**getCounterfeitConcern`** возвращает `**(active, proverCreatorId, reasonHash, timestamp)**` (флаг неактивен → `active == false`, остальные поля нулевые/`""`). Верификаторы и UI паспорта SHOULD вызывать спутник, когда `**NET.counterfeitConcern**` настроен на **тот же** адрес основного реестра.

> **Примечание о deployable split-line v0.6:** деплоимая эталонная линия в этом репозитории оставляет за **основным реестром** только записи создателей, неизменяемое ядро паспорта (карточка + хэши), минт, передачу, отзыв и append-only события паспорта. Чтобы уложиться в `EIP-170`, ряд опциональных поверхностей обслуживают **парные спутники** вместо ABI основного реестра:
> - `**ODPRegistryRelations`** — P-affiliation, делегирование mint-агента, делегирование публикации создателя
> - `**ODPPassportProofRegistry`** — `**submitProof`** и чтение proof
> - `**ODPExtensionMintRouter`** — `**setMintExtension`** и `**mint*ViaExtension`**
> - опциональные `**ODPWalletDocumentAnchor`** и `**ODPCounterfeitConcern`**
>
> Интеграторы НЕ ДОЛЖНЫ предполагать, что эти методы существуют на самом ABI деплоимого `**ObjectDigitalPassport`**. Их SHOULD направлять в спутник, настроенный для того же адреса реестра (`**NET.relations`**, `**NET.proofRegistry`** и т.п.). Deployable split-line также не содержит на основном реестре удобный геттер `**getRemainingMints()`**.

**On-chain governance определений типов с timelock** в байткоде эталона не хранится; управляйте governance (multisig / DAO) вне сети и при необходимости фиксируйте хэши в релизах.

**Переносимый бандл (нормативное расширение):** `**.odpass`** (ZIP). **Эталонные верификаторы и примеры совместимости в этом репозитории используют только `.odpass`.** **Публичный `dataUrl` ОБЯЗАН отдавать ZIP `.odpass`** — не сырой `passport.json` (§9).

## 1. Обзор

Object Digital Passport (ODP) — это открытый стандарт, который позволяет любому регистрировать физический или цифровой объект в публичном блокчейне и проверять его подлинность — без каких-либо централизованных платформ, подписок или зависимости от третьих сторон.

**Ключевые принципы:**

- **Открытость** — любой может реализовать протокол на любом языке или платформе
- **Децентрализация** — нет одной компании, которая контролирует реестр
- **Дружелюбие к офлайну** — подлинность можно проверить без интернета, используя только хэши
- **Бесплатное чтение** — верификация никогда не стоит ничего
- **Минимум on-chain** — нет изображений и больших данных, хранящихся в блокчейне

**Позиционирование (справочно):** ODP сам по себе не заменяет экспертизу и комплаенс. Он рассчитан **дополнять** ручную проверку и параллельные стандарты (**DPP**, **GS1**, **IIIF**, **C2PA** — см. §18). Полезная модель — **проверяемый реестр**: при верификации видно, какой деплой зафиксировал какие хэши, вместе с проверкой размещённых или упакованных файлов. **Спам и шум индекса** уменьшаются лишь частично (например лимиты минта, оффчейн-списки); к стабильной продуктовой линии ожидаются доработки. **Визуальный дизайн** приложений и сайтов здесь **не нормируется** и может обсуждаться сообществом ближе к стабильной версии.

## 2. Passport ID

Каждый зарегистрированный объект получает глобально уникальный Passport ID (строка `ODP-…`).

> **Имена в данных:** в эталонном контракте поле структуры — `**passportId`** (`Passport`, `ProofRecord`, параметры функций вроде `submitProof`). В `passport.json` используйте `**passportId`**. *Passport ID* — имя в спецификации для той же строки. Legacy ABI могут использовать `**humanId`** для идентичного поля.

### Формат

```
ODP-YYYY-MM-NNNNNNNNN
```


| Раздел      | Описание                                                                                       | Пример      |
| ----------- | ---------------------------------------------------------------------------------------------- | ----------- |
| `ODP`       | Фиксированный префикс протокола                                                                | `ODP`       |
| `YYYY`      | **UTC** календарный год **транзакции mint** (`block.timestamp`), не произвольный «год объекта» | `2026`      |
| `MM`        | **UTC** календарный месяц (01–12) **транзакции mint**                                          | `03`        |
| `NNNNNNNNN` | Случайное число из 9 цифр, уникальное в рамках года и месяца                                   | `004829301` |


### Примеры

```
ODP-2026-03-004829301   ← объект зарегистрирован в марте 2026
ODP-2026-03-000193847   ← другой объект в тот же месяц
ODP-2026-04-007392018   ← объект зарегистрирован в апреле 2026
ODP-2027-01-002048391   ← объект зарегистрирован в январе 2027
```

Число не указывает ни порядок, ни общее количество зарегистрированных объектов.
Это сделано намеренно.

### Алгоритм генерации

Референсный `**ObjectDigitalPassport**` (эталон v0.6) использует (Solidity `abi.encodePacked`):

```
key     = uint32(year) * 100 + uint32(month)
entropy = keccak256(block.timestamp, block.prevrandao, msg.sender, nonce, key, gasleft())
number  = uint32(uint256(entropy)) % 1_000_000_000   // 000000000–999999999
if number уже занят для этого года+месяца:
    nonce++, retry (ограниченное число попыток)
passportId = "ODP-" + decimal(year) + "-" + two_digit(month) + "-" + zero_pad(number, 9)
```

**Один миллиард** возможных значений в месяц. Уникальность гарантируется контрактом через проверку коллизий с ограниченным числом повторов.

### Правила

- Число генерируется контрактом — creator не выбирает его
- Число уникально в пределах комбинации год+месяц
- Два одновременных mint'инга упорядочиваются блокчейном — дубликаты невозможны
- Passport ID неизменяем после mint'инга
- Passport ID — канонический идентификатор для всех поисков/запросов

**UTC месяц mint:** on-chain сегменты `YYYY` и `MM` **нельзя** задать произвольно: аргументы `year` и `month` для `mintDigital` / `mintPhysical` (и mint через extension) **должны** совпадать с **григорианским UTC** календарём `block.timestamp`. То же для `submitProof` и префикса `PRF-YYYY-MM-…`. Так человекочитаемый префикс отражает **момент включения транзакции в UTC**, а не дату создания объекта. Для музейной/провенанс-семантики используйте поля `passport.json` — `creationDate`, provenance или необязательное `objectYear` (см. §9). Правило действует только у **новых деплоев**; замороженные реестры не меняются.

**Ограничение:** сеть гарантирует лишь **согласованность с `block.timestamp` в UTC**, а не «истинную» календарную дату физического объекта или файла.

## 3. ID профиля

Каждый creator, бренд или институция должны зарегистрироваться в сети on-chain до mint'инга паспорта или отправки proof. Регистрация назначает постоянный globally уникальный ID профиля.

> **Имена в данных:** короткий идентификатор передаётся строкой `**creatorId`** в контракте и как `**creator.creatorId`** в `passport.json`.

**Зарегистрированный ID профиля обязателен.** Контракт отклоняет любые транзакции mint или proof от незарегистрированного кошелька.

### Формат

```
T-NNN-NNN-NNN-NNN
```


| Раздел            | Описание                                                                      | Пример            |
| ----------------- | ----------------------------------------------------------------------------- | ----------------- |
| `T`               | Префикс типа (см. ниже)                                                       | `C`               |
| `NNN-NNN-NNN-NNN` | 12-значное случайное число, разбитое на **четыре** группы по 3 для читаемости | `482-930-174-005` |


### Префиксы типов


| Префикс | Значение          | Кто использует                                                                                                                                                                   |
| ------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `C`     | Creator           | Индивидуальный художник, фотограф, мастер                                                                                                                                        |
| `B`     | Brand             | Компания, студия, лейбл                                                                                                                                                          |
| `P`     | Proof Institution | Эксперт, аукционный дом, орган сертификации — аттестации (`submitProof`) для любого паспорта                                                                                     |
| `M`     | Museum            | Зарегистрованный музей или коллекция — **неограниченные** passport mints для институциональных holdings (например, работы ушедших художников); может также `submitProof` как `P` |


### Лимиты минта по месяцам (эталонный контракт)

Эталонный деплой `ObjectDigitalPassport` (v0.6) ограничивает **новые mint'ы паспортов** для каждого кошелька в пределах **календарного месяца** (гипотеза против спама; только комиссия сети — без сбора протокола ODP). Лимиты зависят от зарегистрированного **типа Creator**:


| Тип | Оценочный лимит                                                               |
| --- | ----------------------------------------------------------------------------- |
| `C` | 1,000 минтов / месяц                                                          |
| `B` | 100,000 минтов / месяц                                                        |
| `P` | Без лимита (`getRemainingMints` возвращает `2^32−1` в референсной реализации) |
| `M` | Без лимита (как и `P`)                                                        |


**Музеи и крупные инвентарные массивы**, оцифровывающие holdings коллекции, должны регистрироваться как `**M`** (музей/коллекция), **не `B` и не `C`**. Префикс `**P**` предназначен для институций, чья **основная** роль в протоколе связана со сквозными **proof**-аттестациями; `**M`** означает custodian / выпуск от лица коллекции. Очень высокая пропускная способность всё равно может использовать **несколько кошельков**, если так допускает политика.

**Префиксы типов определяются исключительно этой спецификацией.**
Ни один участник, компания или реализация не могут вводить собственные префиксы.
Новые префиксы добавляются только через официальное обновление этой спецификации, после чего смарт-контракт пере-развертывается с обновлённым allowlist.
Контракт это обеспечивает: любая попытка регистрации с нераспознанным префиксом отклоняется на уровне контракта.

### Примеры

```
C-482-930-174-005   ← индивидуальный creator
B-029-384-751-224   ← бренд или компания
P-001-293-847-119   ← институция для proof
M-204-839-112-441   ← музей или коллекция
```

### Алгоритм генерации

Референсный контракт (эталон v0.6) использует (packed encoding, в том же стиле, что и Passport ID):

```
entropy  = keccak256(block.timestamp, block.prevrandao, msg.sender, nonce, gasleft())
number   = uint64(uint256(entropy)) % 1_000_000_000_000   // 12 десятичных цифр
if number уже занят: nonce++, retry (ограниченное число попыток)
group_1  = number / 1_000_000_000
group_2  = (number / 1_000_000) % 1_000
group_3  = (number / 1_000) % 1_000
group_4  = number % 1_000
creatorId = type + "-" + pad3(group_1) + "-" + pad3(group_2) + "-" + pad3(group_3) + "-" + pad3(group_4)
```

1 триллион возможных значений. Уникальность гарантируется контрактом.

### Полная публичная идентичность

У каждого участника есть два формата идентичности:

```
Короткий:  C-482-930-174-005
Полный:    0x742d35Cc…4438f44e
```

В публичных материалах **короткая** строка — ID профиля, **полная** — **только адрес кошелька** (желательно checksum EIP-55). Человекочитаемое **имя** в маркетинговых текстах можно ставить до или после адреса, но оно **не** часть канонической строки и **не** проверяется on-chain.

Полная идентичность включает:

- Короткий ID профиля (**обязательно**)
- Полный адрес кошелька (0x… — 42 символа, **обязательно**)
- Имя или название организации (**необязательно**, только оффчейн-метка)

Полный адрес кошелька — криптографическая опора идентичности и уникальности.
Имя — только человекочитаемая метка. Адрес кошелька — доказательство, подделать которое нельзя.

### Требование публичной идентичности

**Все участники — создатели (C), бренды (B), институции доказательств и родственные типы (P), музеи и коллекции (M) — должны публично публиковать короткий ID профиля вместе с полным адресом кошелька.**

Это фундаментальное требование протокола, а не просто рекомендация.
Система работает только тогда, когда любой может проверить, кто стоит за каждым объектом и за каждой аттестацией.

Участникам следует публиковать свою идентичность максимально прозрачно, с приоритетом на каналы, где обычный человек ищет это в первую очередь:

- На своем официальном сайте — заметно, не прячьте в меню
- В публичных профилях соцсетей и биографиях
- На физических объектах, упаковке и сертификатах, когда это применимо
- В других публичных каналах, которые они контролируют, где ожидается контекст для проверки

**Оба формата должны легко находиться:**

```
Создатель на example.com:
  Короткий:  C-482-930-174-005
  Полный:    0x742d35Cc…4438f44e

Музей на museum.com:
  Короткий:  M-204-839-112-441
  Полный:    0xB3F924ee…1823A3c8A
```

**Важно:** названия институций не хранятся в протоколе и не показываются верификаторами. На on-chain находится только ID профиля. Верификаторы показывают только ID — пользователи должны найти его на официальном сайте институции, чтобы подтвердить идентичность.
Это предотвращает регистрацию под любым названием институции и получение незаслуженного доверия.

Так протокол работает без централизованного реестра: существующая публичная репутация участника становится доказательством его идентичности. Любой может регистрироваться — но только легитимные участники будут иметь свой ID, доступный на доверенном публичном сайте.

### На упаковке и физических объектах

```
ODP-2026-03-004829301
C-482-930-174-005
```

Короткий формат намеренно сделан компактным — удобно печатать, зачитывать вслух или распечатывать.

### Делегирование минта агенту (эталон v0.6)

**Агент минта** — отдельный кошелёк, который может **подписывать транзакции минта** за **владельца профиля** (ниже — **принципал**). Так удобно отдавать минт подрядчику или «операционному» кошельку, не передавая ему сам профиль.

**Как включить (двухшаговое рукопожатие, всё в контракте — см. §8):**

1. Агент вызывает `**requestMintAgentRole(principalCreatorId)`** — заявка на роль для указанного `**creatorId`** принципала.
2. Принципал (кошелёк, которому принадлежит этот профиль) вызывает `**confirmMintAgentRole(agent)`** — подтверждает агента. Смена агента, отзыв и отмена заявок тоже задаются on-chain.

**Чем это не является:** это **не** «делегирование публикации» (`**delegateCreatorPublishing`**). Публикация разрешает только обновлять ссылки (`**updatePassportUrls`**) у **уже** выпущенных паспортов. Агент минта — про **создание** новых паспортов от имени принципала.

**Что записывается в паспорт при минте через агента:** выпускающая сторона по-прежнему **принципал**. В записи `**Passport`**: `**creator`** и `**owner**` — кошелёк принципала; `**creatorId**` — его профиль. Поле `**mintAgent**` — адрес агента, если транзакцию отправил он, иначе нулевой адрес, если минтил сам принципал. Для пользователей и верификаторов «чей это объект» определяется **принципалом**; агент — только тот, кто оплатил газ за вызов. Лимиты **C** / **B** на месяц списываются с **принципала**, не с агента.

## 4. Proof Institution (институция доказательств)

Любой музей, галерея, аукционный дом, эксперт или орган сертификации может зарегистрироваться как Proof Institution, используя префикс типа `P`. Регистрация открыта для любого участника по всему миру — одобрение не требуется.

### Что делает Proof Institution

Зарегистрированная Proof Institution может прикрепить к любому зарегистрированному паспорту on-chain **Proof record**. Это неизменяемое публичное утверждение:
*"Мы рассмотрели этот объект и подтверждаем его подлинность."*

Proof records не изменяют исходный паспорт. Они накапливаются вместе с ним.
Полная история proof навсегда видна в сети.

**Протокол не проверяет, действительно ли ID профиля принадлежит заявленной институции.**
Основанием для доверия служит лишь публичная публикация ID профиля на реальном веб-сайте — вместе с реальной репутацией институции.
Верификаторы показывают только ID профиля, а не самоназванное имя.

### Институциональная претензия к подлинности («флаг подделки»)

**On-chain:** `**ODPCounterfeitConcern`** предоставляет `**raiseCounterfeitConcern`**, `**clearCounterfeitConcern`**, `**getCounterfeitConcern**`. Поднять флаг могут только зарегистрированные профили `**P**` или `**M**`; снять — только тот профиль, который его поднял. Флаг — институциональное мнение, а не судебное решение. `**reasonHash**` — это `**keccak256(UTF-8)`** опционального оффчейн-заявления (по аналогии с верификаторами, которые хэшируют строку причины).

**Оффчейн / метаданные proof:** споры, методология и отчёты по-прежнему уместны в `**passport.json`**, связанных документах и `**submitProof`** (`documentHash` / `documentUrl`).

### Опциональная публичная база ID организаций (оффчейн, против спама)

Реализации верификаторов, маркетплейсов или институциональных интерфейсов **могут** вести **оффчейн** allowlist или каталог профилей `P` (и при необходимости `M`), которые они **выделяют** или **показывают по умолчанию**, чтобы **снизить шум** и упростить UX. Это **не** часть on-chain протокола и **не** отменяет открытую регистрацию в контракте.

**Нормативное ожидание для каталога, который позиционируется как надёжный:** для каждой записи **обязательна** как минимум одна ссылка **HTTPS** на **официальный сайт организации** — на страницу (или устойчивый раздел), где **тот же** ID профиля **явно опубликован**, чтобы пользователь мог проверить соответствие без слепого доверия к оператору каталога. Списки без таких проверяемых ссылок на сайт организации **не следует** выдавать за авторитетные; это максимум неофициальная подборка.

### Опциональная P-аффилиация (один parent на child)

Когда две Proof Institution должны отображаться связанными в простой иерархии (головной офис и подразделение, объединение и участник, сеть и узел — конкретный смысл задаётся оффчейн), протокол допускает опциональную **одноуровневую** аффилиацию между `P`:

- child `P` предлагает parent `P`
- parent `P` подтверждает on-chain
- child `P` может иметь **не более одного активного parent `P`**

Такой двухшаговый handshake снижает спам и исключает односторонние claims доверия.

```
ODP-2026-03-004829301  (original passport, 2026)
  └── Proof from P-029-384-751-224  04-2031
  └── Proof from P-482-930-174-005  09-2038
  └── Proof from P-001-293-847-119  01-2044
  └── Proof from P-774-002-391-888  12-2051
```

### Формат Proof ID

```
PRF-YYYY-MM-NNNNNNNN
```

Суффикс — **десятичная строка фиксированной ширины** (в референсной реализации — 8 цифр). Референсный `**ObjectDigitalPassport`** (эталон v0.6):

```
key              = uint32(year) * 100 + uint32(month)          // год/месяц события proof из аргументов tx
passportIdHash   = keccak256(utf8(passportId))                 // как `Passport.passportId` / аргумент `submitProof`
entropy          = keccak256(block.timestamp, block.prevrandao, msg.sender, nonce, key, passportIdHash, gasleft())
number      = uint32(uint256(entropy)) % 100_000_000      // 00000000–99999999
if number уже занят для этого года+месяца: nonce++, retry (ограниченное число попыток)
proofId     = "PRF-" + decimal(year) + "-" + two_digit(month) + "-" + zero_pad(number, 8)
```

Пример: `PRF-2031-03-07392018`

### Поля записи proof


| Поле              | Тип       | Обязательное | Описание                                                                                           |
| ----------------- | --------- | ------------ | -------------------------------------------------------------------------------------------------- |
| `proofId`         | `string`  | да           | Автоматически: `PRF-YYYY-MM-` + числовой суффикс фиксированной ширины (см. алгоритм выше)          |
| `contractVersion` | `uint8`   | да           | Упакованная линия спеки на момент отправки (должна совпадать с реестром; эталонный деплой → **6**) |
| `prover`          | `string`  | да           | ID профиля институции (например, `P-029-384-751-224`)                                              |
| `passportId`      | `string`  | да           | Passport ID аттестуемого объекта (та же строка, что и `Passport.passportId`; имя поля ABI в эталоне — `passportId`) |
| `documentHash`    | `bytes32` | нет          | SHA-256 подписанного документа экспертизы. `bytes32(0)`, если документа нет                        |
| `documentUrl`     | `string`  | нет          | URL документа экспертизы (макс. 512 символов; пусто, если хэш нулевой)                             |
| `timestamp`       | `uint256` | да           | Устанавливается контрактом                                                                         |


### Стоимость

Отправка записи proof стоит только gas (~$0.01 POL на Polygon).
Протокол комиссий не взимает.

### Требование публичной идентичности для институций

Публичное требование идентичности из раздела 3 полностью относится к Proof Institutions.
Proof от институции, чей ID нельзя найти на их официальном сайте, не несёт верифицируемой ценности.

## 5. Verification Label

Метка верификации — **опциональный** слой удобства.
Базовое доверие строится на on-chain записи и состоянии seal (NFC/нумерованная пломба).
Если метка используется, она ускоряет проверку для конечного пользователя.

### Если метка используется: обязательные элементы


| Элемент                    | Описание                                                                                                  | Пример                              |
| -------------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| QR-код                     | Кодирует `odp://ODP-YYYY-MM-NNNNNNNNN`. Уровень коррекции ошибок Q (минимум 25%). Семантика URI: §12, §19 | `odp://ODP-2026-03-004829301`       |
| Passport ID (`passportId`) | Полный идентификатор объекта в человекочитаемом виде                                                      | `ODP-2026-03-004829301`             |
| Маркер протокола           | Название протокола или его аббревиатура                                                                   | `ODP` или `Object Digital Passport` |


### Опциональные элементы

Реализации могут добавить любое из следующего — протокол их не ограничивает:

- ID профиля текстом (только справочно; не источник доверия)
- Название объекта
- Имя создателя
- Год создания
- Номер издания
- Логотип создателя или визуальный идентификатор
- NFC-чип (встроенный в метку или под ней)
- Номер seal (напечатан на метке или на отдельном элементе)

**Нота о доверии (нормативно):** ID профиля, напечатанный на упаковке/лейбле, сам по себе **не является** доверенным источником и **не обязателен** на метке. Проверяющим следует получать ID профиля из верифицированных публичных источников (официальный сайт и публичные профили в соцсетях), после чего сверять с данными on-chain.

### Если метка используется: требование удержания seal

Метка должна физически покрывать или удерживать seal:

- Если используется NFC-крипточип (NTAG 424 DNA TagTamper) — его следует расположить
под меткой или внутри метки. Чип TagTamper постоянно электронно фиксирует снятие.
Физическое расположение под меткой добавляет дополнительный визуальный индикатор вскрытия, но криптографическое обнаружение вскрытия обеспечивается самим чипом, а не меткой.
- Если используется нумерованный seal — метка должна перекрывать seal так,
чтобы снятие метки требовало снять seal.

### Что эта спецификация НЕ определяет для метки

- Размер, форма, цвет, материал
- Типографика и визуальный дизайн
- Размещение элементов
- Производитель

Это решения реализации. Спецификация определяет только то, что должно присутствовать, а не то, как это должно выглядеть.

## 6. Физическая пломба (Physical Seal)

Физическая пломба связывает цифровой паспорт с конкретным физическим объектом.

**Модель v0.6:** пломбы — это **якоря идентификации** — записи типа `**nfc`** или `**numbered_seal`** внутри блока `passport.json` `**anchors[]`** (§9). Их байты защищены целостностью on-chain через `**dataHash`** и `**anchorsHash`** и отмечены в `**anchorTypesMask`**; выделенных on-chain полей пломбы больше **нет** (`sealType`, `sealHash`, `nfcPublicKey`, `nfcModel` убраны из реестра в линии v0.6).

Пломба **опциональна**: обязательный минимум идентификации физического объекта — набор якорей `photo` + `dimensions` + `materials` + `distinguishing_features` (§9). Якорь пломбы добавляет более сильную, машинопроверяемую привязку поверх этого минимума и рекомендуется для ценных объектов.

Паспорта цифровых объектов (тип `digital`) не используют физическую пломбу.
Хэш файла служит криптографической привязкой.

### Метод A — NFC-крипточип (NTAG 424 DNA TagTamper)

Криптографический NFC-чип, встроенный в объект или прикреплённый к нему.
Рекомендуется для объектов высокой ценности, произведений искусства и коллекционных предметов.

**Строки модели в якоре `nfc`:** `**NTAG424DNA`** или `**NTAG424DNA_TAGTAMPER`**. Обычные теги Type 2 (например NTAG 213) **не** являются подходящим якорем `nfc`. В линии v0.6 строка модели живёт в `data.model` якоря (словарь, определённый SPEC), а не в on-chain allowlist.

**Как это работает в текущем развёртывании ODP v0.6 (NTAG 424 DNA):**

```
Регистрация (обязательный порядок для эмитентов):
  1. Подготовить чип так, чтобы EV2-ключ приложения, который вы
     опубликуете, был загружен в чип (обычно 16-байтовый AES-ключ 0x00)
  2. Отсканировать живой чип ODP Android-компаньоном
     ([odp-android-companion](https://github.com/object-digital-passport/odp-android-companion);
     issuer-chip-setup) и импортировать JSON odp-chip-issuer-setup
     в passport.html — подтверждает UID, EV2-ключ и TagTamper INTACT
     до минта
  3. Записать UID чипа, модель, ключ и заметки о развёртывании
     в якорь `nfc` внутри anchors[] в passport.json
  4. Паспорт хэшируется и регистрируется on-chain как обычно — байты
     якоря защищены dataHash и anchorsHash, бит nfc установлен
     в anchorTypesMask
  5. Записать NFC-носитель (ссылку Verify) после появления Passport ID

Верификация (основной профиль: odp-ntag424-ev2-symmetric-cr-v1):
  1. Верификатор получает якорь nfc из passport.json и подтверждает
     целостность JSON по on-chain dataHash (либо только массив anchors
     по anchorsHash)
  2. Телефон выполняет AuthenticateEV2First, используя 16-байтовое
     значение якоря как EV2 AES-ключ приложения
  3. Чип и телефон завершают взаимный challenge-response (RndA/RndB)
  4. Совпадение → SEAL_NFC_AUTHENTIC по симметричному EV2 challenge-response
     Несовпадение → неверный чип, неверный ключ или неверная подготовка
```

**Честная оговорка для этой версии SPEC:** NTAG 424 DNA **не** предоставляет специфичный для паспорта ECC-приватный ключ, который подписывает произвольный challenge верификатора и проверяется публичным ключом on-chain. Родной challenge-response этого чипа — **симметричная взаимная EV2-аутентификация**. В линии ODP v0.6 публикация 16-байтового EV2-ключа приложения внутри целостно-заякоренного якоря `nfc` — основная публичная модель верификации. `Read_Sig` остаётся лишь дополнительным доказательством от производителя.

**Поведение TagTamper:**

Добавляет петлю антенны для обнаружения вскрытия. Физическое снятие навсегда регистрируется как событие вскрытия.

```
Пломба цела  → чип сообщает: INTACT
Пломба снята → чип сообщает: TAMPERED (навсегда, сбросить нельзя)
```

**Профиль высокой достоверности TagTamper (companion-верификатор):**

Для `NTAG424DNA_TAGTAMPER` эталонный Android-компаньон ([odp-android-companion](https://github.com/object-digital-passport/odp-android-companion)) считает скан **высокодостоверным (high assurance)** только при одновременном выполнении всех условий:

1. **Симметричный EV2 challenge-response** по целостно-заякоренному ключу из якоря `nfc` (16-байтовый EV2-ключ приложения) → `chipKeyMatch = PASS`
2. **Аутентифицированный TagTamper** после EV2 → `tamperState = INTACT`
3. **Совпадение UID чипа**, когда `passport.json` / handoff предоставляет `data.uid` якоря `nfc` → аутентифицированный живой UID равен ожидаемому

Компаньон показывает это как `highAssuranceSeal`. Для обычных паспортов `NTAG424DNA` (без TagTamper) это **не** проверяется.

**Честные пределы:** ни один верификатор не может быть полностью неподделываемым. Вор с оригинальным чипом и ключом, недобросовестный шаг подготовки или утечка EV2-ключа всё равно подрывают доверие. Этот профиль **блокирует** распространённые обманы: поддельные теги «только с URL», чужие чипы с другим ключом и физически вскрытые пломбы TagTamper (видны как `TAMPERED`).

**Физическая установка:**
Чип должен быть встроен или герметизирован так, чтобы при снятии происходило видимое разрушение. Метод установки описывается в `data.notes` якоря.

**Поля `data` якоря `nfc` в `anchors[]` внутри `passport.json`:**


| Поле          | Обязательное | Описание                                          |
| ------------- | ------------ | ------------------------------------------------- |
| `uid`         | да           | 7-байтовый UID чипа, hex в нижнем регистре        |
| `publicKey`   | да           | Для NTAG 424 DNA: 16-байтовый EV2 AES-ключ приложения (hex). Для будущих NFC-чипов: материал публичной проверки, специфичный для развёртывания |
| `model`       | да           | `NTAG424DNA` или `NTAG424DNA_TAGTAMPER` (словарь SPEC) |
| `installedAt` | да           | дата установки в ISO 8601 (например `2026-03-15`) |
| `notes`       | нет          | способ установки, место, материал герметизации    |


### Метод B — нумерованная физическая пломба

Физическая пломба с уникальным напечатанным номером.
Примеры: голографическая наклейка, восковая печать, свинцовая пломба, лейбл со следами вскрытия.

Создатель отвечает за использование пломбы, которую нельзя снять без видимых повреждений.
Этот метод даёт физическую отсылку, а не криптографическое доказательство.

**Поля `data` якоря `numbered_seal` в `anchors[]` внутри `passport.json`:**


| Поле     | Обязательное | Описание                                               |
| -------- | ------------ | ------------------------------------------------------- |
| `number` | да           | Номер пломбы ровно как напечатан                       |
| `type`   | да           | Тип пломбы (например `holographic sticker`, `wax seal`) |
| `color`  | нет          | Цвет                                                   |
| `size`   | нет          | Размеры (например `30x30mm`)                           |
| `notes`  | нет          | Дополнительное описание                                |

| Условие                                                    | Допустимо?                       |
| ----------------------------------------------------------- | --------------------------------- |
| Якорь NFC-крипточипа (NTAG 424 DNA / TagTamper, `NTAG424DNA` или `NTAG424DNA_TAGTAMPER`) | ✅ |
| Только якорь нумерованной пломбы                            | ✅                                 |
| Оба якоря пломбы                                             | ✅                                 |

### On-chain привязка якорей пломбы

У якорей пломбы нет выделенных on-chain полей. Их целостность привязана через `**dataHash`** (весь документ) и `**anchorsHash`** (только массив `anchors`), а присутствие видно в `**anchorTypesMask`** (биты `nfc` = 256, `numbered_seal` = 512 — §9).


### Справочно — другие NFC / tag-технологии

- **HF/UHF RFID** или метки **только с QR**: подходят для логистики или UX, но они **не** являются равноценной заменой NFC-криптоверификации **уровня 2A**, пока будущая SPEC не определит привязку с нормативным рецептом проверки.
- **Другие аутентифицированные NFC-чипы** (вендорские secure-element теги с документированным challenge-response и экспортируемыми публичными ключами): МОГУТ быть добавлены в будущей редакции SPEC расширением словаря `data.model` якоря `nfc` и **уровня 2A** — обычные статические теги NDEF/UID остаются плохо подходящими для той же модели безопасности, что и текущее семейство NTAG 424 DNA.
- **Экспериментальные демо** (например вспомогательные связки тегов с блокчейном): вне области применения эталонного словаря; интеграции не должны подразумевать поддержку протокола без строки модели, определённой в SPEC.

### Адреса канонического реестра (нормативно)

Адреса ниже — **канонический реестр ODP v0.6** в основной сети Polygon. Они **нормативны**: объект, описанный как имеющий «паспорт ODP», или идентификатор, предъявленный как ODP **Passport ID** (§2) или **Profile ID** (§3) без дополнительных уточнений, ссылается на запись в **этом** реестре.

Следствия:

- Верификаторы SHOULD резолвить по умолчанию именно в эти адреса и ОБЯЗАНЫ прямо указывать, какой реестр дал результат, если резолвят куда-то ещё.

### Эталонный контракт — минт (v0.6)

- `**mintPhysical(m, dataUrlIsFolderBase, mintOnBehalfOfCreatorId)`** / `**mintDigital(...)**` / `**mintMixed(...)**` — `**m**` — унифицированный tuple `PassportMintInputs`: `core` (карточка + классификация), `dataHash`, `dataUrl`, `imageHash`, `imageUrl`, `fileHash`, `anchorsHash`, `anchorTypesMask`. Правила по типу: `physical` → `fileHash == 0`, `imageHash != 0`, маска ⊇ `photo|dimensions|materials|distinguishing_features`; `digital` → `fileHash != 0`, маска ⊇ `file_hash`; `mixed` → оба набора.
- `**mintDigitalViaExtension(mintClass, payload, dataUrlIsFolderBase, mintOnBehalfOfCreatorId)`** / `**mintPhysicalViaExtension(...)**` — зарегистрированное governance расширение `**IODPExtension**`; `**normalize**` возвращает ABI-кодирование tuple `PassportMintInputs`. При успехе роутер эмитит `**ExtensionMintUsed(mintClass, kind, passportId)`** с `**kind`**: `0` = digital, `1` = physical, в дополнение к `**PassportMinted`** (включает поля карточки и якорей плюс `**mintAgent**`).

### Эталонный контракт — события, владение, URL, отзыв (v0.6)

- `**recordPassportEvent(passportId, kind, value, note, attachmentHash, attachmentUrl)`** — append-only запись слоя B; вызывается `**creator`**, `**owner`** или `**governance`**; для отозванных паспортов отклоняется. `kind`: `1` = статус (`value` = новый `lifecycleStatus` 1–4, обновляет хранимое сводное поле), `2` = местонахождение, `3` = права, `4` = состояние, `5` = повреждение, `6` = реставрация, `7` = произвольное (`value` ОБЯЗАН быть 0 для видов 2–7). `note` ≤256 байт; опциональное вложение = SHA-256 + HTTPS-подсказка (≤512; URL пуст при нулевом хэше). Эмитит `**PassportEventRecorded`**; on-chain хранилище держит только `eventCount` / `lastEventKind` / `lastEventAt` — история читается из лога. **Текущее значение любого изменяемого аспекта — последнее событие этого вида.**

### Эталонный контракт — деплой, freeze, governance (v0.6)

- `**deployer`**: `immutable`, задаётся в конструкторе как адрес, выполнивший деплой; **единственный** кошелёк, которому разрешено `freeze()`.
- `**governance`**: `address`; **конструктор задаёт `governance = msg.sender`**. Используйте `**transferGovernance(newAddr)**` (вызывающий должен быть текущим `governance`), чтобы передать управление мультисигу/DAO.
- Governance подключает спутники: `**setRelationsSatellite(addr)`**, `**setExtensionRouter(addr)`**.
- `**freeze()**`: **только `deployer`**; **необратимо**; устанавливает `**frozen = true`** и блокирует каждый изменяющий состояние пользовательский путь основного реестра (`registerCreator`, `mintPhysical` / `mintDigital` / `mintMixed`, `recordPassportEvent`, `updatePassportUrls`, `transferPassport`, `revokePassport`) с откатом `**EC(58)`**; все **чтения** остаются доступны. Это **предохранитель линии v0.x**, и он **планируется к удалению в стабильном v1** (`[docs/IDEAS_V1.md](docs/IDEAS_V1.md)`). Freeze затрагивает только основной реестр; спутники сохраняют своё состояние.

### Reverts (откаты)

Эталонный байткод использует только `**error EC(uint16 code)`** (без строковых сообщений), чтобы уложиться в лимит размера EIP-170. Интеграторы **обязаны** расшифровывать коды по исходнику задеплоенного контракта.

### Запланированные расширения протокола (семантика пока не реализована)

Ниже — **перспективные идеи протокола** — они **не** реализованы так, как описано, в семантике текущего эталонного `[ObjectDigitalPassport.sol](chain/contracts/ObjectDigitalPassport.sol)`. *(Разбиение по EIP-170 — линкуемая `**ODPPassportLib`** и спутники — уже реализовано в эталонном стеке; см. §11 уровень 1C и документацию по деплою.)* Смотрите `**[docs/PROTOCOL_TRACKS.md](docs/PROTOCOL_TRACKS.md)`** и `**[docs/EIP170_STRATEGY.md](docs/EIP170_STRATEGY.md)`** перед планированием дальнейшей on-chain работы.

#### A) Глобальная уникальность `dataHash` паспорта (план)

**Замысел (продуктовая опция):** отклонять новый минт, если канонический `**dataHash`** `passport.json` уже был использован для **любого** паспорта в этом реестре, так что один хэш якорит не более одного `passportId` за всё время жизни деплоя.

**Текущее поведение:** эталонный контракт допускает несколько паспортов с одинаковым `dataHash` (разные `passportId`). Переход на глобальную уникальность — это **ломающее изменение семантики** для эмитентов, переиспользующих идентичный JSON для разных объектов.

**При реализации:** проверка должна быть в общем пути коммита минта (все маршруты `mintDigital` / `mintPhysical` / `mint*ViaExtension`). **Не** применять это правило к `**attestExternalDocument`** / якорям документов на кошельке — эти обязательства имеют **другой** on-chain смысл (аттестация хэша файла, а не `Passport.dataHash`). **Рекомендуется:** после `revokePassport` хэш остаётся **потреблённым** (слот никогда не освобождается), чтобы тот же якорь JSON не получил «вторую жизнь».

#### Б) Опциональная аттестация автора (ECDSA) (план)

**Замысел:** позволить **опциональную** криптографическую привязку между **отдельным ключом автора** и якорем целостности (`dataHash`) и/или профилем эмитента, не заменяя доверие к зарегистрированному минтеру, когда эта возможность не используется.

**Не является целью, пока не реализовано:**

- Интеграторы **не должны** предполагать, что `ecrecover` или подписи автора проверяются on-chain в эталонном контракте.
- Опциональная подпись автора **сама по себе не** останавливает скомпрометированного минтера от минта **в обход** пути автора (если только будущая продуктовая линия не сделает аттестацию автора **обязательной**).

**Предлагаемая форма (нормативная цель для будущей линии SPEC, подлежит ревью):**

1. **Хранилище или события:** сохранять `authorSigner` (`address`) в `Passport`, когда используется, и/или эмитить отдельное событие с подписавшим и обязательством по подписи для индексаторов. Хранение полного `bytes signature` on-chain опционально (газ против переверифицируемости).
2. **Дайджест:** использовать типизированные данные **EIP-712** с доменом `chainId` + `verifyingContract` и структурой, включающей как минимум `**bytes32 dataHash`** и привязку к `**creatorId`** (или кошельку принципала), чтобы подпись была специфична для сети и реестра. Более простые хэши **EIP-191** допустимы, только если задокументирована семантика коллизий и повторного использования.
3. **Взаимодействие с агентом минта:** аттестация должна ссылаться на семантику профиля/кошелька **принципала** (on-chain `creator` после минта), а не просто на адрес агента-делегата, если явно не спроектировано иначе.
4. **Параметры:** новые calldata-аргументы у точек входа минта (например `authorSigner`, `authorSignature`) с **пустым** / нулевым значением-меткой «пропустить проверку» для обратной совместимости.

**Условие реализации:** размер байткода (**EIP-170**); вероятно **после** выноса вспомогательной логики в спутник или выпуска нового поколения контракта.

## 9. JSON паспорта (Passport JSON)

Нормативный off-chain документ: `**passport.json`** (UTF-8 JSON, один объект). Минимизированные байты якорят `**dataHash`** on-chain (§8, §10). Для **публичного хостинга** и **переносимой выдачи** эти байты **должны** находиться внутри файла `**.odpass`** (ZIP §15) — **не** как единственное тело HTTP-ответа по `dataUrl` (см. ниже).

### Иерархия `.odpass` (нормативно)

Переносимый артефакт — один файл, имя **заканчивается** расширением `**.odpass`** (пример: `ODP-2026-03-004829301.odpass`). Это архив **ZIP**; имена записей — UTF-8. **Нормативное дерево:**

```
<passportId>.odpass          ← внешний файл; расширение буквально .odpass
├── passport.json            ← обязательно: канонический документ (этот §9); якорь dataHash
├── manifest.json            ← обязательно: метаданные бандла для UX (не якорь доверия)
└── originals/               ← опционально (эталонный layout бандла; см. `bundleVersion` в §15)
    └── <role>__<basename>   ← байты вложений (напр. роли digital, image, image2, image3)
```

- `**passport.json**` — задаётся таблицами полей и правилами **§9**; правила хэширования — **§10**.
- `**manifest.json`** — поле `**manifest.originals`** сопоставляет логические ключи (`fileHash`, `imageHash`, …) путям под `originals/`, если вложения включены (**§15.1.1**).
- **Layout вложений:** байты с on-chain хэшами **ДОЛЖНЫ** находиться только под `**originals/`**, пути — в `**manifest.originals`** (**§15.1**). Старые каталоги верхнего уровня (`original/*`, `image/*`, `image2/*`, `image3/*`) **НЕ ДОЛЖНЫ** использоваться как единственный layout в нормативном бандле `.odpass`; верификаторы **НЕ ДОЛЖНЫ** искать файлы там как запасной вариант (**§15.1**).

Полные правила ZIP, форма манифеста и офлайн-проверка — в **§15**.

### Хостинг `dataUrl` (сторонние сайты)

`dataUrl` указывает на файл `**.odpass`** (ZIP **§15**) на публичном HTTPS-хосте (object storage, CDN, статический сайт, Git forge и т.п.). **Отдельный сырой `passport.json` по этому URL не допускается** — тело ответа HTTP **ДОЛЖНО** быть этим файлом `**.odpass`**; верификатор извлекает из ZIP `passport.json`. Последний сегмент пути **ДОЛЖЕН** быть `<passportId>.odpass` с **точной** строкой Passport ID из контракта (поле `passportId` в эталонном ABI; legacy `humanId` в старых ABI; напр. `ODP-2026-03-004829301.odpass`). Реализации, которые получают файл, **ОБЯЗАНЫ** выполнять:

1. **HTTPS** — URL с TLS; сервер возвращает HTTP **200**, тело — файл `**.odpass`** (ZIP §15; сигнатура `PK\x03\x04`), не HTML, не логин и не UI репозитория. Из архива извлекается `**passport.json`**, далее каноникализация по §10.
2. **Raw на Git-хостингах** — для GitHub, GitLab и т.п. используйте **raw** URL к файлу `**.odpass`** (например `raw.githubusercontent.com/.../ODP-....odpass`), не HTML blob.
3. **CORS (веб-верификаторы)** — хост **ДОЛЖЕН** разрешать cross-origin **GET** для `dataUrl`, чтобы браузер прочитал тело.
4. **Целостность** — после извлечения и каноникализации `passport.json` байты **ДОЛЖНЫ** совпадать с `dataHash` on-chain (см. §10).

#### Ответственность создателя за `passport.json` после mint (нормативно)

Протокол **не** хранит полный `passport.json` в on-chain — только `dataHash` и связанные поля (см. §8). Создатель **ОБЯЗАН** сохранять **канонический минимизированный** `passport.json` (внутри публикуемого файла `**.odpass`**). `**dataUrl`** может быть пустым на mint; если задан — создатель должен разместить файл `**.odpass**` по этому адресу для публичной веб-верификации.

1. Если `dataUrl` **не пуст**, но нет HTTP **200** с валидным файлом `**.odpass`** (ZIP §15), из которого `passport.json` после каноникализации совпадает с `dataHash`, верификаторы **ОБЯЗАНЫ** считать веб-верификацию **проваленной** (напр. **UNVERIFIABLE** / несовпадение хэша по §11).
2. Если `dataUrl` **пуст**, HTTP не применяется; проверить `dataHash` могут стороны с `**.odpass`** или `**passport.json`** (UX: предупреждать создателя при mint).
3. `**creator` или `owner`** могут обновить `dataUrl` (и основной `imageUrl`) через `**updatePassportUrls**` (эталон **v0.4**) **без** повторного mint, если размещённый `**.odpass`** по-прежнему содержит тот же `passport.json` для `dataHash` и паспорт не отозван.
4. **Референсные и совместимые UIs** **ДОЛЖНЫ** требовать **явного подтверждения** перед mint: публикация `**.odpass`** — ответственность создателя; публичная проверка зависит от доступности файла `**.odpass`** по URL при заданном `dataUrl`; пользователь должен скачать бандл до закрытия экрана успеха, если UI это предлагает.

### Каноническая схема паспорта v0.5 (нормативно)

Канонический `passport.json` для текущей линии — это форма **v0.5**, используемая референсным контрактом и веб-интерфейсом. Старые верхнеуровневые таксономии `type` / `digital.subtype` больше **не** являются главным классификатором. Обязательная ось классификации теперь такая:

- `domain`
- `objectType`
- `status`
- `contentClass`
- опционально `refinementTags`

#### Обязательные верхнеуровневые группы полей

| Поле / группа | Обязательное | Тип | Примечание |
| --- | --- | --- | --- |
| `version` | yes | `string` | Для этой линии ДОЛЖНО быть `"0.5"`. |
| `passportId` | yes | `string` | ДОЛЖНО совпадать с Passport ID on-chain. |
| `title` | yes | `string` | Человекочитаемое название. |
| `description` | рекомендуется | `string` | Краткое описание объекта. |
| `creationDate` | рекомендуется | `string` | Дата создания объекта или якорь периода создания; формат SHOULD быть однозначным и ISO-подобным. |
| `authorship` | yes | `object` | Содержит `author` (обязательно), опционально `coAuthors`, опционально `team`. |
| `domain` | yes | `string` | Область / поле, например `contemporary_art`, `graphic_design`, `software`. |
| `objectType` | yes | `string` | Одно из `physical`, `digital`, `mixed`. |
| `status` | yes | `string` | Lifecycle-состояние, зеркалируемое в on-chain `lifecycleStatus`. |
| `contentClass` | yes | `string` | Одно из контролируемых значений ниже. |
| `aiStatus` | yes | `string` | Одно из контролируемых значений ниже. |
| `verificationMethod` | yes | `string` | Одно из контролируемых значений ниже. |
| `edition` | yes | `object` | ДОЛЖНО содержать `model`; МОЖЕТ содержать `number` и `total`, если это осмысленно. |
| `year`, `month` | yes | integer | UTC год/месяц минта; ДОЛЖНЫ совпадать с on-chain mint inputs. |
| `registeredAt`, `registration` | yes | number / object | Представление момента регистрации только через UTC; см. ниже. |

#### Контролируемые значения

| Поле | Допустимые значения |
| --- | --- |
| `status` | `concept`, `prototype`, `produced_object`, `archived` |
| `contentClass` | `static`, `time_based`, `spatial`, `textual`, `composite`, `executable` |
| `aiStatus` | `none`, `assisted`, `generated` |
| `verificationMethod` | `self_asserted`, `institutional`, `nfc`, `c2pa`, `hybrid` |
| `edition.model` | `unique`, `limited`, `open`, `dynamic` |

#### Объектно-специфические блоки

| Блок | Обязателен когда | Примечание |
| --- | --- | --- |
| `currentState` | рекомендуется для всех объектов | Снимок изменяемого состояния: `location`, `rightsNote`, `conditionNote`, опционально `damageHistoryHash`, `damageHistoryUrl`. |
| `physical` | `objectType = physical` или `mixed` | Структурированные физические факты: `category`, `medium`, `materials`, `dimensions`, `weight`, `marks`, `seal`. |
| `digital` | `objectType = digital` или `mixed` | Структурированные цифровые факты: `subtype`, `format`, `fileHash`, `fileSize`, опционально `c2pa`. |
| `image` | рекомендуется | Основное preview-изображение: hash / URL. |
| `images` | опционально | Дополнительные preview-изображения. |
| `refinementTags` | опционально | Свободные уточняющие ярлыки; не заменяют контролируемую таксономию. |
| `additionalMetadata` | опционально | Стабильная метадата со строковыми ключами, не описанная отдельными полями. |

#### Семантика mixed-объекта

Если `objectType = mixed`, канонический JSON **ДОЛЖЕН** содержать **оба** блока: `physical` и `digital`. Верификатор должен понимать такой паспорт как один объект реестра с двумя поверхностями доверия:

1. физический слой, привязанный к seal / NFC / numbered marks;
2. цифровой слой, привязанный к `fileHash` и цифровым дескрипторам.

`mixed` — это **не** запасной ярлык на случай сомнений, а явное утверждение, что обе стороны объекта являются first-class.

#### Mutable vs immutable (нормативно)

Линия v0.5 намеренно разделяет неизменяемый hash-bound документ и выбранное изменяемое on-chain состояние:

- **Неизменяемо и входит в `dataHash`:**
  `title`, `description`, `creationDate`, `authorship`, `domain`, `objectType`, `contentClass`, `refinementTags`, `aiStatus`, `verificationMethod`, `edition`, `image`, `images`, `physical`, `digital`, `additionalMetadata`, `year`, `month`, `registeredAt`, `registration`.
- **Изменяемые on-chain поля текущего состояния:**
  `status`, `currentState.location`, `currentState.rightsNote`, `currentState.conditionNote`, `currentState.damageHistoryHash`, `currentState.damageHistoryUrl`.
- **Правило авторитетности после mint:**
  если hash-bound JSON snapshot и on-chain mutable state расходятся, верификатор **ДОЛЖЕН** считать авторитетными именно **on-chain current-state fields** для текущего статуса / локации / прав / состояния.
- **Append-only history:**
  `ProofRecord` остаётся отдельным append-only on-chain слоем. Подробные provenance / ownership / damage histories SHOULD вестись как append-only off-chain документы, а в `currentState` хранится текущий pointer или summary.

### Таксономия класса контента (нормативно для v0.5)

Чтобы не привязывать протокол к быстро устаревающим ярлыкам форматов файлов, реализации ДОЛЖНЫ добавлять верхнеуровневый `contentClass` в `passport.json` со значением из списка:

- `static` — фиксированный статичный вывод
- `time_based` — фиксированная последовательность во времени
- `spatial` — 3D-структура / геометрия
- `textual` — семантическое символьное содержание
- `composite` — структурированный multi-file bundle
- `executable` — исполняемая логика, производящая результат

### Календарные `year` / `month` в `passport.json` (нормативно, референс v0.4+)

Верхнеуровневые `year` и `month` **должны** совпадать с **UTC** значениями, переданными в транзакцию mint и записанными on-chain — они входят в хэшируемый документ и связывают префикс Passport ID `ODP-YYYY-MM-…` с **месяцем mint**, а не с исторической датой создания объекта или файла. Если в UI собирается отдельный «год объекта» (например поле `f_year`), реализации **должны** выводить `**objectYear`** (целое), когда он отличается от года mint, чтобы провенанс мог, например, отразить работу XIX века, зарегистрированную в 2026 году.

### Момент регистрации (строки времени только в UTC) (нормативно)


| Поле                        | Обязательное | Тип                | Описание                                                                                                                                                                                                     |
| --------------------------- | ------------ | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `registeredAt`              | yes          | `number` (integer) | **Unix-время в секундах** (момент в UTC) на момент регистрации — тот же момент, что и on-chain `timestamp` intent.                                                                                           |
| `registration`              | yes          | `object`           | Тот же момент, что и `registeredAt`, в privacy-safe представлении только через UTC.                                                                                                                          |
| `registration.utcIso8601`   | yes          | `string`           | Тот же момент, что и `registeredAt`, в **UTC** с суффиксом `**Z`** и точностью до **секунды** (например `2026-03-22T18:45:30Z`). Соответствует тому, как интерпретируется время в цепочке/блоках (offset 0). |
| `registration.localIso8601` | yes          | `string`           | ISO 8601, нормализованный в UTC, с числовым offset `**+00:00`**, точность до **секунды** (например `2026-03-22T18:45:30+00:00`).                                                                             |
| `registration.ianaTimeZone` | yes          | `string`           | Всегда `**UTC`** в референсном privacy-режиме (локальная IANA-зона устройства не записывается).                                                                                                              |


Реализации **ДОЛЖНЫ** использовать **один и тот же** момент в UTC для `registeredAt`, `registration.utcIso8601` и `registration.localIso8601`.
Если локальное время устройства показывается пользователю, перед записью в `passport.json` его **ДОЛЖНЫ** нормализовать в **UTC (GMT+0)**.

Реализации **НЕ ДОЛЖНЫ** записывать **IANA-часовой пояс устройства** (например `Europe/Berlin`), **НЕ ДОЛЖНЫ** выводить в `registration.localIso8601` смещение, **отличное от `+00:00`**, и **НЕ ДОЛЖНЫ** строить `registration.*` от **локальных календарных часов** устройства. Имя поля `localIso8601` — **историческое**: значение по-прежнему кодирует **тот же момент в UTC** только со смещением `+00:00` (см. референс `chain/tools/mint.py` и веб-минт).

### Legacy note on old subtype/category fields

`physical.category` и `digital.subtype` МОГУТ сохраняться как описательные подполя, но это **вторичные дескрипторы**. Первичная классификация v0.5 ДОЛЖНА исходить из `domain`, `objectType`, `status`, `contentClass` и опциональных `refinementTags`.


### Принцип цифрового авторства

**Регистрируйте перед публикацией.**

Создатель, который первым зарегистрировал хэш файла, является автором записи.
После регистрации публично следует публиковать только производные версии (сжатые, водяные знаки, уменьшенное разрешение). Оригинальный файл должен оставаться у создателя как криптографическое доказательство авторства.

```
DO:     Регистрируйте → затем публикуйте сжатые/с водяными знаками версии
DON'T:  Не публикуйте оригинальный файл до регистрации его хэша
```

Если кто-то ещё публикует тот же файл, timestamp в блокчейне доказывает, кто зарегистрировал его первым.

### Совместимость с C2PA

ODP совместим с C2PA (Coalition for Content Provenance and Authenticity) на уровне хэша файла.

**Уровень 1 — совместимость по хэшу (autopol):**
Если файл уже содержит встроенный C2PA-манифест (созданный Photoshop,
Lightroom, камерой Leica или любым инструментом, совместимым с C2PA), то
SHA-256 этого файла включает неразделимо и контент, и манифест.
Дополнительные шаги не требуются.

**Уровень 2 — хэш манифеста (опционально):**
Если создатель хочет, чтобы C2PA-манифест был явно проверяем, он может сохранить его хэш отдельно в `digital.c2pa.manifestHash`.
Верификаторы, поддерживающие C2PA, могут использовать это, чтобы показать полную цепочку provenance C2PA рядом с результатом проверки ODP.

Рекомендуемая структура:

```json
"digital": {
  "subtype": "image",
  "fileHash": "sha256:...",
  "c2pa": {
    "manifestHash": "sha256:...",
    "activeManifest": "опциональная метка"
  }
}
```

Наличие C2PA нужно определять через C2PA parser/validator (найден active manifest или manifest store), а не по самодельным сигнатурам байтов.
Если C2PA-метаданные не найдены, `digital.c2pa` лучше не добавлять.

**Уровень 3 — ODP ID профиля как assertion в C2PA (в будущем):**
C2PA позволяет добавлять кастомные assertion внутри манифеста. В будущем расширение этой спецификации может определить стандартную assertion `odp:creatorId`, чтобы ODP ID профиля можно было встраивать в C2PA-манифесты.

### Правила сериализации

Все строковые значения в `passport.json` **ОБЯЗАНЫ** быть в Unicode NFC normalization до хэширования. Это гарантирует одинаковый `dataHash` во всех реализациях независимо от платформы (Python, JavaScript, mobile).

```
# Python
import unicodedata
value = unicodedata.normalize("NFC", value)

// JavaScript
value = value.normalize("NFC")
```

Любая реализация, которая вычисляет `dataHash`, **ОБЯЗАНА** нормализовать все строковые поля в NFC перед сериализацией. Если этого не сделать, легитимные паспорта будут выглядеть как **TAMPERED** в других реализациях.

### Правила

- Требуются поля: `version`, `passportId`, `objectType`, а также `creator.creatorId`
- Для физических объектов: требуется хотя бы одно из `seal.nfc` или `seal.numbered`
- Для цифровых объектов: требуется `digital.fileHash`
- `passportId` в JSON должно **точно** совпадать с on-chain записью (legacy `humanId` допустим для старых экспортов)
- `creator.wallet` должно совпадать с зарегистрированным кошельком в Creator Registry
- Кодировка: UTF-8
- Файл должен быть минимизирован перед хэшированием

## 10. Хэширование

### `dataHash`

```
dataHash = SHA-256( minified passport.json bytes )
```

1. Нормализуйте все строковые значения в Unicode NFC
2. Соберите `passport.json` со всеми полями
3. Отсортируйте все ключи по алфавиту на каждом уровне вложенности
4. Минимизируйте: нет пробелов вне значений строк
5. Кодируйте как UTF-8 байты
6. Посчитайте SHA-256 → сохраните как `bytes32`

### `sealHash`

```
sealHash = SHA-256( minified seal object bytes )
```

Объект `seal` извлекается, минимизируется отдельно и хэшируется.
Это позволяет быстро проверять seal без повторного хэширования всего паспорта.

### `fileHash` (цифровые объекты)

```
fileHash = SHA-256( raw file bytes )
```

Возьмите оригинальный файл. Не перекомпрессируйте, не меняйте размер и не редактируйте.
Посчитайте SHA-256 от raw-байтов. Сохраняйте как hex-строку с префиксом `sha256:`:

```
"sha256:abc123def456..."   ← correct format in passport.json
```

Этот формат используется последовательно в `passport.json`, Python CLI и web UI.
Поле `fileHash` в on-chain хранится как “сырой” `bytes32` (без префикса).

### `imageHash`

```
imageHash = SHA-256( raw image file bytes )
```

Перед хэшированием ни в коем случае не модифицируйте файл.

### `ndppCommitmentHash` (опциональный NDPP / public offline payload)

```
ndppCommitmentHash = SHA-256( raw bytes NDPP payload )
```

`**ndppCommitmentHash`** якорит опциональный **публичный offline payload** без превращения основного реестра в хранилище большого JSON. Типичные примеры:

- байты, переносимые NFC / QR как NDPP-style public payload,
- компактный публичный snapshot для offline- или low-bandwidth-проверки,
- long-DPP-style public disclosure файл, публикуемый отдельно от канонического `**.odpass`**.

ODP **НЕ ДОЛЖЕН** моделироваться так, будто каждый паспорт обязан быть объектом NFC Forum DPP / NDPP. NFC и NDPP — это только **опциональный carrier layer**. Паспорт может выпускаться и проверяться через QR, прямую публикацию `**.odpass`**, печатный сертификат, ручной ввод Passport ID или другой совместимый транспорт вообще без NFC-метки.

Аналогично, DPP / sustainability disclosure **не равно** authenticity. Нормативное ядро ODP — это on-chain registry, Passport ID, канонический `**passport.json`** / `**.odpass`** и правила hash verification из этой спецификации. NDPP-совместимый payload — это лишь слой удобной public disclosure / offline delivery, но не новая основа модели подлинности.

В этой линии реестр **не** задаёт один обязательный NDPP media type. Payload **МОЖЕТ** быть JSON, CBOR, NDEF-payload byte string, ZIP или другой детерминированной последовательностью байтов, о которой договорились issuer и verifier stack. Верификаторы **обязаны хэшировать точные raw-байты**, полученные из файла / carrier / URL, и сравнивать их с `**ndppCommitmentHash`**.

Если issuer использует NFC / QR **carrier**, который оборачивает эти байты (например URL-first NDEF message со второй ODP payload record), `**ndppCommitmentHash`** всё равно якорит только **raw-байты NDPP / offline payload**. Он **не** хэширует внешнее carrier-оформление, весь NDEF message целиком или байты URL record.

`**ndppCommitmentUri`** — только подсказка, где можно получить эти байты. Он **не** заменяет `**dataUrl`**, а NDPP **не** заменяет верификацию канонического `**passport.json`** / `**.odpass`**, привязанного через `**dataHash`**.

ODP **не требует** sustainability-полей вроде состава материалов, ремонтопригодности, recycling instructions, end-of-life disclosure или carbon-footprint reporting. Реализации **МОГУТ** публиковать такие данные внутри отдельного NDPP / public-disclosure payload, когда это уместно, но эти поля не входят в нормативное ядро ODP, если другой профиль явно не требует иного.

Для NFC Forum-compatible NDEF carriers реализации **ДОЛЖНЫ** размещать стандартную URL / URI запись **первой** ради широкой совместимости со смартфонами. Дополнительно они **МОГУТ** добавлять отдельную ODP-specific запись с компактными verification metadata или иным детерминированным public payload, чьи raw-байты заякорены через `**ndppCommitmentHash`**.

#### Опциональный профиль: ODP-in-NDPP

Эта спецификация определяет **опциональный**, **ненормативный для ядра** профиль совместимости под названием **ODP-in-NDPP** для issuers, которым нужен smartphone-friendly NFC / QR carrier без изменения trust model ODP.

Замысел профиля:

- сохранить канонический ODP-поток подлинности (`**Passport ID`**, on-chain record, `**dataHash`**, канонический `**.odpass`** / `**passport.json`**),
- оставить NDPP только **дополнительным** public-disclosure / offline-слоем,
- сохранить совместимость с типичным поведением телефонов, открывая сначала обычную веб-ссылку.

Рекомендуемый NFC NDEF layout для этого профиля:

1. **Record 1 (обязателен для профиля):** стандартная URL / URI запись, открывающая страницу ODP **Verify** или другой verifier entry URL для этого паспорта.
2. **Record 2 (необязателен, но типичен для профиля):** вторичная ODP / NDPP payload record с детерминированными байтами offline-public payload.

Правило хэширования для этого профиля:

- `ndppCommitmentHash = SHA-256(raw bytes secondary payload)`
- **не** `SHA-256(full NDEF message)`
- **не** `SHA-256(URL record + payload record)`

`**ndppCommitmentUri`** **МОЖЕТ** указывать на размещённую копию этих же raw payload bytes (например публичный CBOR / NDPP payload download). Это только подсказка для обнаружения; она **не** превращает NDPP в канонический артефакт паспорта и **не** заменяет ни Verify URL, ни `**dataUrl`**.

Поведение верификатора для этого профиля:

- если телефон умеет только открыть первый URL record, это лишь **шаг входа через carrier**;
- если verifier stack умеет читать и вторичную payload record, он **МОЖЕТ** захэшировать её raw payload и сравнить с `**ndppCommitmentHash`**;
- если вторичная record не разбирается, каноническая ODP-проверка всё равно возможна; отсутствие NDPP-parsing само по себе **не** инвалидирует паспорт.

## 11. Алгоритм верификации

### Уровень 1 — Подлинность объекта (всегда доступно)

```
Ввод: passportId (из QR, NFC или ручного ввода)

1. Запросить read surface контракта:
   - `getPassportHeader(passportId)`
   - `getPassportClassification(passportId)`
   - `getPassportMedia(passportId)`
   - `getPassportPhysical(passportId)`
   - `getPassportState(passportId)`
   → собрать поля, нужные для верификации (`dataHash`, `objectType`, `sealType`, `sealHash`,
     `nfcPublicKey`, `fileHash`, `dataUrl`, `creator`, `creatorId`, `timestamp`, текущее состояние)

2. Если запись не найдена → INVALID

3. Запрос к реестру создателей: getCreator(creatorId)
   → добавить к результату имя и кошелёк создателя

4. Записи proof: getProofsForPassport(passportId)
   → получить данные по каждому proof

5. Загрузить с `dataUrl`: тело HTTP **200** **ДОЛЖНО** быть файлом **`.odpass`** (ZIP §15); извлечь `passport.json` (сигнатура `PK\x03\x04`; путь **ДОЛЖЕН** заканчиваться на **`.odpass`**). Сырой JSON по `dataUrl` **не** допускается (§9).

6. Если загрузка не удалась → UNVERIFIABLE
   (on-chain запись всё равно доказывает, что объект был зарегистрирован)

7. Минифицировать JSON → вычислить SHA-256

8. Совпадение → AUTHENTIC
   Нет совпадения → TAMPERED
```

### Авторство и правовой статус (справочно)

On-chain поля `**creator**`, `**creatorId**` и хэши содержимого показывают, **кто зарегистрировал** паспорт в **каком деплойменте** и **какие байты** были зафиксированы. Они **не** заменяют национальное **авторское право**, **моральные права** или **право собственности** на физический объект. Для пользователя по-прежнему важны **репутация выпускающей стороны** (§3), публичная идентичность и перекрёстные проверки с **DPP**, **C2PA**, институциональными каталогами и т.д., когда это уместно.

### Уровень 1B — доказательство контроля кошелька creator (off-chain, EIP-191)

**Назначение:** доказать контроль над **кошельком creator** (`passport.creator`) **без** блокчейн-транзакции (верификатор не платит gas).

Это **не** юридическое доказательство авторства произведения — это лишь подтверждение, что подписант контролирует ключ, привязанный к этому паспорту on-chain.

**Каноничное сообщение (v1)** — строка UTF-8, подписываемая Ethereum **EIP-191** (`personal_sign` / `eth_sign` со стандартным префиксом сообщения):

```
Object Digital Passport — creator wallet proof (EIP-191) v1

passportId: <Passport ID>
chainId: <decimal chain ID>
contract: <registry contract address, EIP-55 checksum recommended>
nonce: <random unique string, e.g. 0x-prefixed hex>
```

**Шаги верификации:**

1. `recoveredAddress = ecrecover(EIP191(message), signature)` (как в `ethers.verifyMessage` или аналоге).
2. `getPassportHeader(passportId)` у реестра этой сети → прочитать `creator`.
3. **Совпадение**, если `recoveredAddress == creator` (сравнение адресов без учёта регистра).

Верификатор должен подтвердить, что `chainId` и `contract` в сообщении совпадают с проверяемым деплойментом. Реализации могут отклонять сообщения, у которых строка `passportId` не соответствует паспорту, который проверяется.

**Референсный веб-UI:** страница `verify.html` в этом репозитории **не** предоставляет инструмент уровня 1B. Интеграторы и кошельки могут по-прежнему реализовать уровень 1B по этому разделу для совместимых off-chain доказательств; каноничный формат сообщения и шаги верификации выше остаются нормативными.

### Уровень 1C — хэш внешнего документа (PDF, файл контракта)

**Назначение:** связать on-chain **SHA-256** оффчейн-файла (например PDF-контракт) с **кошельком Creator**, чтобы контрагенты могли проверить те же байты без доверия только email-вложениям.

**Эталон v0.5 (нормативно в этой спецификации):** в основном контракте `**ObjectDigitalPassport`** **нет** `attestExternalDocument` / `**getExternalDocumentAttestation`** (удалено ради **EIP-170**). Уровень 1C реализуется только спутником `**ODPWalletDocumentAnchor`**: деплой после основного реестра, в конструктор передаётся адрес реестра. Регистрация проверяется через `**getCreatorByWallet`** основного контракта; доступны `**attestExternalDocument`**, `**getExternalDocumentAttestation`**, событие `**ExternalDocumentAttested**` с индексированным `documentHash` (плюс индексированные `creatorId` и адрес `**attestor**`). Не более одной аттестации на `(wallet, documentHash)` в одном контракте-якоре. В репозитории спутник деплоится из `**chain/deploy/scripts/deploy.js**`; подключение к уже задеплоенному реестру — `**chain/deploy/scripts/deploy-doc-anchor-only.js`** (см. `**chain/deploy/README.md`**). Эталонный деплой Polygon хранит оба адреса в `**deployments/polygon.json`**.

Старые линии протокола, где эти функции были в монолитном основном реестре, **вне области** этого документа — здесь описан только расклад **v0.5** (основной реестр + `**ODPWalletDocumentAnchor`**).

Для **второго якоря документа, привязанного к паспорту**, на основном реестре используйте `**auxCommitmentHash` / `auxCommitmentUri`** (mint или `**updatePassportAuxCommitment`**).

**On-chain (`ODPWalletDocumentAnchor`, эталон v0.5):**

- `attestExternalDocument(bytes32 documentHash, string documentUri)` — вызывающий должен быть зарегистрирован в **основном** реестре; `documentHash` — SHA-256 от raw-байтов файла (как для `fileHash`); `documentUri` опциональный HTTPS URL (макс. 512 символов); **не более одной** аттестации на `(wallet, documentHash)` в этом контракте-якоре.
- `getExternalDocumentAttestation(address wallet, bytes32 documentHash)` — возвращает `attested`, `creatorId`, timestamp и `documentUri`.

**Верификация:** SHA-256 локального файла; запрос к `**ODPWalletDocumentAnchor`**; **совпадение** — кошелёк записал хэш в `timestamp`. Это **не** замена квалифицированным e-подписям — это **публичный якорь**.

**Референсный веб-UI:** `verify.html` включает уровень 1C при поддержке стека (**generation ≥ 2** в `odp-contract.js`). Запись и discovery идут через `**NET.docAnchor`** (задеплоенный `**ODPWalletDocumentAnchor`**); без него панель Anchor a file скрыта. Проверка хэша использует настроенный якорь и `**ExternalDocumentAttested`** / `**getExternalDocumentAttestation`**.

- **Закрепить (submit):** зарегистрированный кошелёк вызывает `attestExternalDocument` на `**ODPWalletDocumentAnchor`**; UI допускает опциональный HTTPS URL (макс. 512 символов).
- **Проверить (verify):** загрузка файла, локальный SHA-256, поиск аттестаций по `**ExternalDocumentAttested`** (`documentHash` в topic), подтверждение через `**getExternalDocumentAttestation`** на якоре; **глобальный** поиск без ввода profile ID.

### Уровень 1D — NDPP / public offline payload (опциональный carrier layer)

**Назначение:** заякорить компактный **публичный** payload для offline- или low-bandwidth-раскрытия без замены канонического `**passport.json`** / `**.odpass`**.

Этот уровень **опционален**. Паспорт остаётся валидным и без NFC, и без NDPP, и без какого-либо специального carrier payload сверх канонической связки registry + `**.odpass`**.

**On-chain (`ObjectDigitalPassport`, эталон v0.5):**

- `**ndppCommitmentHash`** / `**ndppCommitmentUri`** в записи паспорта.
- `**updatePassportNdppCommitment(passportId, newHash, newUri)`** — только `**creator`** или `**governance`**; то же правило пустоты/хэша, что и у aux commitment.

**Верификация:**

1. Получить NDPP payload bytes из ожидаемого источника (например байты, считанные через NFC, файл по QR, или raw body, загруженный по `**ndppCommitmentUri`**).
2. Вычислить `**SHA-256(raw bytes)`**.
3. Сравнить с on-chain `**ndppCommitmentHash`**.
4. **Совпадение**    → публичный offline payload сейчас заякорен для этого паспорта.
5. **Нет совпадения** → mismatch NDPP payload.

**Интерпретация для верификатора:** NDPP — это **дополнительный слой публичной информации**, а не основной integrity anchor паспорта. Совпавший NDPP payload можно показывать как заякоренные public disclosure data; mismatch означает, что именно NDPP-слой не прошёл проверку, но сам по себе не отменяет результат канонической проверки `**dataHash`** / `**.odpass`**. И наоборот: совпавший `**dataHash`** не валидирует отдельный NDPP payload автоматически, пока не совпадёт и его собственный хэш.

Если carrier использует NFC Forum-compatible NDEF, верификаторы и issuers должны воспринимать сам NFC-носитель только как удобный транспорт. Стандартная URL / URI запись может быть phone-friendly точкой входа, а любая дополнительная ODP-specific verification record остаётся вторичной и опциональной.

В опциональном профиле **ODP-in-NDPP** нужно явно различать URL-first carrier opening, chip-authentication и offline-payload validation:

1. открытие первой URL / URI record лишь запускает verifier entry point;
2. проверка вторичного payload доказывает только то, что public offline bytes совпадают с `**ndppCommitmentHash`**;
3. проверка физического chip по-прежнему требует chip-side proof против on-chain `**nfcPublicKey`**, если ожидается NFC seal verification; для текущего NTAG 424 deployment это честно означает документированный mirror-profile path, а не автоматически native challenge-response.

### Уровень 2A — проверка NFC seal (physical, sealType 1 или 3)

```
1. Открыть защищённую EV2-authenticated сессию с чипом, если
   deployment документирует такой verifier path
2. Считать документированный protected mirror file с чипа
3. Сравнить возвращённые live bytes с `nfcPublicKey` из блокчейна
4. Match    → SEAL_NFC_AUTHENTIC в рамках documentированного mirror profile
   No match → SEAL_NFC_INVALID / mismatch профиля / mismatch подготовки

If chip model is `NTAG424DNA_TAGTAMPER`:
5. Read tamper status
   INTACT   → SEAL_NFC_INTACT
   TAMPERED → SEAL_NFC_TAMPERED
```

`Read_Sig` / originality evidence и сам факт EV2-session establishment полезны как supporting signals, но сами по себе не равны passport-specific `nfcPublicKey` match. Этот уровень также **не** заявляет завершённый native arbitrary challenge/response для текущего NTAG 424 deployment, пока отдельный будущий профиль явно его не опишет.

### Уровень 2B — проверка нумерованной seal (physical, sealType 2 или 3)

```
1. Read seal.numbered.number from passport.json
2. User visually compares number on object to number in passport
3. Cannot be automated — requires human inspection
```

### Уровень 2C — проверка хэша файла (цифровые объекты)

```
1. User provides the original file
2. Compute SHA-256 of raw file bytes
3. Compare with fileHash from blockchain
4. Match    → FILE_AUTHENTIC (this is the registered original)
   No match → FILE_MISMATCH (different file — not the registered original)
```

### Уровень 3 — подлинность изображения (опционально)

```
1. If imageHash == 0x000...0 → NO_IMAGE_REGISTERED, stop
2. Compute SHA-256 of raw image bytes
3. Match    → IMAGE_AUTHENTIC
   No match → IMAGE_REPLACED
```

### Состояния верификации


| Состояние             | Значение                                               |
| --------------------- | ------------------------------------------------------ |
| `AUTHENTIC`           | Объект зарегистрирован, данные паспорта верифицированы |
| `INVALID`             | `passportId` не найден в блокчейне                     |
| `UNVERIFIABLE`        | Запись существует, но `dataUrl` недоступен             |
| `TAMPERED`            | Несовпадение хэша — `passport.json` был изменён        |
| `SEAL_NFC_AUTHENTIC`  | Проверена подпись NFC-чипа                             |
| `SEAL_NFC_INVALID`    | Подпись NFC-чипа не прошла проверку                    |
| `SEAL_NFC_INTACT`     | TagTamper: seal никогда не снимался                    |
| `SEAL_NFC_TAMPERED`   | TagTamper: seal снимался в какой-то момент             |
| `FILE_AUTHENTIC`      | Хэш файла совпадает — это зарегистрированный оригинал  |
| `FILE_MISMATCH`       | Хэш файла не совпадает                                 |
| `IMAGE_AUTHENTIC`     | Хэш изображения совпадает                              |
| `IMAGE_REPLACED`      | Несовпадение хэша изображения                          |
| `NO_IMAGE_REGISTERED` | В записи нет хэша изображения                          |

## 12. QR-код и URI-схемы протокола

### 12.1 Схема `odp` (нормативно)

Имя URI-схемы одно: `**odp**`. **Authority** (RFC 3986) — один незакодированный токен, либо:

- **Passport ID** по §2, напр. `odp://ODP-2026-03-004829301`, либо
- **Profile ID** по §3, напр. `odp://P-482-930-174-005`.

Клиент **обязан** отличать паспорт от профиля по грамматике authority: Passport ID начинается с `**ODP-`**; Profile ID — с `**C-`**, `**B-**`, `**P-**`, `**M-**`. В этой редакции спеки path и query отсутствуют.

### 12.2 Кодирование QR (нормативный минимум)

Примеры:

```
odp://ODP-2026-03-004829301
odp://P-482-930-174-005
```

- Коррекция ошибок: **Q** (минимум 25%)
- Кодировка: UTF-8
- Fallback HTTPS (задаётся реализацией), напр.: `https://verify.example.com/?id=…`

Иерархические path и query без будущего нормативного определения — **зарезервированы / экспериментальны**; реализации **не должны** на них опираться в интеропе.

### 12.3 Контекст реестра (нормативно)

URI `**odp://`** **не** указывает **chain ID** и **адрес реестра**. Любой клиент **обязан** получить **контекст реестра** (`chainId`, адрес основного контракта, ABI, при необходимости спутники) из конфигурации, доверенного deeplink или доверенного резолвера (§19). См. также §7.

## 13. Требования к SDK

### Почти-ERC стандарт чтения (эталонный контракт v0.4)

Раздел задаёт практическую поверхность чтения/интеграции для референсного `**ObjectDigitalPassport`** (**v0.4**; байт **4** при минте).

Уровень 1 (основное чтение)

- `exists(passportId) -> bool` (не делает revert)
- `getPassportHeader(passportId) -> PassportHeaderView`
- `getPassportClassification(passportId) -> PassportClassificationView`
- `getPassportMedia(passportId) -> PassportMediaView`
- `getPassportPhysical(passportId) -> PassportPhysicalView`
- `getPassportState(passportId) -> PassportStateView`
- `getCreator(creatorId) -> CreatorRecord`
- `governance() -> address`

Опционально — **counterfeit / authenticity concern:** `getCounterfeitConcern(passportId) -> (active, proverCreatorId, reasonHash, ts)` на `**ODPCounterfeitConcern`** (спутник); не на `**ODPWalletDocumentAnchor`**. Запись: `**raiseCounterfeitConcern(passportId, reasonHash)`**, `**clearCounterfeitConcern(passportId)**` (**P** / **M**).

Опционально — **спутник proof (`ODPPassportProofRegistry`):**

- `submitProof(passportId, noteHash, noteUrl, year, month) -> proofId`
- `getProofsForPassport(passportId) -> string[]` (ID доказательств; верификаторы SHOULD пагинировать **на клиенте**, если список может быть большим)
- `getProof(proofId) -> ProofRecord`

Опционально — **спутник relations (`ODPRegistryRelations`):**

- `getCreatorPublishingDelegation(creatorWallet) -> (agent, expiresAt)`
- `getPAffiliationAudit(childPId) -> (activeParent, joinedAt, detachedAt, lastDetachedFromParent)`
- `delegateCreatorPublishing(agent, expiresAt)`
- `revokeCreatorPublishing()`
- `requestMintAgentRole(principalCreatorId)` / `confirmMintAgentRole(agent)` / `revokeMintAgentRole()`

Опционально — **router extension mint (`ODPExtensionMintRouter`):**

- `setMintExtension(mintClass, extension)`
- `mintDigitalViaExtension(mintClass, payload, dataUrlIsFolderBase, mintOnBehalfOfCreatorId)`
- `mintPhysicalViaExtension(mintClass, payload, dataUrlIsFolderBase, mintOnBehalfOfCreatorId)`

Опциональные списки Уровня 1

- `getPassportsByCreatorPaged(creatorWallet, offset, limit) -> string[]` — bounded slice на deployable main registry
- legacy / convenience `getPassportsByCreator(creatorWallet) -> string[]` может существовать в старых деплоях, но deployable split-line интеграции SHOULD от него не зависеть

**Составное чтение (вместо удалённого `resolvePassport`):** `getPassport*View` с main registry + `getCreator(passport.creatorId)` + опциональный счётчик proof через спутник + `CONTRACT_VERSION` (публичная константа).

Инварианты (гарантии)

- Хэши неизменяемы после mint: `dataHash`, `**imageHash`, `imageHash2`, `imageHash3`**, `fileHash`, `sealHash`.
- `updatePassportUrls()` может менять **только** primary `dataUrl` и `**imageUrl`** (не `imageUrl2`/`imageUrl3`) и требует `confirmedDataHash == on-chain dataHash`; вызывать могут `**creator` или `owner`**, либо **активный агент публикации** (`getCreatorPublishingDelegation(passport.creator)`).
- `**submitProof` reverts**, если паспорт **отозван**.

Аффилиация (P → P, один уровень)

- `getPAffiliatedChildren(parentPId) -> string[]` возвращает весь список. Верификаторы/фронтенды MUST считать результат потенциально большим и применять **клиентскую** пагинацию или лимиты, либо `**getPAffiliatedChildrenPaged(parentPId, offset, limit)`** на эталонном основном реестре (**v0.4**).
- Hard caps: у одного parent `P` максимум **100** активных child `P`, у одного child `P` максимум **100** ожидающих предложений parent.

Закрепление документов

- `**getExternalDocumentAttestation(wallet, documentHash)`** на `**ODPWalletDocumentAnchor`** (эталон **v0.5** — задайте `**NET.docAnchor`**) возвращает метаданные для одной аттестации `(wallet, hash)`, если запись есть.

## 15. Бандл `**.odpass`** (offline-контейнер)

**Нормативный** переносимый файл — `**.odpass`**: ZIP-контейнер для распространения и резервного копирования ODP-паспорта.

Он позволяет офлайн-верификаторам пересчитать хэши и сверить их с on-chain записями.
On-chain поля остаются криптографическим источником истины.

### 15.1 Формат

Контейнер — **ZIP-файл с именем `.odpass`** (имена внутри — UTF-8).

Ожидаемые записи в ZIP:

- Обязательные:
  - `passport.json` — канонические байты ODP `passport.json` (UTF-8).
  - `manifest.json` — метаданные бандла для UX (не якорь доверия).
- Опциональные (текущий референсный layout бандла; поле `**bundleVersion**` в `manifest.json` задаёт вариант layout):
  - Все байтовые файлы с on-chain хэшами — в `**originals/<role>__<filename>**` (`<role>` — короткий токен: `digital`, `image`, `image2`, `image3`, чтобы не совпадали имена).
  - `**manifest.originals**` — объект: ключи `fileHash`, `imageHash`, `imageHash2`, `imageHash3`, значения — **точные пути в ZIP** к файлам; отсутствующий ключ = этого сайдка нет в архиве.

**Нормативное правило:** сайдкары **ДОЛЖНЫ** использовать layout `**originals/`** (см. выше). Отдельные папки верхнего уровня (`original/*`, `image/*`, `image2/*`, `image3/*`) **НЕ ДОЛЖНЫ** быть единственным способом размещения сайдкаров в соответствующем бандле.

#### 15.1.1 Эталонная форма `manifest.json`

Референс в репозитории (`web/passport.html`, `chain/tools/mint.py`) пишет `manifest.json` в UTF-8 как минимум с:

- `format`: `"odpass-bundle"` (legacy может быть `"odp-bundle"`)
- `bundleVersion`: строка layout’а, который пишет референсный экспорт (старые значения layout могут по-прежнему читаться)
- `passportId` (или legacy `humanId`), `createdAtUtc` (UTC ISO-8601), `mode` (напр. `"full"`)
- `onChain`: `dataHash`, `imageHash`, `imageHash2`, `imageHash3`, `fileHash` (`0x` + 64 hex или нули), `txHash`, `chainId`, `contract`
- `originals`: явные пути под `originals/` (см. выше)
- `files`: `{ path, role, mime }`; для sidecar допускаются `sizeBytes`, `sha256`

Реализации МОГУТ добавлять ключи. Верификаторы НЕ ДОЛЖНЫ считать `manifest.json` якорем доверия; пути в `originals` — только подсказка, какой entry хэшировать; критерий — on-chain `bytes32`.

### 15.2 Правила верификации

Офлайн-верификатор бандла `**.odpass`** ДОЛЖЕН:

1. Извлечь `passport.json`.
2. Пересчитать `localDataHash` (канонический JSON ODP; для chain-hash нормализовать Passport ID как `passportId: null` — в legacy JSON допустим тот же шаг с `humanId: null`).
3. Сравнить `localDataHash` с on-chain `dataHash` для заявленного Passport ID (`passportId`).

При ненулевом `fileHash` — найти байты по пути из `manifest.originals.fileHash` (должен быть под `originals/`, см. правила ниже), пересчитать SHA-256, сравнить с `fileHash`.

При ненулевых `imageHash` / `imageHash2` / `imageHash3` — то же через `manifest.originals.imageHash` / `imageHash2` / `imageHash3` (только пути под `originals/`). Запасной поиск в устаревших каталогах `original/*` или `image*/*` **не допускается**. Пути с `..` или без префикса `originals/` отклонять; итог задают on-chain хэши.

### 15.3 Модель доверия

- Бандл — недоверенный ввод, без выполнения кода.
- Бандл не заменяет on-chain истину; якорь — `dataHash` и при необходимости `fileHash` / хэши изображений.

## 17. Кошелёк и ключи

ODP не задаёт способ хранения ключей; нужен только Ethereum-адрес для подписи транзакций.

**Рекомендация:** отдельный кошелёк **только для ODP** — не для крупных балансов, DeFi и трейдинга. Второй keypair протокол не требует: подпись — ключи кошелька. **Выбор кошелька:** ориентируйтесь на **официальную документацию** вашего инструмента (пример: [справочный центр MetaMask](https://support.metamask.io/)); **конкретный бренд нормативно не задан**. **Эталонные страницы** этого репозитория на момент подготовки текста **проверялись в основном с MetaMask**; другие кошельки с EIP-1193 ожидаются рабочими, но не гарантируются во всех пограничных случаях. Опциональные **DID**-документы (§18) МОГУТ объявлять доп. ключи для VC; это вне базового register/mint.

### Эталонный веб-UI: расширение и WalletConnect (информативно)

**Эталонные статические страницы** (`**passport.html`**, `**creator.html`**) поддерживают:

- **Инжектированный EIP-1193** (типичное браузерное расширение).
- **WalletConnect v2** через пакет [Reown](https://docs.reown.com/) `**@walletconnect/ethereum-provider`** — отдельный пункт в UI подключения. Сессия WalletConnect по-прежнему даёт интерфейс **EIP-1193** (`eth_requestAccounts`, `eth_chainId`, подпись транзакций) для тех же путей register/mint.

WalletConnect использует **relay** и приложение кошелька (QR или deep link); **доступность, конфиденциальность и доверие** к этому каналу — между пользователем, вендором кошелька и инфраструктурой WalletConnect — **здесь не нормируются**. Семантика on-chain не меняется: авторитетны `**msg.sender`**, кошелёк создателя и `**chainId`**.

**Сборка репозитория** (Project ID в Reown Cloud, ленивая загрузка бандла, восстановление сессии после перезагрузки): `**web/odp-wc-config.js`**, `**web/odp-wallet-wc-loader.js`**, `**[../../../docs/V0.4.md](../../../../docs/V0.4.md)**`.

### Принцип генерации ключа

Приватный ключ создаётся на устройстве пользователя. Его нельзя передавать в инфраструктуру ODP или третьим лицам; протокол не принимает и не хранит ключи.

### Способы хранения

**A — Софт-кошелёк (seed)**
Seed — мастер-бэкап. При потере — кошелёк не восстановить. Записать seed на бумаге, проверить порядок слов, хранить офлайн, не хранить в облаке/фото/мессенджерах, иметь вторую копию в другом месте.

**B — Аппаратный кошелёк**
Ключ в устройстве; подпись с подтверждением на устройстве. Seed всё равно нужен как бэкап — те же правила.

**C — Аппарат без seed (чип)**
Ключ не покидает чип. Нужен запасной девайс до регистрации; потеря всех устройств = безвозвратная потеря доступа к профилю и паспортам.

### Потеря доступа

- Профиль в блокчейне навсегда; удалить ODP не может
- Выпущенные паспорта остаются проверяемыми
- Новые mint и обновления под этим профилем невозможны без кошелька

### Расширения (вне спецификации)

Шифрованное хранение, мобильный KMS, multisig, social recovery и т.п. — на усмотрение реализаций.

## 18. Интероп, позиционирование, DID (информативно)

ODP задуман как **криптографический слой доверия** рядом с **DPP**, **GS1**, **IIIF**, **C2PA** и др., а не их замена.

### 18.1 Опциональные поля `passport.json` (черновик)

Реализации МОГУТ добавлять (всё оффчейн, если включено — входит в `dataHash`):

- `**sustainability`**, `**compliance`**
- `**identifiers.gtin**` — привязка к GS1 Digital Link в tooling
- `**iiif.manifest**`
- Метаданные объекта: габариты, вес, глубина, `**creationDate**`, `**listingPrice**`, `**internalTag**`
- `**images**` — до трёх логических изображений (primary ↔ `imageHash`, доп. ↔ `imageHash2`/`imageHash3`)

Верификатор не трактует цену как юридическую оферту.

### 18.1.1 Паттерн связки с GS1 Digital Link

GS1 Digital Link **необязателен** и остаётся **внешним** по отношению к core-протоколу ODP. Практический паттерн: использовать URI GS1 Digital Link как стандартизованный **URL/QR-вход**, а ODP оставлять слоем **криптографической верификации**.

Минимальный паттерн интеграции:

1. GS1 Digital Link идентифицирует **GTIN** и, если есть, **серийный номер**.
2. Страница-резолвер или сервис сопоставляет эту GS1-пару с паспортом ODP и открывает нужную страницу паспорта или верификации с требуемым контекстом реестра.
3. Далее верификатор проверяет ODP **Passport ID**, канонические байты `**.odpass`** / `**passport.json`** относительно on-chain `**dataHash`**, а опциональные `**ndpp`** / public offline payload использует только как дополнительный слой транспортировки или раскрытия данных.

`**identifiers.gtin`** в `**passport.json`** — естественное off-chain место для выравнивания записи ODP с идентификаторами GS1. Сам по себе GS1 Digital Link **не** доказывает подлинность и **не** заменяет реестр ODP, Passport ID или проверку хэшей.

### 18.2 DID (`did:odp`)

- `did:odp:passport:<Passport ID>`
- `did:odp:profile:<Profile ID>`

Минимальный DID document (JSON): `id`, `verificationMethod` на Ethereum-адрес создателя (или отдельные ключи для VC), `alsoKnownAs` к `passport.json` / деплою. Глобальный on-chain resolver не требуется. Для **уровня URI** (`odp://`), контекста реестра и опциональных HTTP-профилей см. **§19**.

#### 18.2.1 Опциональный поток «регистрации» DID (информативно)

Создание или публикация DID document **необязательны** и **не** требуют отдельной on-chain транзакции. Эмитент (или tooling) **может** экспортировать JSON DID document **в любой момент** после минта, если известны Passport ID и контекст реестра: из `getPassport` читаются `creator` / `creatorId` и при необходимости `dataUrl`, далее — §18.2. Кошелёк, не подключавшийся в момент минта, может собрать тот же документ из публичных данных сети. Реализации **могут** добавлять ненормативные подсказки (например `chainId`, адрес контракта) рядом с DID для каталогов или резолверов.

### 18.3 Verifiable Credentials

Институциональные **proof** (`submitProof`) можно отображать как VC-claims; для протокольного верификатора авторитетна on-chain `ProofRecord`.

## 19. URI-схема и опциональные резолверы (информативно)

Раздел согласован с §12 по грамматике `**odp://`** и описывает **опциональные** off-chain помощники. Авторитетное состояние всегда берётся из настроенного **контекста реестра** (**chain ID**, **адрес** контракта, **ABI**).

### 19.1 Нормативная URI-схема (минимум для QR и deeplink)


| Схема | Authority (токен в стиле host)                        | Правило                                                          |
| ----- | ----------------------------------------------------- | ---------------------------------------------------------------- |
| `odp` | Либо `<Passport ID>` по §2, либо `<Profile ID>` по §3 | Различать по префиксу (`ODP-` vs `C-`/`B-`/`P-`/`M-`); см. §12.1 |


Дополнительные path/query **в этой редакции спеки не нормативны**; реализации **не должны** от них зависеть в интеропе — считать **зарезервированными / экспериментальными**, пока будущая версия их не определит.

### 19.2 Контекст реестра (нормативно)

Чтобы связать `odp://…` с on-chain состоянием, нужен **контекст реестра**: как минимум `**chainId`**, адрес основного реестра и **ABI** (плюс опционально спутники). Клиент **обязан** получать его из: конфигурации пользователя/интегратора; доверенного транспорта (HTTPS-страница с метаданными); ответа **доверенного** off-chain резолвера (§19.4). URI **без** метаданных реестра **неоднозначен** — возможны несовместимые реестры на разных адресах.

### 19.3 Связь с `did:odp` (§18.2)

Схема `**odp://`** удобна для QR и вставки. Строки `**did:odp:passport:`** / `**did:odp:profile:`** — форма **W3C DID** для документов и VC. Один и тот же Passport ID / Profile ID может фигурировать в обоих слоях; DID-документ по-прежнему **опционален** (§18.2).

### 19.4 Опциональный HTTP-«резолвер» (ненормативно)

HTTP-резолвер **не** заменяет JSON-RPC к сети. Это опциональный **кэш, агрегатор или шлюз**, который **может** собирать read-only данные ради задержки или UX.

**Иллюстративные** формы REST (не требование для соответствия протоколу):

- `GET …/passport/{passportId}` → JSON с данными из `getPassport`, `getCreator`, списками proof и явными полями `chainId`, `registryAddress`, пробой `CONTRACT_VERSION`, опционально спутники.
- `GET …/creator/{creatorId}` → запись создателя и подсказки по списку паспортов (через `getPassportsByCreator`* или индексатор).

`**/.well-known/odp-resolver` (опциональное discovery):** развёртывание **может** отдавать небольшой JSON, например:

```json
{
  "odpResolverVersion": 1,
  "baseUrl": "https://resolver.example.com",
  "supportedChains": [137, 80002],
  "description": "Пример — имена полей не нормативны."
}
```

Клиенты MUST трактовать неизвестные ключи как непрозрачные. Это развивает пометку про implementation-specific `.well-known` в §18.2.

### 19.5 Контент и идентичность (информативно)

- **Контент:** загрузка **§15 `.odpass`** (или извлечённого из него `passport.json`) с `dataUrl` или через прокси резолвера **всё равно** **ДОЛЖНА** сверяться с on-chain `**dataHash`** — резолвер может отдать неверные байты.
- **Идентичность:** маркетинговые каталоги Profile ID → сайт — **вне протокола**.

### 19.6 Обратный поиск по хэшу файла (ненормативно)

Референсный реестр **не** задаёт канонический on-chain индекс **SHA-256(файл) → Passport ID**. Эндпоинты вроде `GET …/resolve/hash/{hex}` возможны только через **off-chain индексатор** и **не** входят в базовое соответствие протоколу.

### 19.7 Сводка модели доверия


| Подход                                                              | Роль                                                              |
| ------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Прямой JSON-RPC к **известному** реестру + локальные проверки хэшей | Максимальное соответствие истине протокола                        |
| HTTP-резолвер                                                       | Удобство; для критичной верификации — **подтверждать** по цепочке |
| Голая ссылка `odp://` **без** метаданных реестра                    | **Недостаточно**, чтобы знать, какой реестр опрашивать            |
