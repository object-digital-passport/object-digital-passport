# ODP — draft notes for v0.2

*Author: Andrei Chernikov*

**Status:** informal design notes. **Not** a specification. v0.1 remains defined in [`SPEC.md`](SPEC.md).

This file collects directions where a **major** revision (v0.2) could differ from v0.1 — including ideas that would require contract changes, new hash rules, or verifier behaviour.

---

## 1. Why consider a “v0.2” at all

v0.1 optimises for: one contract, one `dataHash` over canonical `passport.json`, `dataUrl` stored on-chain only.

Pain points that keep coming up:

- Creators think in **folders** (`https://example.com/art/passports/`), not in a single opaque URL decided before mint.
- Human ID is **random at mint**; the mental model “upload `ODP-….json` under my folder” is easier than “pick a URL without the ID, then update”.
- **Embedding `dataUrl` inside `passport.json`** would help self-description and mirrors, but **today it would change `dataHash`** and break verification unless the rules change.

A v0.2 could explicitly redesign **where the URL lives** and **what enters the hash**.

---

## 2. Folder-first hosting (canonical URL pattern)

**Idea** (partially explored in the v0.1 web UI): the creator registers only a **base URL** (HTTPS folder). The protocol defines a **deterministic file URL**:

```text
{baseUrl_without_trailing_slash}/{HumanID}.json
```

Example: `https://art.com/passport/` + `ODP-2026-03-80531787` →  
`https://art.com/passport/ODP-2026-03-80531787.json`

**v0.1 reality:** the chain stores `dataUrl` as an arbitrary string; the UI can call `updatePassportUrls` after mint. The **file** still must not add extra fields that were not in the hashed `passport.json` at mint time.

**v0.2 options:**

| Approach | Pros | Cons |
|----------|------|------|
| **A — Keep hash as today; URL only on-chain** | No migration; matches v0.1 | JSON file never lists its own canonical URL |
| **B — `dataUrl` in JSON, excluded from hash** | Self-describing file; mirrors | Verifier must implement explicit “exclude list” for hashing |
| **C — `dataUrl` in JSON, included in hash** | Single source of truth | Must mint **after** the URL is known, or use a **template** + second hash step |

**Radical option (true “folder protocol”):** mint only commits `dataHash` + `baseUrl` (or `baseUrlHash`), and the **verifier derives** `dataUrl` from `HumanID`. That implies **contract ABI** and **indexer** changes.

---

## 3. Hashing boundary

v0.1: `dataHash = SHA-256( minified passport.json bytes )` with `humanId` null in the hashed payload for mint.

v0.2 could define:

- **Explicit manifest** (e.g. `odp-manifest.json`) separate from display metadata.
- **Typed fields:** which keys are “binding” vs “display only”.
- **URI template** field on-chain: `https://example.com/passport/{humanId}.json` with a **normative** expansion rule.

Any change here is **not** backward-compatible without version flags on-chain.

---

## 4. Versioning model

v0.1: `contractVersion` is `uint8` (e.g. `0`); spec speaks of “v0.1” in docs.

v0.2 could:

- Split **spec semver** (`0.2.0`) from **contract generation** (`0`, `1`, …), or
- Introduce a **single** `version` string in JSON + migration rules.

---

## 5. Open questions (not decisions)

- Should **verify** accept “folder + Human ID” without fetching the chain for `dataUrl` (only for `dataHash` lookup)? That couples UX to a URL pattern.
- **Internationalised domains** (IDN) and path encoding: normative rules for `baseUrl`.
- **IPFS / Arweave:** same folder pattern, or a different URI scheme in v0.2.
