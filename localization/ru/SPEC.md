# Object Digital Passport
### Specification v0.2 — DRAFT

*Author: Andrei Chernikov*

> An open standard for physical and digital object authentication
> via blockchain and human-readable identifiers.

## ВАЖНО: 0.X — это не совместимое долгосрочное хранилище

Этот репозиторий описывает **протокольную линию v0.X**. На этапе **0.X** on-chain контракты (и то, как работает регистрация creator'ов) могут меняться между деплойментами.

Поскольку **Creator IDs и on-chain записи относятся к конкретно развернутому контракту**, данные, которые вы записали в одном деплойменте 0.X, останутся доступными в нём, но не стоит ожидать, что вы сможете зарегистрировать того же creator и добавить те же записи в более поздний деплоймент контракта 0.X.

Даже при том же адресе кошелька новый деплоймент может сгенерировать **другой** `creatorId`.

Если вам нужно **один кошелёк и один постоянный `creatorId`** для канонического долгосрочного хранения, пожалуйста дождитесь стабильного деплоймента **v1**.

## 1. Обзор

Object Digital Passport (ODP) — это открытый стандарт, который позволяет любому регистрировать
физический или цифровой объект в публичном блокчейне и проверять его подлинность — без
каких-либо централизованных платформ, подписок или зависимости от третьих сторон.

**Ключевые принципы:**

- **Открытость** — любой может реализовать протокол на любом языке или платформе
- **Децентрализация** — нет одной компании, которая контролирует реестр
- **Дружелюбие к офлайну** — подлинность можно проверить без интернета, используя только хэши
- **Бесплатно читать** — верификация никогда не стоит ничего
- **Минимум on-chain** — нет изображений и больших данных, хранящихся в блокчейне

### 1.1 Терминология

В этой спецификации используются следующие термины в строгом смысле:

| Термин | Определение |
|:--|:--|
| **Mint**, **minting** | Отправка Ethereum-транзакции, которая **создаёт** новую on-chain запись паспорта через `mintPhysical` или `mintDigital` (или эквивалент) в контракте. Контракт назначает **Human ID**, записывает **хэши**, опциональные **URL** и metadata seal. В **v0.2** применяется **только network gas** (без отдельного **MINT_FEE**). Minting **не** загружает `passport.json` в блокчейн; creator **может** размещать этот файл по адресу `dataUrl` (см. §8–§9). Если `dataUrl` пуст, публичная веб-верификация не сможет получить JSON — проверка по `dataHash` доступна только обладателю канонического **passport.json**. |
| **Register (Creator ID)** | Отправка `registerCreator` (или эквивалента), чтобы кошелёк получил постоянный **Creator ID** до любых mint или proof. **v0.2**: только gas (без **REGISTER_FEE**). |
| **Passport** | On-chain **Passport** запись плюс (если применимо) байты **`passport.json`**, которые соответствуют `dataHash` (по `dataUrl`, если он задан). |
| **`passport.json`** | Нормативный оффчейн JSON-документ (§9). |
| **`dataUrl`** | Опциональный HTTPS URL, где обслуживается `passport.json` (§8–§9). Может быть пустым on-chain в **v0.2**; если пусто, то верификаторы, которые рассчитывают на HTTP, **не смогут** получить файл, пока пользователь не предоставит его сам. |
| **Gas** | Стоимость нативного токена (POL на Polygon PoS), которую платят сети за выполнение транзакций. В **v0.2** нет дополнительного сжигаемого протокольного fee на register/mint (в отличие от **v0.1** деплойментов). |
| **Verification** | Процесс read-only (§11), который получает on-chain данные и (если `dataUrl` задан) `passport.json`, после чего проверяет согласованность с `dataHash` и другими полями. Если `dataUrl` пуст, всё равно применяется файловая верификация, когда у верификатора есть `passport.json`. |

## 2. Human ID

Каждый зарегистрированный объект получает глобально уникальный человекочитаемый идентификатор.

### Формат

```
ODP-YYYY-MM-NNNNNNN
```

| Раздел | Описание | Пример |
|------|-----------|---------|
| `ODP` | Фиксированный префикс протокола | `ODP` |
| `YYYY` | Год регистрации (любой год > 0) | `2026` |
| `MM` | Месяц регистрации (01–12) | `03` |
| `NNNNNNN` | Случайное число из 7 цифр, уникальное в рамках года и месяца | `4829301` |

### Примеры

```
ODP-2026-03-4829301   ← объект зарегистрирован в марте 2026
ODP-2026-03-0193847   ← другой объект в тот же месяц
ODP-2026-04-7392018   ← объект зарегистрирован в апреле 2026
ODP-2027-01-2048391   ← объект зарегистрирован в январе 2027
```

Число не указывает ни порядок, ни общее количество зарегистрированных объектов.
Это сделано намеренно.

### Алгоритм генерации

```
entropy = keccak256(block.timestamp + msg.sender + nonce)
number  = uint32(entropy) % 10_000_000        // 0000000–9999999
if number already exists for this year+month:
    nonce++, retry
humanId = "ODP-" + year + "-" + month + "-" + zero_pad(number, 7)
```

10 миллионов возможных значений в месяц. Уникальность гарантируется контрактом
посредством проверки коллизий через autopol retry.

### Правила

- Число генерируется контрактом — creator не выбирает его
- Число уникально в пределах комбинации год+месяц
- Два одновременных mint'инга упорядочиваются блокчейном — дубликаты невозможны
- Human ID неизменяем после mint'инга
- Human ID — канонический идентификатор для всех поисков/запросов

## 3. Creator ID

Каждый creator, бренд или институция должны зарегистрироваться в сети on-chain
до mint'инга паспорта или отправки proof. Регистрация назначает постоянный globally уникальный Creator ID.

**Creator ID обязателен.** Контракт отклоняет любые транзакции mint или proof
от незарегистрированного кошелька.

### Формат

```
T-NNN-NNN-NNN
```

| Раздел | Описание | Пример |
|------|-----------|---------|
| `T` | Префикс типа (см. ниже) | `C` |
| `NNN-NNN-NNN` | 9-значное случайное число, разделённое на группы по 3 для читаемости | `482-930-174` |

### Префиксы типов

| Префикс | Значение | Кто использует |
|--------|----------|----------------|
| `C` | Creator | Индивидуальный художник, фотограф, мастер |
| `B` | Brand | Компания, студия, лейбл |
| `P` | Proof Institution | Эксперт, аукционный дом, орган сертификации — аттестации (`submitProof`) для любого паспорта |
| `M` | Museum | Зарегистрованный музей или коллекция — **неограниченные** passport mints для институциональных holdings (например, работы ушедших художников); может также `submitProof` как `P` |

### Лимиты минта по месяцам (референсный контракт v0.2)

Референсный деплой `ObjectDigitalPassport` ограничивает **новые mint'ы паспортов** для каждого кошелька в пределах **календарного месяца** (anti-spam; только gas — без протокольной комиссии). Лимиты зависят от зарегистрированного **типа Creator**:

| Тип | Оценочный лимит |
|------|-----------------|
| `C` | 1,000 минтов / месяц |
| `B` | 100,000 минтов / месяц |
| `P` | Без лимита (`getRemainingMints` возвращает `2^32−1` в референсной реализации) |
| `M` | Без лимита (как и `P`) |

**Музеи и крупные инвентарные массивы** оцифровывающие holdings коллекции должны регистрироваться как **`M`** (музей/коллекция) или **`B`** (более широкая организация), а не **`C`**. Префикс **`P`** предназначен для институций, чья **основная** роль в протоколе связана со сквозными **proof**-аттестациями; **`M`** означает custodian / выпуск от лица коллекции. Очень высокая пропускная способность всё равно может использовать **несколько кошельков**, если так допускает политика.

**Префиксы типов определяются исключительно этой спецификацией.**
Ни один участник, компания или реализация не могут вводить собственные префиксы.
Новые префиксы добавляются только через официальное обновление этой спецификации,
после чего смарт-контракт пере-развертывается с обновлённым allowlist.
Контракт это обеспечивает: любая попытка регистрации с нераспознанным
префиксом отклоняется на уровне контракта.

### Примеры

```
C-482-930-174   ← индивидуальный creator
B-029-384-751   ← бренд или компания
P-001-293-847   ← институция для proof
M-204-839-112   ← музей или коллекция
```

### Алгоритм генерации

```
entropy  = keccak256(block.timestamp + msg.sender + nonce)
number   = uint32(entropy) % 1_000_000_000     // 000000000–999999999
if number already exists: nonce++, retry
group_1  = number / 1_000_000                  // first 3 digits
group_2  = (number / 1_000) % 1_000            // middle 3 digits
group_3  = number % 1_000                      // last 3 digits
creatorId = type + "-" + pad3(group_1) + "-" + pad3(group_2) + "-" + pad3(group_3)
```

1 миллиард возможных значений. Уникальность гарантируется контрактом.

### Полная публичная идентичность

У каждого участника есть два формата идентичности:

```
Короткий:  C-482-930-174
Полный:   C-482-930-174 / Artist Name / 0x742d...f2c8
```

Полная идентичность включает:
- Короткий Creator ID
- Имя или название организации
- Полный адрес кошелька (0x... — 42 символа)

Адрес кошелька — криптографическая опора идентичности.
Имя — человекочитаемая метка. Адрес кошелька — доказательство, подделать которое нельзя.

### Требование публичной идентичности

**Все участники — creators (C), brands (B) и institutions (P) —
должны публично публиковать оба формата идентичности.**

Это фундаментальное требование протокола, а не просто рекомендация.
Система работает только тогда, когда любой может проверить, кто стоит за каждым объектом
и за каждой аттестацией.

Участники должны публиковать свою идентичность:

- На своем официальном сайте — заметно, не прячьте в меню
- Во всех публичных профилях соцсетей и биографиях
- На физических объектах, упаковке и сертификатах, которые они выдают
- Во всех официальных коммуникациях и пресс-релизах

**Оба формата должны легко находиться:**

```
Художник на artist.com:
  Короткий:  C-482-930-174
  Полный:   C-482-930-174 / Artist Name / 0x742d...f2c8

Музей на museum.com:
  Короткий:  P-029-384-751
  Полный:   P-029-384-751 / Institution Name / 0xB3F9...
```

**Важно:** названия институций не хранятся в протоколе и не показываются
верификаторами. На on-chain находится только Creator ID. Верификаторы показывают только ID —
пользователи должны найти его на официальном сайте институции, чтобы подтвердить идентичность.
Это предотвращает регистрацию под любым названием институции и получение незаслуженного доверия.

Так протокол работает без централизованного реестра: существующая
публичная репутация участника становится доказательством его идентичности. Любой может
регистрироваться — но только легитимные участники будут иметь свой ID, доступный
на доверенном публичном сайте.

### На упаковке и физических объектах

```
ODP-2026-03-4829301
C-482-930-174
```

Короткий формат намеренно сделан компактным — удобно печатать, зачитывать вслух или распечатывать.

## 4. Proof Institution (институция доказательств)

Любой музей, галерея, аукционный дом, эксперт или орган сертификации может
зарегистрироваться как Proof Institution, используя префикс типа `P`. Регистрация открыта для
любого участника по всему миру — одобрение не требуется.

### Что делает Proof Institution

Зарегистрированная Proof Institution может прикрепить к любому
зарегистрированному паспорту on-chain **Proof record**. Это неизменяемое публичное утверждение:
*"Мы рассмотрели этот объект и подтверждаем его подлинность."*

Proof records не изменяют исходный паспорт. Они накапливаются вместе с ним.
Полная история proof навсегда видна в сети.

**Протокол не проверяет, действительно ли Creator ID принадлежит заявленной институции.**
Основанием для доверия служит лишь публичная публикация Creator ID на реальном веб-сайте —
вместе с реальной репутацией институции.
Верификаторы показывают только Creator ID, а не самоназванное имя.

```
ODP-2026-03-4829301  (original passport, 2026)
  └── Proof from P-029-384-751  2031
  └── Proof from P-482-930-174  2038
  └── Proof from P-001-293-847  2044
  └── Proof from P-774-002-391  2051
```

### Формат Proof ID

```
PRF-YYYY-MM-NNNNNNN
```

Генерируется тем же алгоритмом, что и Human ID:

```
entropy = keccak256(block.timestamp + msg.sender + humanId + nonce)
number  = uint32(entropy) % 10_000_000
if number already exists for this year+month: nonce++, retry
proofId = "PRF-" + year + "-" + month + "-" + zero_pad(number, 7)
```

Пример: `PRF-2031-03-7392018`

### Поля записи proof

| Поле | Тип | Обязательное | Описание |
|-------|------|-------------|----------|
| `proofId` | `string` | да | Автоматически генерируется: `PRF-2031-03-7392018` |
| `prover` | `string` | да | Creator ID институции (например, `P-029-384-751`) |
| `humanId` | `string` | да | Human ID аттестуемого объекта |
| `noteHash` | `bytes32` | нет | SHA-256 прикрепленного документа. `bytes32(0)`, если документа нет |
| `noteUrl` | `string` | нет | URL прикрепленного документа (макс. 512 символов) |
| `timestamp` | `uint256` | да | Устанавливается контрактом |

### Стоимость

Отправка записи proof стоит только gas (~$0.01 POL на Polygon).
Протокол комиссий не взимает.

### Требование публичной идентичности для институций

Публичное требование идентичности из раздела 3 полностью относится к Proof Institutions.
Proof от институции, чей ID нельзя найти на их официальном сайте,
не несёт верифицируемой ценности.

## 5. Verification Label
Метка верификации — физический носитель, который размещается на объекте.
Она содержит все данные, необходимые для проверки, и физически удерживает seal.

### Обязательные элементы

| Элемент | Описание | Пример |
|---------|-----------|--------|
| QR-код | Кодирует `odp://ODP-YYYY-MM-NNNNNNN`. Уровень коррекции ошибок Q (минимум 25%) | `odp://ODP-2026-03-4829301` |
| Human ID | Полный идентификатор объекта в человекочитаемом виде | `ODP-2026-03-4829301` |
| Creator ID | Короткий идентификатор создателя | `C-482-930-174` |
| Маркер протокола | Название протокола или его аббревиатура | `ODP` или `Object Digital Passport` |

### Опциональные элементы

Реализации могут добавить любое из следующего — протокол их не ограничивает:

- Название объекта
- Имя создателя
- Год создания
- Номер издания
- Логотип создателя или визуальный идентификатор
- NFC-чип (встроенный в метку или под ней)
- Номер seal (напечатан на метке или на отдельном элементе)

### Требование удержания seal

Метка должна физически покрывать или удерживать seal:

- Если используется NFC-крипточип (NTAG 424 DNA TagTamper) — его следует расположить
  под меткой или внутри метки. Чип TagTamper постоянно электронно фиксирует снятие.
  Физическое расположение под меткой добавляет дополнительный визуальный индикатор вскрытия,
  но криптографическое обнаружение вскрытия обеспечивается самим чипом, а не меткой.
- Если используется нумерованный seal — метка должна перекрывать seal так,
  чтобы снятие метки требовало снять seal.

### Что эта спецификация НЕ определяет для метки

- Размер, форма, цвет, материал
- Типографика и визуальный дизайн
- Размещение элементов
- Производитель

Это решения реализации. Спецификация определяет только то,
что должно присутствовать, а не то, как это должно выглядеть.

## 6. Физическая seal

Физическая seal связывает цифровой паспорт с конкретным физическим объектом.
**При минтачении паспорта типа `physical` требуется как минимум один способ seal.**

Без seal паспорт лишь доказывает, что запись существует в сети —
он не доказывает, что объект перед вами является зарегистрированным оригиналом.

Паспорта цифровых объектов (тип `digital`) не требуют физической seal.
Хэш файла служит криптографической привязкой.

### Метод A — NFC Crypto Seal (NTAG 424 DNA TagTamper)

Криптографический NFC-чип, встроенный в объект или прикреплённый к нему.
Рекомендуется для объектов высокой ценности, произведений искусства и коллекционных предметов.

**Требуемый чип:** только NXP NTAG 424 DNA TagTamper.
Стандартный NTAG 424 DNA (без TagTamper) и стандартные NFC-теги (NTAG213 и т.п.) не поддерживаются.
Только TagTamper навсегда фиксирует факт физического снятия seal.

**Как это работает:**

```
Регистрация:
  1. Считать public key чипа и UID через NFC
  2. Записать в passport.json под seal.nfc
  3. Паспорт хэшируется и регистрируется on-chain как обычно
  4. `nfcPublicKey` также сохраняется напрямую on-chain для быстрой
     криптографической проверки без загрузки passport.json

Верификация:
  1. Телефон отправляет чипу случайный challenge по NFC
  2. Чип подписывает challenge, используя свой внутренний private key
     (private key заперт в кремнии — никогда не покидает чип)
  3. Телефон проверяет подпись по `nfcPublicKey`, полученному из блокчейна
  4. Совпадение → оригинальный чип подтверждён
     Несовпадение → неверный или клонированный чип
```

**Вариант NTAG 424 DNA TagTamper:**

Добавляет петлю антенны для обнаружения вскрытия.
Физическое снятие навсегда регистрируется как событие вскрытия.

```
Пломба цела  → чип сообщает: INTACT
Пломба снята  → чип сообщает: TAMPERED (permanent, cannot be reset)
```

**Физическая установка:**
Чип должен быть встроен или герметизирован так, чтобы при снятии происходило
видимое разрушение. Метод установки описывается в `seal.nfc.notes`.

**Поля NFC seal в passport.json:**

| Поле | Обязательное | Описание |
|-------|---------------|-------------|
| `uid` | yes | 7-байтовый UID чипа, hex в нижнем регистре |
| `publicKey` | yes | открытый ключ ECC, hex строка |
| `model` | yes | `NTAG424DNA_TT` — принимается только TagTamper |
| `installedAt` | yes | дата установки в ISO 8601 (например `2026-03-15`) |
| `notes` | no | способ установки, место, материал герметизации |

### Метод B — нумерованная физическая seal

Физическая seal с уникальным напечатанным номером.
Примеры: голографическая наклейка, восковая печать, свинцовая пломба, label со следами вскрытия.

Создатель отвечает за использование seal, которую нельзя снять без видимых повреждений.
Этот метод даёт физическую “ссылку”, а не криптографическое доказательство.

**Поля нумерованной seal в passport.json:**

| Поле | Обязательное | Описание |
|-------|---------------|-------------|
| `number` | yes | Номер seal ровно как напечатан |
| `type` | yes | Тип seal (например `holographic sticker`, `wax seal`) |
| `color` | no | Цвет |
| `size` | no | Размеры (например `30x30mm`) |
| `notes` | no | Дополнительное описание |

### Правило требований к seal

| Условие | Верно? |
|-----------|--------|
| NFC криптосеal (NTAG 424 DNA TagTamper) | ✅ |
| Только нумерованная seal | ✅ |
| Обе seal | ✅ |
| Стандартный NFC-тег (NTAG213 и т.п.) | ❌ Не поддерживается |
| Нет seal (физический объект) | ❌ Контракт отклоняет |
| Нет seal (цифровой объект) | ✅ Хэш файла — привязка |

## 9. JSON паспорта (Passport JSON)

### Хостинг `dataUrl` (сторонние сайты)

`dataUrl` может указывать на любой публичный HTTPS-хост (object storage, CDN, статический сайт, Git forge и т.п.). Последний сегмент пути **ДОЛЖЕН** иметь вид `<humanId>.json`, используя **точную** строку Human ID из контракта (например `ODP-2026-03-4829301.json` — тот же регистр, что и в on-chain). Реализации, которые получают файл, **ОБЯЗАНЫ** выполнять:

1. **HTTPS** — URL использует TLS; сервер возвращает HTTP **200**, а тело ответа содержит **только** байты passport JSON (не HTML-страницу, не страницу логина и не UI просмотра репозитория).
2. **Raw-файл на Git-хостингах** — для GitHub, GitLab и похожих хостов используйте URL **raw** файла (например `raw.githubusercontent.com/.../passport.json`), а не HTML-страницу blob.
3. **CORS (веб-верификаторы)** — веб-верификаторы выполняют `fetch()` от своего origin; хост **ДОЛЖЕН** разрешать cross-origin **GET** для `dataUrl`, чтобы браузер мог прочитать тело (многие статические хосты и GitHub Raw это поддерживают; неверно настроенный приватный сервер может блокировать верификацию).
4. **Целостность** — после каноникализации содержимое **ДОЛЖНО** совпадать с `dataHash` в сети (см. §10). Любое изменение байтов (включая пробелы/отступы) меняет хэш.

#### Ответственность создателя за `passport.json` после mint (нормативно)

Протокол **не** хранит полный `passport.json` в on-chain — только `dataHash` и связанные поля (см. §8). Создатель **ОБЯЗАН** сохранять **канонический минимизированный** набор байтов `passport.json`. **v0.2** позволяет оставлять `dataUrl` пустым на момент mint; если он задан, создатель **должен** сделать эти байты доступными по `dataUrl` для публичной веб-верификации.

1. Если `dataUrl` **не пуст**, но нет HTTP **200** ответа, тело которого после каноникализации соответствует `dataHash`, то верификаторы **ОБЯЗАНЫ** считать веб-верификацию **проваленной** (например **UNVERIFIABLE** / несовпадение хэша по §11 — точные названия состояний зависят от реализации).
2. Если `dataUrl` **пуст**, то HTTP-загрузка примениться не может; проверить `dataHash` могут только стороны с **файлом `passport.json`** (UX зависит от реализации; предпочтительно предупреждать создателя в момент mint).
3. Создатель **может** позже обновить `dataUrl` через on-chain обновление URL (например `updatePassportUrls` в референсном контракте) **без** повторного mint’инга, если размещённый файл всё ещё соответствует `dataHash`.
4. **Референсные и совместимые UIs** **ДОЛЖНЫ** требовать **явного подтверждения пользователя** сразу перед отправкой mint-транзакции: что сохранение `passport.json` — ответственность создателя; что публичная проверка зависит от доступности этого файла по зарегистрированному URL при заданном `dataUrl`; и что пользователь должен скачать или скопировать файл до закрытия экрана успеха, если реализация предоставляет это действие.

### Роль issuer и дополнительная метадата (нормативно, v0.2)

| Поле | Обязательное | Тип | Описание |
|-------|---------------|------|----------|
| `issuerRole` | рекомендуется | `string` | Одно из: `individual`, `brand`, `proof_institution`, `museum`. Описывает **роль issuer в сети** для этого паспорта (например музей, каталогизирующий работу ушедшего художника → `museum`). **ДОЛЖНО** согласовываться с **префиксом `creatorId`** (`C`/`B`/`P`/`M`) по ситуации. |
| `additionalMetadata` | опционально | `object` | Произвольные **строковые ключи**, сопоставленные **строковым значениям** (Unicode NFC). Используйте для фактов, специфичных для институции или объекта, которые **не** описаны в других полях — например номер инвентаря, accession id, флаг постоянной коллекции, заметка по выставке. Ключи **ДОЛЖНЫ** быть стабильными идентификаторами (`snake_case` или `camelCase`). |

Эти поля входят в хэшируемую часть `passport.json`; изменение приводит к изменению `dataHash`.

### Момент регистрации и локальные часы (нормативно, v0.2)

| Поле | Обязательное | Тип | Описание |
|-------|---------------|------|----------|
| `registeredAt` | yes | `number` (integer) | **Unix-время в секундах** (момент в UTC) на момент регистрации — тот же момент, что и on-chain `timestamp` intent. |
| `registration` | yes | `object` | Тот же момент, что и `registeredAt`: явная строка **UTC** плюс **локальное** wall time + IANA zona. |
| `registration.utcIso8601` | yes | `string` | Тот же момент, что и `registeredAt`, в **UTC** с суффиксом **`Z`** и точностью до **секунды** (например `2026-03-22T18:45:30Z`). Соответствует тому, как интерпретируется время в цепочке/блоках (offset 0). |
| `registration.localIso8601` | yes | `string` | ISO 8601 **date-time с числовым offset**, точность до **секунды** (например `2026-03-22T21:45:30+03:00`). В референсном UI нет дробных долей меньше секунды. |
| `registration.ianaTimeZone` | yes | `string` | [Имя IANA часового пояса](https://www.iana.org/time-zones) для среды, где был собран `passport.json` (например `Europe/Moscow`, `America/New_York`). Используйте `UTC`, если неизвестно. |

Реализации **ДОЛЖНЫ** использовать **один и тот же** момент в UTC для `registeredAt`, `registration.utcIso8601` и момента, закодированного в `registration.localIso8601` (различается только представление).

### Принцип цифрового авторства

**Регистрируйте перед публикацией.**

Создатель, который первым зарегистрировал хэш файла, является автором записи.
После регистрации публично следует публиковать только производные версии (сжатые,
водяные знаки, уменьшенное разрешение). Оригинальный файл должен
оставаться у создателя как криптографическое доказательство авторства.

```
DO:     Регистрируйте → затем публикуйте сжатые/с водяными знаками версии
DON'T:  Не публикуйте оригинальный файл до регистрации его хэша
```

Если кто-то ещё публикует тот же файл, timestamp в блокчейне доказывает,
кто зарегистрировал его первым.

### Совместимость с C2PA

ODP совместим с C2PA (Coalition for Content Provenance and Authenticity)
на уровне хэша файла.

**Уровень 1 — совместимость по хэшу (autopol):**
Если файл уже содержит встроенный C2PA-манифест (созданный Photoshop,
Lightroom, камерой Leica или любым инструментом, совместимым с C2PA), то
SHA-256 этого файла включает неразделимо и контент, и манифест.
Дополнительные шаги не требуются.

**Уровень 2 — хэш манифеста (опционально):**
Если создатель хочет, чтобы C2PA-манифест был явно проверяем,
он может сохранить его хэш отдельно в `digital.c2pa.manifestHash`.
Верификаторы, поддерживающие C2PA, могут использовать это, чтобы показать
полную цепочку provenance C2PA рядом с результатом проверки ODP.

**Уровень 3 — ODP Creator ID как assertion в C2PA (в будущем):**
C2PA позволяет добавлять кастомные assertion внутри манифеста. В будущем
расширение этой спецификации может определить стандартную assertion `odp:creatorId`,
чтобы ODP Creator ID можно было встраивать в C2PA-манифесты.

### Правила сериализации

Все строковые значения в `passport.json` **ОБЯЗАНЫ** быть в Unicode NFC normalization
до хэширования. Это гарантирует одинаковый `dataHash` во всех реализациях
независимо от платформы (Python, JavaScript, mobile).

```
# Python
import unicodedata
value = unicodedata.normalize("NFC", value)

// JavaScript
value = value.normalize("NFC")
```

Любая реализация, которая вычисляет `dataHash`, **ОБЯЗАНА** нормализовать все строковые поля
в NFC перед сериализацией. Если этого не сделать, легитимные паспорта
будут выглядеть как **TAMPERED** в других реализациях.

### Правила

- Требуются поля: `version`, `humanId`, `objectType`, а также `creator.creatorId`
- Для физических объектов: требуется хотя бы одно из `seal.nfc` или `seal.numbered`
- Для цифровых объектов: требуется `digital.fileHash`
- `humanId` в JSON должно **точно** совпадать с on-chain записью
- `creator.wallet` должно совпадать с зарегистрированным кошельком в Creator Registry
- Кодировка: UTF-8
- Файл должен быть минимизирован перед хэшированием

---

## 10. Хэширование

### `dataHash`

```
dataHash = SHA-256( minified passport.json bytes )
```

1. Нормализуйте все строковые значения в Unicode NFC
2. Соберите `passport.json` со всеми полями
3. Отсортируйте все ключи по алфавиту на каждом уровне вложенности
4. Минимизируйте: нет пробелов вне значений строк
5. Кодируйте как UTF-8 байты
6. Посчитайте SHA-256 → сохраните как `bytes32`

### `sealHash`

```
sealHash = SHA-256( minified seal object bytes )
```

Объект `seal` извлекается, минимизируется отдельно и хэшируется.
Это позволяет быстро проверять seal без повторного хэширования всего паспорта.

### `fileHash` (цифровые объекты)

```
fileHash = SHA-256( raw file bytes )
```

Возьмите оригинальный файл. Не перекомпрессируйте, не меняйте размер и не редактируйте.
Посчитайте SHA-256 от raw-байтов. Сохраняйте как hex-строку с префиксом `sha256:`:

```
"sha256:abc123def456..."   ← correct format in passport.json
```

Этот формат используется последовательно в `passport.json`, Python CLI и web UI.
Поле `fileHash` в on-chain хранится как “сырой” `bytes32` (без префикса).

### `imageHash`

```
imageHash = SHA-256( raw image file bytes )
```

Перед хэшированием ни в коем случае не модифицируйте файл.

## 11. Алгоритм верификации

### Уровень 1 — Подлинность объекта (всегда доступно)

```
INPUT: humanId (from QR, NFC, or manual entry)

1. Query contract: getPassport(humanId)
   → { dataHash, objectType, sealType, sealHash,
       nfcPublicKey, fileHash, dataUrl, creator, creatorId, timestamp }

2. If not found → INVALID

3. Query Creator Registry: getCreator(creatorId)
   → attach creator name and wallet to result

4. Query Proof records: getProofsForPassport(humanId)
   → fetch institution data for each proof

5. Fetch passport.json from dataUrl

6. If fetch fails → UNVERIFIABLE
   (on-chain record still proves the object was registered)

7. Minify JSON → compute SHA-256

8. Match    → AUTHENTIC
   No match → TAMPERED
```

### Уровень 1B — доказательство контроля кошелька creator (off-chain, EIP-191)

**Назначение:** доказать контроль над **кошельком creator** (`passport.creator`) **без** блокчейн-транзакции (верификатор не платит gas).

Это **не** юридическое доказательство авторства произведения — это лишь подтверждение, что подписант контролирует ключ, привязанный к этому паспорту on-chain.

**Каноничное сообщение (v1)** — строка UTF-8, подписываемая Ethereum **EIP-191** (`personal_sign` / `eth_sign` со стандартным префиксом сообщения):

```
Object Digital Passport — creator wallet proof (EIP-191) v1

humanId: <Human ID>
chainId: <decimal chain ID>
contract: <registry contract address, EIP-55 checksum recommended>
nonce: <random unique string, e.g. 0x-prefixed hex>
```

**Шаги верификации:**

1. `recoveredAddress = ecrecover(EIP191(message), signature)` (as implemented by `ethers.verifyMessage` / equivalent).
2. `getPassport(humanId)` on the registry for that chain → read `creator`.
3. **Match** if `recoveredAddress == creator` (compare as addresses, case-insensitive).

Верификатор должен подтвердить, что `chainId` и `contract` в сообщении совпадают с проверяемым деплойментом. Реализации могут отклонять сообщения, у которых строка `humanId` не соответствует паспорту, который проверяется.

### Уровень 1C — хэш внешнего документа (PDF, файл контракта)

**Назначение:** связать on-chain **SHA-256** оффчейн-файла (например PDF-контракт) с **кошельком Creator**, чтобы контрагенты могли проверить те же байты без доверия только email-вложениям.

**On-chain (референсный контракт, generation ≥ 2):**

- `attestExternalDocument(bytes32 documentHash, string documentUri)` — вызывающий должен быть зарегистрирован; `documentHash` — это SHA-256 от raw-байтов файла (то же, что используется для кодирования `fileHash`); `documentUri` опциональный HTTPS URL (макс. 512 символов); **не более одной** аттестации на `(wallet, documentHash)`.
- `getExternalDocumentAttestation(address wallet, bytes32 documentHash)` — возвращает `attested`, `creatorId`, timestamp и `documentUri`.

**Верификация:** вычислите SHA-256 локального файла; запросите контракт; **совпадение** означает, что создатель записал этот хэш в `timestamp`. Это **не** заменяет квалифицированные e-подписи или национальное право — это **публичная, неизменяемая привязка**, связывающая кошелёк с хэшем файла.

### Уровень 2A — проверка NFC seal (physical, sealType 1 или 3)

```
1. Send random challenge to chip via NFC
2. Chip returns signed response
3. Verify signature against nfcPublicKey from blockchain
4. Match    → SEAL_NFC_AUTHENTIC
   No match → SEAL_NFC_INVALID

If chip is NTAG424DNA_TT:
5. Read tamper status
   INTACT   → SEAL_NFC_INTACT
   TAMPERED → SEAL_NFC_TAMPERED
```

### Уровень 2B — проверка нумерованной seal (physical, sealType 2 или 3)

```
1. Read seal.numbered.number from passport.json
2. User visually compares number on object to number in passport
3. Cannot be automated — requires human inspection
```

### Уровень 2C — проверка хэша файла (цифровые объекты)

```
1. User provides the original file
2. Compute SHA-256 of raw file bytes
3. Compare with fileHash from blockchain
4. Match    → FILE_AUTHENTIC (this is the registered original)
   No match → FILE_MISMATCH (different file — not the registered original)
```

### Уровень 3 — подлинность изображения (опционально)

```
1. If imageHash == 0x000...0 → NO_IMAGE_REGISTERED, stop
2. Compute SHA-256 of raw image bytes
3. Match    → IMAGE_AUTHENTIC
   No match → IMAGE_REPLACED
```

### Состояния верификации

| Состояние | Значение |
|-------|---------|
| `AUTHENTIC` | Объект зарегистрирован, данные паспорта верифицированы |
| `INVALID` | `humanId` не найден в блокчейне |
| `UNVERIFIABLE` | Запись существует, но `dataUrl` недоступен |
| `TAMPERED` | Несовпадение хэша — `passport.json` был изменён |
| `SEAL_NFC_AUTHENTIC` | Проверена подпись NFC-чипа |
| `SEAL_NFC_INVALID` | Подпись NFC-чипа не прошла проверку |
| `SEAL_NFC_INTACT` | TagTamper: seal никогда не снимался |
| `SEAL_NFC_TAMPERED` | TagTamper: seal снимался в какой-то момент |
| `FILE_AUTHENTIC` | Хэш файла совпадает — это зарегистрированный оригинал |
| `FILE_MISMATCH` | Хэш файла не совпадает |
| `IMAGE_AUTHENTIC` | Хэш изображения совпадает |
| `IMAGE_REPLACED` | Несовпадение хэша изображения |
| `NO_IMAGE_REGISTERED` | В записи нет хэша изображения |

## 14. Versioning

- This specification is **v0.2** (draft); `passport.json` uses `"version": "0.2"` for current examples
- Breaking changes increment the minor version: `0.2`, `0.3`, ...
- Stable release will be `1.0`
- All `passport.json` files include a `version` field for forward compatibility
- The contract is not upgradeable — a new protocol version deploys a new contract
- Type prefixes may only be added through an official specification update

## 15. What this protocol does NOT define

- Who hosts `passport.json` or digital files — the creator's responsibility
- What happens when `dataUrl` goes offline — the on-chain hash remains valid indefinitely
- UI or visual design of verifiers or labels
- Pricing or marketplace mechanics
- Transfer of ownership (may be defined in a future extension)
- Support for multiple blockchain networks (reserved for a future version)
- Human-readable names — Creator ID is a number, not a name
- Which specific seal product to use — any seal meeting the requirements is valid
- Full C2PA integration beyond hash compatibility (reserved for a future extension)

## 16. Wallet & Key Management

ODP does not define how users manage their cryptographic keys.
The protocol only requires a valid Ethereum-compatible wallet address
to sign transactions. How the key is generated, stored, and secured
is entirely the user's responsibility and choice.

### Key generation principle

The private key must be generated on the user's own device.
It must never be transmitted to ODP infrastructure, any third-party server,
or any other party. The protocol has no mechanism to receive or store keys.

### Storage approaches

Three broad categories exist. The protocol is compatible with all of them:

**Category A — Software wallet (seed phrase)**
The key is derived from a 12–24 word seed phrase stored by the user.
The seed phrase is the master backup. If lost, the wallet cannot be recovered.
Users choosing this approach must:
- Write the seed phrase on paper immediately upon creation
- Verify the phrase by confirming word order as prompted
- Store the paper copy offline in a secure physical location
- Never store the seed phrase digitally (no photos, no cloud, no messaging apps)
- Keep at least one physical backup copy in a separate location

**Category B — Hardware device (seed phrase + physical security)**
The key is generated and stored inside a dedicated physical device.
Transactions are signed on the device and require physical confirmation.
A seed phrase is still generated as a backup — the same rules apply.
The physical device adds a layer of protection: even if the computer
is compromised, transactions cannot be signed without the device.

**Category C — Seed-less hardware (key in chip)**
Some physical devices generate a key inside a secure chip with no seed phrase.
The key never leaves the device in any form.
Users choosing this approach must:
- Purchase at least one additional backup device before registering
- Losing all devices means permanent loss of access to the Creator ID and all passports
- There is no recovery path without a backup device

### What losing access means for ODP

If a creator loses their wallet:
- Their Creator ID remains in the blockchain forever — nothing in ODP can ever be deleted
- All passports they minted remain valid and verifiable by anyone
- They can no longer mint new passports under that Creator ID
- They can no longer update existing passports

Passports already minted are **not corrupted**. The blockchain record is permanent.
Only the ability to create new records under that identity is lost.

### Extensions (outside this specification)

The following are possible extensions that implementations may choose to build.
They are not part of the ODP protocol and are not standardized here:

- Encrypted key storage on a user-controlled server
- Key management integrated into a mobile application
- Multi-signature wallets (multiple keys required to sign)
- Social recovery schemes
- Any other approach compatible with Ethereum-signed transactions
