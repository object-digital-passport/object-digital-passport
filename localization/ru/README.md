## ВАЖНО: контракты 0.X не предназначены для долгосрочного хранения

В этом репозитории мы выкладываем деплойменты **0.X** как proof-of-concept. На этапе 0.X **он-чейн-контракты могут меняться** (в том числе то, как устроена регистрация creator'ов). Поскольку **Creator IDs назначаются конкретным развернутым контрактом**, предполагается следующее:

- Вы можете **регистрировать и минтачить (mint) только внутри именно этого деплоймента контракта**.
- Даже при **том же адресе кошелька** новый деплоймент может сгенерировать **другой** `creatorId`.
- После нового деплоймента 0.X вы **не сможете “добавить” старую информацию в новый контракт** (новый реестр = новая регистрация creator'а / новые записи). То, что вы записали, остается доступным в старом реестре on-chain, но оно **не переносится автоматически** в следующий деплоймент.
- Если вы хотите иметь **только один кошелек + один постоянный `creatorId`** как основное долгосрочное хранилище, **пожалуйста, дождитесь стабильной версии v1** и используйте её для ваших канонических записей.

## Термины (прочитайте в первую очередь)

Блокчейн-приложения часто переиспользуют слова из NFT и финансов — вот что они означают **в ODP**:

| Термин | Значение в ODP |
|:--|:--|
| **Mint / minting** | Отправка **транзакции**, которая **создаёт** новую on-chain запись. Для паспорта **mint** означает, что смарт-контракт **регистрирует** ваш объект: он назначает **Human ID** и хранит криптографические **хэши** (в v0.2: **только gas сети** — без отдельного протокольного fee). Вы всё равно **скачиваете** и можете **хостить** `passport.json` отдельно. |
| **Register (Creator ID)** | **Одноразовый** on-chain шаг: ваш кошелёк платит **gas** и получает постоянный **Creator ID** (`C-…`, `B-…` или `P-…`). Делать это нужно **до** того, как вы сможете минтачить паспорта. |
| **Passport** | **Вся** запись по одному объекту: on-chain строка плюс (если опубликован) файл **passport.json** по адресу `dataUrl`. |
| **`passport.json`** | Оффчейн JSON-документ с названием, seal, хэшами и т.д. На on-chain хранится только **хэш**; **вы** должны хранить файл. Если вы указываете `dataUrl`, публикуйте файл там, чтобы верификаторы могли его скачать. |
| **`dataUrl`** | Необязательная **HTTPS** ссылка, где размещён `passport.json`. Если поле пустое on-chain, публичная страница Verify **не сможет** скачать JSON — тогда детали и аутентичность сможет проверить только тот, у кого есть сам **файл**. |
| **Verify / verification** | **Read-only** проверка: загружаются данные из сети + (если доступно) `passport.json`, затем пересчитываются хэши — **без** кошелька и без протокольных комиссий. |
| **Gas** | **POL** платится в сеть Polygon за выполнение транзакций (величина зависит от загруженности). В v0.2 нет дополнительного сжигаемого протокольного fee на register/mint — только gas. |
| **Protocol fee** | Деплойменты v0.1 использовали фиксированное сжигание **0.001 POL** на некоторых действиях. В v0.2 этого нет — вы платите **только gas** (POL). |
| **Wallet** | Ethereum-совместимое приложение, которое держит ваши ключи и **подписывает** транзакции. На десктопе референсные HTML-страницы используют **injected** провайдеры (см. ниже “Кошельки (в браузере)”), а не только MetaMask. |

Нормативные определения и форматы: **[`SPEC.md`](SPEC.md)** (особенно §1.1 и дальше по тексту).

### Кошельки (в браузере)

Страницы **Creator** и **Passport** используют `window.ethereum` ([**EIP-1193**](https://eips.ethereum.org/EIPS/eip-1193)): любой браузерный extension, который инжектит этот провайдер, может подключаться и подписывать. Примеры: **MetaMask**, **Rabby**, **Coinbase Wallet**, **Brave Wallet**, **OKX Wallet** и другие EIP-1193–совместимые расширения. Хелпер в [`web/creator.html`](web/creator.html) / [`web/passport.html`](web/passport.html) (`injectedEthereum`) предпочитает MetaMask, если доступны `providers[]`; иначе используется первый инжектнутый провайдер.

**Не входит в рамки этого репозитория:** сценарии вроде **WalletConnect** (или аналоги), которые не инжектят `window.ethereum`, в статических страницах не подключены — для них нужна явная интеграция. На **mobile Safari** без расширения используйте “in-app browser” вашего кошелька или открывайте страницы по ссылке из приложения кошелька, чтобы появился тот же injected provider.

### Версионирование (сайт vs контракт)

| | |
|:--|:--|
| **Сайт / статический релиз** | **`0.X.Y`** (см. `ODP_SITE_VERSION` в [`web/odp-contract.js`](web/odp-contract.js)). Увеличивайте `Y`, когда меняете только документацию, HTML/CSS или инструменты **без** нового деплоймента контракта. |
| **Контракт / генерация протокола** | **`0.X`** в спецификациях и git-тегах — когда меняется байткод или правила on-chain (например, v0.1 → v0.2). Референсный контракт отдаёт **`SPEC_MAJOR`** / **`SPEC_MINOR`** (читаемая строка спецификации) и упакованный байт **`CONTRACT_VERSION`** для UI. |
| **On-chain `CONTRACT_VERSION`** | Это **не** маркетинговый semver. UI читает его, чтобы выбрать ABI: **≥2** = spec **v0.2** (gas-only, опциональный `dataUrl`, mint с folder-base, **внешний хэш документа**, префикс **`M` (museum)**, неограниченные **P/M** мints, **`submitProof`** из P или M). **`CONTRACT_VERSION == 0`** (исторические деплойменты v0.1 fee-era) **отклоняются**. См. [`web/odp-contract.js`](web/odp-contract.js). |
| **Упакованный байт** | **`SPEC_MAJOR`/`SPEC_MINOR`** каждая &lt; 16. Spec 0.2 → `SPEC_MINOR=2` → **`CONTRACT_VERSION = 2`**. |
| **Старый mainnet деплой** | Первый публичный Polygon-контракт использовал on-chain байт **0** (fee-era). Текущие HTML из этого репозитория **не поддерживают этот адрес** как `NET.contract`; используйте **v0.2+** деплой. Историческое обсуждение: **`SECURITY.md`**, **`SPEC.md`**. |

### Подпись стека и доверие (всегда включено в веб-интерфейсе)

Страницы в `web/` показывают **панель стека** (см. `odpFormatStackBlockHtml` в [`web/odp-contract.js`](web/odp-contract.js)), чтобы операторы не полагались на скрытые предположения:

| Тема | Что это значит |
|:--|:--|
| **Чтение старых данных** | **read ABI** продолжает декодировать предыдущие on-chain значения **`contractVersion`**. Верификатор сначала вызывает **основной** `NET.contract`; если паспорт или creator **не найден** там, он пробует **`NET.previousContracts`** (старые Polygon-деплойменты — каждый это свой реестр). |
| **Site SemVer — red** | **`0.x.y`** (`ODP_SITE_VERSION`) = **красный флаг**: proof-of-concept / не production-stable. |
| **Site SemVer — green** | **`1.0.0`** и выше: стабильная линия. UI становится **зелёным**, когда major этой страницы совпадает с `ODP_LATEST_STABLE_MAJOR` (поднимать константу нужно при выпуске нового стабильного major, например `2` после `1.x`). |
| **Site SemVer — yellow** | Если latest stable major это **N ≥ 2**, то majors **`1 … N−1`** — **yellow** (старые stable-линии: нужна проверка миграции). Major страницы, новее `ODP_LATEST_STABLE_MAJOR`, тоже **yellow**, пока не совпадёт константа. |

**Канонические live URL** (GitHub Pages проектный сайт): базовый URL — [https://object-digital-passport.github.io/object-digital-passport/](https://object-digital-passport.github.io/object-digital-passport/) — например [Creator ID](https://object-digital-passport.github.io/object-digital-passport/creator.html), [Passport](https://object-digital-passport.github.io/object-digital-passport/passport.html), [Verify](https://object-digital-passport.github.io/object-digital-passport/verify.html).

## Что это за система (и зачем она)

**Object Digital Passport (ODP)** — открытый стандарт регистрации **физического или цифрового объекта** в публичном блокчейне и последующего **доказывания** того, что данный объект соответствует регистрации — без проприетарной платформы, подписки или центрального gatekeeper.

Как части “склеиваются”:

- **Human ID** (`ODP-YYYY-MM-NNNNNNN`) — удобный, читаемый и уникальный идентификатор объекта; назначается контрактом, неизменяем.
- **Creator ID** (`C-482-930-174` и т.п.) — постоянная идентичность художника, бренда или института; нужна перед mint’ом.
- **On-chain record** — компактно: хэши, привязка к creator, URL, metadata seal. **Без** больших картинок и полного JSON на on-chain.
- **Passport JSON** — полный документ, который должен жить по **`dataUrl`**, когда вам нужна публичная веб-верификация (HTTPS); в сети хранится хэш, чтобы любое изменение файла было обнаружено. **`dataUrl` можно не указывать** при mint (v0.2), но тогда подтверждение будет доступно только тем, у кого есть **файл**.

**Ключевые принципы** (из **`SPEC.md` §1**; там нормативные формулировки):

| Принцип | Значение |
|:--|:--|
| **Open** | Любой может реализовать протокол на любом языке/платформе. |
| **Decentralized** | Нет одной компании, которая контролирует реестр. |
| **Offline-friendly** | Подлинность можно проверить без интернета, используя только хэши (см. **SPEC.md**). Типичные веб-верификаторы также читают цепочку и `dataUrl` для полного чека. |
| **Free to read** | Проверка никогда не стоит ничего (чтение в сети использует публичные RPC). |
| **Minimal on-chain** | На on-chain нет изображений и больших данных — только то, что требует **`SPEC.md`**. |

**Этот репозиторий** — **один референсный пример**: Solidity-контракт, статические страницы в `web/`, скрипты деплоя и хелперы — **автор: Andrei Chernikov**. Он демонстрирует идею end-to-end. **Нормативные правила** (форматы ID, хэширование, верификация, seals) находятся в **[`SPEC.md`](SPEC.md)**; обсуждение безопасности — в **[`SECURITY.md`](SECURITY.md)**.

*Если корень сайта показывает README-стилевый контент, но `verify.html` отдаёт 404, возможно GitHub Pages всё ещё обслуживает сборку отдельной ветки/Jekyll. Предпочитайте Settings → Pages → Source: GitHub Actions и зеленую успешную сборку Deploy GitHub Pages — смотрите [`.github/workflows/pages.yml`](.github/workflows/pages.yml).*

**GitHub Pages — адрес реестра:** статический HTML в git содержит `NET.contract: ""`. Workflow Pages подставляет ваш Polygon address на этапе сборки из **`ODP_CONTRACT_ADDRESS`** (repository secret или variable — строка checksum `0x…`; workflow использует secret, если он задан, иначе variable). Добавьте это в Settings → Secrets and variables → Actions (одинаковое значение для всех трёх страниц). Workflow также пишет `registry-config.json` рядом с HTML; UI грузит его с `cache: no-store`, чтобы после деплоя первая загрузка HTML подтянула адрес даже если браузер закэшировал старый HTML без `NET.contract`. Если secret отсутствует — задайте адрес локально в `web/creator.html`, `web/passport.html` и `web/verify.html` или добавьте `web/registry-config.json` с `{"contract":"0x…"}` для статического хостинга. **Быстрая проверка локально:** откройте `creator.html` один раз как `…/creator.html?contract=0xYourPolygonAddress` — UI сохраняет значение в **sessionStorage** для этой вкладки (ключ зависит от chain id), так что вы сможете убрать query и продолжить в рамках той же сессии.

## Что это такое

ODP позволяет зарегистрировать любой физический или цифровой объект в блокчейне Polygon и подтвердить его подлинность — используя человекочитаемый ID, криптографический хэш и (для физических объектов) физическую привязку (seal).

```
ODP-2026-03-4829301     ← Human ID (на этикетке, упаковке, сайте)
C-482-930-174          ← Creator ID (ваша постоянная идентичность)
```

Любой, у кого есть телефон, может отсканировать QR и проверить:

- кто это сделал
- когда это было зарегистрировано
- менялись ли данные (и если да — обнаружит ли это протокол)
- сохранен ли физический seal (в зависимости от выбранного метода seal)

---

## Как это работает

```
1. Регистрируете Creator ID    (~US$0.02 типично, один раз — gas + fee)
       ↓
2. Регистрируете ваш объект        (~US$0.02 типично — gas + fee)
   → генерируется Human ID
   → хэш данных сохраняется в on-chain
       ↓
3. Печатаете метку верификации
   → QR code  odp://ODP-2026-03-4829301
   → Human ID
   → Creator ID
   → физический seal (см. ниже)
       ↓
4. Любой сканирует → верификатор проверяет блокчейн → подлинность ✓
```

## Быстрый старт (пример веб-интерфейса)

Следующие шаги используют **live demo** ссылки выше — **рабочие примеры** по **официальному v0.1** контракту.

### 1. Кошелёк

- **Десктопный браузер:** любое расширение **EIP-1193**, которое инжектит **`window.ethereum`**, может подключиться (см. “Кошельки (в браузере)” вверху этого README). **MetaMask** — популярный вариант; **Rabby**, **Coinbase Wallet**, **Brave Wallet** и другие тоже работают так же, когда вы нажимаете **Connect**.
- **Телефон:** установите приложение кошелька (**MetaMask** или другое, которое поддерживает Polygon и in-app browsing). Откройте демо в **in-app browser** кошелька, чтобы страница получила injected provider — та же идея для десктопа.

Создайте кошелёк, сохраните seed-фразу (backup) и добавьте **Polygon PoS**, если вас попросят.

### 2. POL для gas и комиссий

Регистрация Creator ID и минтач паспорта происходят через **транзакции** в Polygon PoS. Вы платите **network gas** в **POL**, и каждая такая операция дополнительно сжигает фиксированную **0.001 POL** протокольную комиссию — на практике часто это **~US$0.02 суммарно за транзакцию** (gas + fee; зависит от ситуации). Страница **Verify** — read-only и **не требует** POL или кошелёк. Обновление URL on-chain — только **gas** (без дополнительного протокольного fee).

### 3. Официальный контракт

Таблица **Current release** показывает канонический деплой **v0.1**. Демонстрационный HTML уже настроен на этот адрес.

**Хостинг папкой (`passport.html`):** имя файла на вашем сервере должно строго совпадать с форматом **`<Human ID>.json`** (например `ODP-2026-03-4829301.json`), а зарегистрированный `dataUrl` должен быть **полной HTTPS ссылкой** на этот файл (например `https://example.com/passport/ODP-2026-03-4829301.json`). Solidity-контракт в этом репозитории умеет резолвить `folderBase + "/" + HumanID + ".json"` **внутри транзакции mint** при пере-деплойменте (`dataUrlIsFolderBase`); текущий публичный Polygon-деплой ещё использует более старый ABI, поэтому веб-UI держит **`NET.supportsFolderBaseMint: false`** и делает **вторую** транзакцию (`updatePassportUrls`), чтобы заменить временный mint-URL. Поставьте **`supportsFolderBaseMint: true`** только после деплоймента обновлённого контракта и вставки его адреса.

Если вам нужен **отдельный** деплой (например, приватный тест), используйте stack из `deploy/` и подключайте адреса согласно **`SPEC.md`** — этот workflow предназначен для операторов и интеграторов, и не нужен для попытки публичного демо.

### 4. Регистрируйте ваш Creator ID

**Пример UI:** откройте **[Creator ID (live demo)](https://object-digital-passport.github.io/object-digital-passport/creator.html)** — **Connect Wallet**, затем пройдите шаги регистрации.

При регистрации выберите тип:

- **`C`** — Creator (индивидуальный художник, фотограф, автор)
- **`B`** — Brand (компания, студия, лейбл)
- **`P`** — Proof Institution (музей, галерея, аукционный дом)

Вы получите постоянный ID вида `C-482-930-174`.

**Публикуйте ваш ID публично** — на вашем сайте, в соцсетях и на физических объектах. Именно так другие подтверждают, что паспорт был выдан вами.

```
Short:  C-482-930-174
Full:   C-482-930-174 / Your Name / 0x742d35Cc...
```

### 5. Минтите паспорт

**Пример UI:** откройте **[Passport (live demo)](https://object-digital-passport.github.io/object-digital-passport/passport.html)**, подключите кошелёк, заполните форму и нажмите **Mint Passport**. После mint'инга скачайте `passport.json` и разместите его по **`dataUrl`**, который вы использовали.

*(Опционально: автоматизацию и CLI-процессы описывает `tools/mint.py` — это не требуется для демо в браузере.)*

#### Хостинг `passport.json` на сторонних сайтах

Верификатор загружает ваш `dataUrl` в браузере. URL должен:

- быть **HTTPS**
- возвращать **сырой JSON** — HTTP-ответ должен содержать только байты паспорта (не HTML GitHub-страницы, не login wall)
- для GitHub/Git-Forge использовать **Raw** ссылку (`raw.githubusercontent.com/...`), а не blob-viewer
- поддерживать **CORS** — хост должен разрешать cross-origin `GET` для страницы верификации (у многих статических хостингов и GitHub Raw это разрешено)
- загружать **неизменные байты** — файл нужно отправлять без правок с того скачивания, которое даёт mint

Если вам нужен Human ID в пути URL, минтите с “стабильным” URL сначала, загрузите файл, затем используйте **Update hosting URLs** в UI кошелька (gas только — без второго mint fee).

Полное нормативное описание: **SPEC.md §9 — Hosting `dataUrl` (third-party sites)**.

### 6. Проверка

**Пример UI:** откройте **[Verify (live demo)](https://object-digital-passport.github.io/object-digital-passport/verify.html)** в любом браузере. Введите Human ID или вставьте URI в формате `odp://`. **Кошелёк не нужен.**

**Шаблон прямой ссылки:**

```
https://object-digital-passport.github.io/object-digital-passport/verify.html?id=ODP-2026-03-4829301
```

## Физическая привязка (Physical seal)

Для физических объектов seal обязательна: она связывает цифровой паспорт с **конкретным** объектом перед вами.

### Нумерованный seal (простой, широко используемый)

Подходит любая seal, где есть доказательство вскрытия и **уникальный напечатанный номер** — голографическая наклейка, восковая печать, пломба, нумерованная этикетка. Запишите номер и описание в паспорте; любой сможет сверить физическую метку с документом.

- Оценочная стоимость: от ~$0.05 за штуку (зависит от материала)
- Легко найти в разных масштабах

Этот референсный демонстрационный пример сделан вокруг понятных рабочих процессов; **нумерованные seal** закрывают большинство потребностей мастеров без дополнительного оборудования.

### NFC криптосил (высокая надёжность)

Протокол поддерживает опциональную **криптографическую NFC seal** (challenge–response с ключом, привязанным к чипу). Требования строгие (см. **`SPEC.md` §6**): “обычные” NFC стикеры не подходят для этого профиля. Выбор продукта и UX верификации — детали реализации; следуйте спецификации, если реализуете этот путь.

### Метка верификации

Распечатайте метку для каждого объекта, которая содержит:

- QR code (`odp://ODP-YYYY-MM-NNNNNNN`)
- Human ID текстом
- Creator ID текстом
- метку протокола (`ODP`)

Метка должна физически покрывать/удерживать seal так, чтобы при снятии метки seal была повреждена или хотя бы нарушена (см. **`SPEC.md`** правила удержания seal).

## Цифровые объекты

Для цифрового искусства, видео, 3D-моделей и других цифровых файлов:

1. **Регистрируйте до публикации** исходный файл
2. On-chain сохраняется SHA-256 хэш исходного файла
3. Тот, кто первым зарегистрировал хэш, и является “автором” в записи
4. После регистрации публикуйте только производные версии (сжатые, watermarked, уменьшенное разрешение)
5. Оригинальный файл остаётся вашей криптографической “пруф”-проверкой авторства

C2PA совместимость: если ваш файл содержит встроенный C2PA манифест
(из Photoshop, Lightroom, Leica camera и т.п.), то хэш файла автоматически включает и манифест. Никаких дополнительных шагов не нужно.

## Proof Institution

Музеи, галереи и эксперты могут регистрироваться как тип `P`
и прикреплять attestations к любому паспорту:

```
ODP-2026-03-4829301
  └── Proof от P-029-384-751  Garage Museum    2031
  └── Proof от P-774-002-391  Sotheby's        2051
```

Регистрация открыта — утверждение не требуется.
Институции обязаны публиковать свой ID публично, чтобы любой мог проверить их идентичность.

## SDK

Чтобы собрать верификатор или интегрировать ODP в приложение:

```javascript
// Минимальная верификация — чтение из блокчейна
const provider = new ethers.providers.JsonRpcProvider("https://polygon-rpc.com");
const contract = new ethers.Contract(CONTRACT_ADDRESS, ABI, provider);

const record   = await contract.getPassport("ODP-2026-03-4829301");
const creator  = await contract.getCreator(record.creatorId);
const proofIds = await contract.getProofsForPassport("ODP-2026-03-4829301");
```

Используйте **адрес контракта из Current release** для `CONTRACT_ADDRESS` в Polygon PoS. Чтение бесплатно. Кошелёк или API key не нужны.

См. `SPEC.md` секцию 13 для полного описания интерфейса SDK.

## Стоимость

**v0.2+** (упакованный байт on-chain **≥ 2**): транзакции **register**, **mint** и **proof** платят **только gas** сети Polygon (POL) — **без** отдельного протокольного fee в этой строке.

Старые деплойменты **v0.1-era** использовали отдельное сжигаемое fee на некоторых действиях; этот референсный UI не нацелен на такие контракты.

| Действие | Оценочная стоимость (v0.2) |
|:--|:--|
| Register Creator ID | ~US$0.01 (разово) — gas only |
| Mint a passport | ~US$0.01 — gas only |
| Submit a proof | ~US$0.01 — gas only |
| Обновлять только URL паспорта (`updatePassportUrls`) | Только gas |
| Проверить объект | Бесплатно |
| Читать любые данные | Бесплатно |
