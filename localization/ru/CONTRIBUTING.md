## С чего начать

- Нормативный протокол — в **[`../../SPEC.md`](../../SPEC.md)**; обзор — в **[`../../README.md`](../../README.md)** и **[`README.md`](README.md)**.
- **Хорошие первые задачи:** issues с метками **`good first issue`** или **`help wanted`** (ставятся сопровождающими, когда задача подходит новичкам).
- **Идеи по протоколу / спецификации:** откройте обсуждение в формате *Specification / protocol* или согласуйте до крупных PR.
- **Безопасность:** не публикуйте эксплуатируемые детали в открытых issues — следуйте **[`../../SECURITY.md`](../../SECURITY.md)**.

## Форк и pull request (кратко)

1. **Форк** репозитория на GitHub (или запросите доступ **collaborator** в организации, если работаете плотно с сопровождающими).
2. **Ветка** от `main` с говорящим именем, например `fix/verify-mobile`, `docs/contributing-typos`.
3. **Изменения** сфокусированными коммитами; стиль как в соседних файлах (`web/`, `contracts/`, `tools/`, Markdown).
4. **Проверка** локально (статические страницы, Hardhat, `mint.py`) — CI может покрывать не всё.
5. **Pull request** в **`main`** — шаблон PR попросит краткое описание и чеклист.
6. **Ответы** на ревью; сопровождающие стараются отвечать в течение нескольких дней (у небольших проектов сроки зависят от доступности).

## Не только код

Ревью английского и переведённых текстов, UX, визуальный дизайн, доступность и локализация (каталог [`localization/`](../)) ценны так же, как патчи к контрактам или JS. Цель — **стабильный протокол и продуктовая линия к январю 2027**; широкая обратная связь по [`SPEC.md`](../../SPEC.md) и статическим страницам помогает.

## Области репозитория

| Область | Заметки |
|--------|---------|
| **`SPEC.md`** | Ломающие изменения требуют обсуждения; зафиксируйте версию спецификации для реализаторов. |
| **`contracts/`** | Неизменяемость on-chain: многие исправления — **новый деплой** и линия версий — укажите в PR. |
| **`web/`** | Статический HTML/JS/CSS; помните о доступности и мобильных сценариях. |
| **`deploy/`** | Hardhat; не коммитьте приватные ключи. |
| **`tools/`** | Python CLI; новые флаги документируйте в `--help` или README. |

## Стиль

- **Markdown:** заголовки и тон как в соседних файлах.
- **JavaScript:** как в `web/*.html` (новый фреймворк — только по согласованию).
- **Solidity:** в духе `ObjectDigitalPassport.sol` и комментариев в нём.

## Метки issues (для сопровождающих)

Имеет смысл создать в **Issues → Labels**:

| Метка | Назначение |
|-------|------------|
| `good first issue` | Небольшая, понятная задача для первого PR |
| `help wanted` | Сопровождающим нужна помощь сообщества |
| `bug` | Что-то сломано |
| `enhancement` | Функция или улучшение |
| `spec` | Протокол / SPEC.md |
| `documentation` | Только документация / тексты |

Стандартные метки GitHub **`good first issue`** и **`help wanted`** хорошо узнаваемы ([здоровье сообщества](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions)).

## Настройка сопровождающих (защита веток) — по желанию

Чтобы в **`main`** попадали только изменения через pull request, см. **[`../../.github/BRANCH_PROTECTION.md`](../../.github/BRANCH_PROTECTION.md)** и включите правила в **GitHub → Settings**. Для ежедневных контрибьюторов не обязательно.

## По желанию: GitHub Discussions

**Discussions** можно включить в **Settings → Features** для вопросов и идей, ещё не оформленных как issues. Для маленьких проектов необязательно.
