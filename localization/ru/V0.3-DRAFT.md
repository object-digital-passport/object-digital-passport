- **Passport ID** (человекочитаемый термин) соответствует полю протокола **`humanId`**.
- **ID профиля** (человекочитаемый термин) соответствует полю протокола **`creatorId`**.

### 2.2 Матрица классификации, которую надо держать синхронной

- **Класс объекта**: physical / digital (уже есть в v0.2).
- **Кто может делать proof**: `P` и `M` (уже есть в v0.2).
- **Класс аффилиации** (proposal): `P_PARENT_CHILD` с жизненным циклом событий.

## 3) Несколько изображений в одном паспорте (proposal)

### 3.1 Зачем

Для ряда объектов одного изображения недостаточно (front/back/detail/macro/provenance page).  
В v0.2 on-chain хранится только один `imageHash` + `imageUrl`.

### 3.2 Кандидатные варианты v0.3

**Option A (строже и дешевле):**
- Оставить один канонический on-chain `imageHash` для совместимости.
- Добавить опциональный off-chain массив `images[]` в `passport.json` (до N элементов).
- Каждый элемент содержит URL + hash metadata; trust anchor остаётся через `dataHash`.

**Option B (богаче on-chain):**
- Добавить ограниченный on-chain массив изображений (например, до 3 или до 5).
- Хранить hash каждого изображения и опциональный URL.
- Дать paged getters и ABI-структуры для verifier UI.

### 3.3 Рабочая рекомендация

- Стартовать с **max 3** (рекомендуемое значение по умолчанию) и оставить возможность поднять до **5** до freeze.
- Если по gas выходит слишком дорого, для v0.3 оставить Option A, а Option B перенести на следующую линию.

### 3.4 Черновая схема данных (если Option B)

- `imageCount` (uint8, максимум 3 или 5).
- `images[i].imageHash` (bytes32, обязателен для занятого слота).
- `images[i].imageUrl` (string, optional, ограничения URL согласовать с политикой `dataUrl`).

## 4) Родительская P может отвязать дочернюю P (proposal)

Текущий flow v0.2: child предлагает, parent подтверждает.  
В v0.3 предлагается явная операция **detach** со стороны текущего parent.

### 4.1 Предлагаемые действия

- `proposePRelation(parent, child)` (логика уже есть).
- `confirmPRelation(parent, child)` (логика уже есть).
- `detachPRelation(parent, child, reasonCode?)` (новое).

### 4.2 Ограничения безопасности

- Отвязать может только текущий записанный parent.
- Child может перепривязаться к новому parent стандартным propose/confirm flow.
- Отвязка должна быть явно аудируемой (event + timestamp).

## 5) Обязательные даты связей и журнал изменений (proposal)

Добавить даты и историю для всех переходов состояния аффилиации:

- `joinedAt` — когда связь стала активной (время подтверждения).
- `detachedAt` — когда связь завершена (если завершена).
- `updatedAt` — последнее изменение состояния связи.
- Опционально `reasonCode` для detach (с ограниченной enum/string политикой в черновике спеки).

### 5.1 История на уровне событий

Эмитить отдельные события с UTC epoch timestamp:

- `PRelationProposed(...)`
- `PRelationConfirmed(..., joinedAt)`
- `PRelationDetached(..., detachedAt, reasonCode)`

### 5.2 Поведение UI / docs

- Показывать текущий статус: active / detached / never-linked.
- Для active показывать дату "since".
- Для detached показывать дату отвязки и reason (если есть).
- В verifier показывать историю, а не только текущее состояние.
