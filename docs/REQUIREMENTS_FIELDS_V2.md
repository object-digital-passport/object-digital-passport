# ODP v2 — Требования к полям данных: `.odpass` ↔ блокчейн

> **Статус:** рабочий документ-требования (draft). Не является нормативной редакцией SPEC.md.
> После утверждения станет основой редакции SPEC (линия 0.6, packed contract version `6`).
> Нормативный язык спецификации — английский; этот документ ведётся на русском как материал обсуждения.
>
> Референсная реализация требований: контракты v2 в `chain/contracts/` (эта же ветка).

---

## 1. Цели и принципы

ODP решает задачу: **отличить оригинал от подделки** — для любого физического или цифрового (онлайн) объекта, начиная с произведений искусства.

Система построена по принципу **Object ID** (международный стандарт описания объектов для идентификации: тип объекта, материалы и техника, размеры, надписи и маркировки, отличительные особенности, название, сюжет, дата/период, автор + фотографии + краткое описание). ODP — не надстройка над Object ID и не контейнер для него: ODP **развивает** этот принцип («Object ID v2»), добавляя криптографическую фиксацию во времени, публичный реестр и модель заверений.

Принципы:

1. **Паспорт полностью публичен.** Ни одно поле стандарта не рассчитано на сокрытие; приватных полей нет.
2. **Блокчейн доказывает две вещи:** (а) *момент* регистрации конкретного объекта и (б) *краткую суть* объекта — читаемую карточку, понятную даже без файла `.odpass`.
3. **Ядро неизменяемо.** Всё, что описывает объект и идентифицирует его, фиксируется при регистрации навсегда. Ошибка = ревокация + новый паспорт.
4. **Всё изменяемое — событие.** История владения и состояния ведётся только как append-only события on-chain после регистрации; перезаписываемых полей нет.
5. **Протокол не назначает «настоящего».** При конфликте двух паспортов на один объект решение принимает человек по совокупности сигналов (дата, заверения, флаги, репутация издателя).
6. **Издатель — сам владелец/автор** (многоуровневая модель): паспорт валиден без заверений; заверения экспертов/институций добавляются позже отдельными on-chain записями и повышают доверие, но не являются условием существования паспорта.

## 2. Модель хранения: три слоя

| Слой | Где | Изменяемость | Содержимое |
|---|---|---|---|
| **A. Ядро** | on-chain (`Passport` struct) | неизменяемо после минта (кроме URL-подсказок и owner) | карточка объекта, классификация, хеши-якоря (`dataHash`, `anchorsHash`, `imageHash`, `fileHash`), идентификаторы |
| **B. События** | on-chain (append-only записи + event log) | только добавление | передачи владения, изменения статуса/состояния, заверения, флаги подозрения, ревокация |
| **C. Полные данные** | файл `.odpass` (`passport.json` внутри ZIP) | неизменяемо: привязано `dataHash` | полное описание по принципу Object ID, блок якорей `anchors[]`, переводы, оригиналы/фото в `originals/` |

Правило целостности: `dataHash = SHA-256(минифицированный канонический passport.json)` — как в v0.5 (Unicode NFC, сортировка ключей, без пробелов, UTF-8, `passportId: null` при вычислении). `.odpass` остаётся ZIP-контейнером: `passport.json` + `manifest.json` (UX-метаданные, не якорь доверия) + `originals/`.

## 3. Слой A — on-chain ядро (неизменяемое)

### 3.1 Карточка объекта (новое в v2)

Краткая карточка хранится **прямо в блокчейне** и читается без `.odpass`. Это осознанный разворот решения v0.5 «имена в чейне не храним»: публичность и самодостаточность записи важнее анти-импersonation-аргумента, который закрывается репутационной моделью (§7) и обязательной публикацией Profile ID на официальном сайте участника.

| Поле | Тип | Лимит | Обяз. | Назначение |
|---|---|---|---|---|
| `title` | string | 1–128 байт | да | название объекта (в v0.5 было ≤256 — ужесточено: карточка, а не описание) |
| `authorName` | string | 1–128 байт | да | **новое**: читаемое имя автора/бренда (в v0.5 — только числовой `creatorId`) |
| `shortDescription` | string | 1–256 байт | да | **новое**: одна строка-аннотация — тип объекта, техника, год создания («мини-Object ID») |
| `domain` | string | ≤128 байт | нет | область (contemporary_art, software, …) — как в v0.5 |

Правила карточки:

- **Язык — как ввёл автор** (любой Unicode, нормализация NFC). Переводы и транслитерации — опциональный блок `translations` в `passport.json` (слой C), on-chain всегда одна строка.
- **Неизменяема навсегда.** Функций редактирования карточки в контракте нет. Опечатка или переименование = `revokePassport` + новый минт.
- **Байт-в-байт согласованность:** значения `title`, `authorName`, `shortDescription`, `domain` в `passport.json` обязаны в точности (байт-в-байт после NFC) совпадать с on-chain значениями. Верифайер обязан сравнить и при любом расхождении показывать паспорт как **невалидный** (см. §6).

### 3.2 Идентификаторы и классификация (сохранены из v0.5)

| Поле | Тип | Обяз. | Примечание |
|---|---|---|---|
| `passportId` | string | да | `ODP-YYYY-MM-NNNNNNNNN`, генерируется контрактом |
| `contractVersion` | uint8 | да | packed `SPEC_MAJOR*16+SPEC_MINOR`; v2-референс = `6` (линия 0.6) |
| `creator` | address | да | кошелёк издателя, неизменяем |
| `owner` | address | да | текущий владелец; меняется только `transferPassport` (событие слоя B) |
| `creatorId` | string | да | Profile ID (`C-…`/`B-…`/`P-…`/`M-…`); модель профилей C/B/P/M и месячные лимиты минта (C=1000, B=100000, P/M — без лимита) сохранены без изменений |
| `year`, `month` | uint32/uint8 | да | UTC-календарь месяца минта (проверяется контрактом) |
| `objectType` | string | да | `physical` / `digital` / `mixed` |
| `contentClass`, `lifecycleStatus`, `aiStatus`, `verificationMethod`, `editionModel` | uint8 | да | контролируемые словари v0.5 сохранены; `lifecycleStatus` далее меняется только событием (§4) |
| `timestamp` | uint256 | да | время блока минта — **главное доказательство момента регистрации** |
| `mintAgent` | address | да | `address(0)` = принципал минтил сам; иначе кошелёк делегата |

### 3.3 Хеши-якоря

| Поле | Тип | Обяз. | Назначение |
|---|---|---|---|
| `dataHash` | bytes32 | да | SHA-256 канонического `passport.json` — якорь всего слоя C |
| `anchorsHash` | bytes32 | да | **новое**: SHA-256 канонического минифицированного массива `anchors` из `passport.json` — позволяет проверить блок якорей отдельно, не имея всего паспорта |
| `anchorTypesMask` | uint32 | да | **новое**: битовая маска типов присутствующих якорей (§5.2); контракт проверяет жёсткий минимум по `objectType` |
| `imageHash` | bytes32 | физ./mixed — да | SHA-256 главного фото (карточка + первичная сверка). Для digital — опционально |
| `fileHash` | bytes32 | digital/mixed — да; physical — 0 | SHA-256 файла-оригинала — главный якорь цифрового объекта |
| `dataUrl`, `imageUrl` | string | нет | ≤512; изменяемые URL-подсказки хостинга (`updatePassportUrls` с подтверждением `dataHash` — сохранено из v0.5); `dataUrl` указывает только на `.odpass` |

### 3.4 Ревокация (сохранена)

`revoked` / `revokedAt` / `revocationReasonHash` — необратимая ревокация создателем или governance, как в v0.5.

### 3.5 Удалено из on-chain ядра v0.5 — и куда ушло

| Поле v0.5 | Судьба в v2 |
|---|---|
| `sealType`, `sealHash`, `nfcPublicKey`, `nfcModel` | → якоря `nfc` / `numbered_seal` в `anchors[]` (слой C), зафиксированы `anchorsHash`. NFC-криптопроверка выполняется off-chain по публичному ключу из якоря, целостность которого доказана on-chain |
| `imageHash2/3`, `imageUrl2/3` | → якоря `photo` в `anchors[]` (количество фото не ограничено тремя); on-chain остаётся только главный `imageHash` |
| `currentLocation`, `rightsNote`, `conditionNote`, `damageHistoryHash/Url` | → события слоя B (`recordPassportEvent`); перезаписываемых полей нет, история не теряется |
| `auxCommitmentHash/Uri` (COA PDF) | → заверение с `documentHash` в реестре заверений (§4.3) либо якорь `document` |
| `ndppCommitmentHash/Uri` | → удалено: офлайн-носитель (NFC/QR) — транспортный слой; его полезная нагрузка проверяется по `dataHash`/`anchorsHash`, отдельный коммитмент избыточен |

## 4. Слой B — on-chain события (append-only)

Всё изменяемое — события. Текущее значение = последнее событие соответствующего типа; полная история всегда доступна из event log. Перезапись невозможна.

### 4.1 Владение и жизненный цикл (основной контракт)

| Событие | Функция | Кто вправе |
|---|---|---|
| `PassportTransferred` | `transferPassport` | текущий `owner` |
| `PassportEventRecorded` | `recordPassportEvent(passportId, kind, value, note, attachmentHash, attachmentUrl)` | `creator`, `owner` или governance |
| `PassportRevoked` | `revokePassport` | `creator` или governance |
| `PassportUrlsUpdated` | `updatePassportUrls` | creator / owner / активный publishing-делегат |

Виды `kind` для `recordPassportEvent`:

| kind | Значение | Полезная нагрузка |
|---|---|---|
| 1 | `status` — смена жизненного статуса | `value` = новый `lifecycleStatus` (1–4), обновляет хранимое поле |
| 2 | `location` — смена местонахождения | `note` ≤256 |
| 3 | `rights` — изменение прав | `note` ≤256 |
| 4 | `condition` — состояние | `note` ≤256 |
| 5 | `damage` — повреждение | `note` + опц. `attachmentHash/Url` (акт, фото) |
| 6 | `restoration` — реставрация | `note` + опц. `attachmentHash/Url` |
| 7 | `custom` — прочее | `note` + опц. `attachmentHash/Url` |

On-chain хранится компактное резюме (`eventCount`, `lastEventKind`, `lastEventAt` + актуальный `lifecycleStatus`); тексты живут в event log — это заменяет четыре перезаписывающих сеттера v0.5 одной функцией и экономит байткод.

### 4.2 Provenance

История объекта **до** регистрации стандартом не фиксируется и не сериализуется: она непроверяема протоколом и создавала бы ложное чувство достоверности. Провенанс в ODP начинается с момента минта: `PassportMinted` → цепочка `PassportTransferred` + события состояния + заверения. Издатель может изложить прежнюю историю в свободном поле `description` (слой C) — без структурного статуса.

### 4.3 Заверения (сателлит `ODPPassportProofRegistry`)

Модель v2 (многоуровневая): заверение = on-chain запись «объект/паспорт проверен» от профиля типа P (проверяющая институция) или M (музей).

| Поле записи | Обяз. | Назначение |
|---|---|---|
| `proofId` (`PRF-YYYY-MM-NNNNNNNN`) | да | идентификатор заверения |
| `prover` (Profile ID) | да | кто заверил |
| `passportId` | да | что заверено |
| `documentHash` | нет | SHA-256 подписанного документа экспертизы (PDF и т.п.) |
| `documentUrl` | нет (≤512, только при наличии хеша) | где документ опубликован |
| `timestamp` | да | момент заверения |

Гранулярность по якорям **не вводится** (решение владельца стандарта): заверение подтверждает факт проверки паспорта в целом; детали — в приложенном документе.

### 4.4 Флаги подозрения (сателлит `ODPCounterfeitConcern`)

Сохраняется как есть: P/M-профиль может поднять/снять флаг «подозрение на подделку» с `reasonHash`. Это ключевой инструмент модели дубликатов (§7).

### 4.5 Прочие сателлиты (сохранены без изменений модели)

- `ODPRegistryRelations` — P-аффилиации, mint-агенты (двухшаговое рукопожатие), publishing-делегирование.
- `ODPWalletDocumentAnchor` — Level 1C: привязка хеша внешнего документа к кошельку.
- `ODPExtensionMintRouter` + `IODPExtension` — расширяемый минт; входные структуры обновлены под v2.
- Level 1B (EIP-191 подпись кошелька создателя) — off-chain механизм, без изменений.

## 5. Слой C — `passport.json` (полные данные, привязаны `dataHash`)

### 5.1 Поля

Ядро схемы v2 — категории Object ID как поля первого класса. «Р» = обязательно, «Р*» = обязательно для указанного типа объекта, «О» = опционально.

| Поле | Объект | Категория Object ID | Примечание |
|---|---|---|---|
| `version` | Р | — | `"0.6"` |
| `passportId` | Р | — | `null` до минта (правило хеширования сохранено) |
| `title` | Р | Название | = on-chain байт-в-байт |
| `authorName` | Р | Автор | = on-chain байт-в-байт |
| `shortDescription` | Р | Краткое описание | = on-chain байт-в-байт |
| `domain` | О | — | = on-chain байт-в-байт (в т.ч. пустая строка) |
| `description` | О | Краткое описание (расшир.) | полное описание, без лимита |
| `subject` | О | Сюжет | что изображено/о чём объект |
| `creationDate` | Р | Дата/период | дата или период создания объекта (не путать с датой регистрации) |
| `objectType` | Р | Тип объекта | `physical`/`digital`/`mixed` |
| `contentClass`, `aiStatus`, `verificationMethod` | Р | — | словари v0.5 |
| `status` | Р | — | статус на момент регистрации; текущий — из событий слоя B |
| `edition` | Р | — | `model` (unique/limited/open/dynamic) + параметры тиража |
| `authorship` | О | Автор (расшир.) | структурный блок: соавторы, команда, идентификаторы автора |
| `anchors[]` | Р | Материалы, Размеры, Надписи, Особенности, Фото | единый блок идентификационных якорей — §5.2 |
| `digital` | Р* (digital/mixed) | — | `subtype`, `format`, `fileHash`, `fileSize` |
| `translations` | О | — | переводы `title`/`shortDescription`/`description` по языкам (`{"en": {...}}`) |
| `year`, `month`, `registeredAt`, `registration` | Р | — | момент регистрации, UTC-only (правила v0.5 сохранены) |
| `refinementTags`, `additionalMetadata` | О | — | как в v0.5 |

Удалено из схемы v0.5: `currentState` (→ события), `physical.seal` (→ якоря), `image`/`images` (→ якоря `photo`), `identifiers`/`iiif`/`sustainability`-namespace-черновики (переносятся в `additionalMetadata` до отдельного решения).

### 5.2 Блок `anchors[]` — якоря привязки паспорта к объекту

Якорь — проверяемое свойство, мешающее приложить настоящий паспорт к подделке. Каждый якорь:

```json
{
  "type": "photo",
  "data": { "...тип-специфичные поля..." },
  "hash": "sha256:...",
  "verification": "как проверять (свободный текст или код методики)"
}
```

Стартовый реестр типов и биты `anchorTypesMask`:

| Бит | Тип | Категория Object ID | Содержимое `data` |
|---|---|---|---|
| 1 | `photo` | Фотографии | ссылка на файл в `originals/`, ракурс; `hash` = SHA-256 файла |
| 2 | `dimensions` | Размеры | габариты с единицами и точностью |
| 4 | `materials` | Материалы и техника | материалы, техника исполнения |
| 8 | `distinguishing_features` | Отличительные особенности | дефекты, кракелюр, следы ремонта и т.п. |
| 16 | `marks` | Надписи и маркировки | подписи, штампы, серийные номера, где расположены |
| 32 | `file_hash` | — | точный SHA-256 файла-оригинала (= on-chain `fileHash`) |
| 64 | `perceptual_hash` | — | перцептивный хеш с обязательным `algorithm` (рекомендуемые: `phash-dct-64`, `pdq`); только дополнительный якорь |
| 128 | `c2pa` | — | хеш C2PA-манифеста; только дополнительный якорь |
| 256 | `nfc` | — | модель чипа (`NTAG424DNA`/`NTAG424DNA_TAGTAMPER`), публичный ключ |
| 512 | `numbered_seal` | — | номерная пломба/голограмма |
| 1024 | `fingerprint` | — | измеримый отпечаток объекта: `method` + `dataHash` + ссылка на методику |
| 2048 | `dna` | — | синтетическая ДНК-метка / микроточки |
| 2^31 | `custom` | — | якорь вне реестра; тип указывается в `data.customType` |

Новые типы добавляются редакцией SPEC без изменения схемы (зарезервированы биты 12–30).

**Жёсткий минимум (валидируется контрактом по маске):**

- `physical` и `mixed`: обязательны `photo` (≥1) + `dimensions` + `materials` + `distinguishing_features` (маска ⊇ 15) и `imageHash ≠ 0`;
- `digital` и `mixed`: обязателен `file_hash` (маска ⊇ 32) и `fileHash ≠ 0`.

Паспорт без этого минимума не минтится: паспорт без фото и размеров ничего не доказывает.

**`anchorsHash`** = SHA-256 канонической минифицированной сериализации массива `anchors` (те же правила, что для `dataHash`). Контракт хранит его отдельно от `dataHash`, чтобы блок якорей можно было проверить изолированно (например, по данным с офлайн-носителя).

## 6. Правила согласованности и верификации

Верифайер обязан проверить (порядок нормативен):

1. `SHA-256(passport.json) == dataHash` (с канонизацией и `passportId: null`);
2. `SHA-256(canonical(anchors)) == anchorsHash`, и фактические типы якорей соответствуют `anchorTypesMask`;
3. карточка: `title`, `authorName`, `shortDescription`, `domain` в JSON байт-в-байт равны on-chain значениям;
4. `objectType`, `year`, `month` в JSON равны on-chain;
5. для digital/mixed: `digital.fileHash == fileHash` on-chain; якорь `photo` главного фото == `imageHash`;
6. `revoked == false`; наличие активного флага подозрения (§4.4) — предупреждение;
7. далее — физическая сверка объекта с якорями (фото, размеры, материалы, особенности, метки).

Любое расхождение в пп. 1–5 = паспорт **невалиден** (не «предупреждение»). On-chain данные всегда авторитетны.

## 7. Модель дубликатов и подделок

Ничто не мешает мошеннику зарегистрировать собственный паспорт на подделку или на чужой объект. Ответ стандарта — репутационный, протокол не выбирает «настоящего»:

- глобальная уникальность `dataHash`/`fileHash`/якорей **не вводится**: она защищает только от точных копий, создаёт гонку «кто первый зарегистрировал» и вручает добросовестному автору отказ в минте как инструмент атаки;
- верифайер обязан показывать: дату регистрации (`timestamp`), издателя (`creatorId` + подтверждение Profile ID на официальном сайте), заверения P/M-институций, активные флаги подозрения;
- конкурирующие паспорта разрешаются людьми: более ранняя регистрация + заверения авторитетных институций + отсутствие флагов против поздней регистрации без заверений;
- инструмент эскалации — `ODPCounterfeitConcern` (флаг с причиной от P/M-профиля).

## 9. Референсная реализация и бюджет EIP-170

Контракты v2 в `chain/contracts/` компилируются с продовыми настройками (solc 0.8.20, optimizer runs=1, viaIR). Замеры deployed bytecode — см. Приложение А; лимит EIP-170 = 24 576 байт.

Ожидаемый эффект v2 на размер: удаление 6 перезаписывающих функций и 20+ полей структуры компенсирует добавление карточки и якорей; проверяется компиляцией в CI этой же ветки.

## 10. Трассируемость решений

Документ реализует решения владельца стандарта от 2026-07-15: (1) чейн = момент + карточка; (2) карточка title/автор/описание; (3) язык автора + переводы в файле; (4) карточка неизменяема, байт-в-байт; (5) многоуровневый издатель; (6) полная публичность; (7) провенанс только после минта; (8) событийная модель состояния — подтверждена владельцем стандарта 2026-07-16; (9) единый anchors[]; (10) жёсткий минимум идентификации; (11) SHA-256 основной, perceptual/C2PA дополнительные; (12) заверение = факт проверки + опц. документ; (13) дубликаты — репутация + флаги, без глобальной уникальности хешей.
