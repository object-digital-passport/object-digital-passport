# ODP — design notes (historical / exploratory)

*Author: Andrei Chernikov*

**Status:** informal notes and **future directions**. **Not** the specification. The binding document is **[`SPEC.md`](../SPEC.md)** (v0.2 draft).
Open, not-yet-implemented ideas from this file are actively tracked in **[`V0.3-DRAFT.md`](V0.3-DRAFT.md)**.

This file kept early thinking about a **major** revision relative to v0.1. Much of what was “v0.2 direction” is now **specified in SPEC** (optional `dataUrl`, folder-base flows in the web UI, **`.odp` offline bundle §15**, etc.). Treat sections below as **context and open ideas**, not requirements.

---

## 1. Why a “v0.2” line existed

v0.1 optimised for: one contract, one `dataHash` over canonical `passport.json`, `dataUrl` stored on-chain.

Pain points that motivated discussion:

- Creators think in **folders** (`https://example.com/art/passports/`), not always a single opaque URL chosen before mint.
- Passport ID is **assigned at mint** (`passportId` in JSON, `humanId` in ABI); the mental model “upload `ODP-….json` under my folder” is easier than “pick a URL without the ID, then update”.
- **Embedding `dataUrl` inside `passport.json`** would help self-description, but **would change `dataHash`** unless the spec defines an exclusion list or new rules.

**Current SPEC** already allows empty `dataUrl` and documents hosting patterns; the web **Passport** flow supports folder-base mint where the deployment supports it.

---

## 2. Folder-first hosting (canonical URL pattern)

**Idea:** register a **base URL** (HTTPS folder); the file URL is **`{base}/{passportId}.json`** (same string as Passport ID / JSON field `passportId`; ABI wire name `humanId`).

**Reality in repo:** the chain stores `dataUrl` as a string; the UI may call `updatePassportUrls` after mint. The **file bytes** must still match the on-chain `dataHash`.

See **SPEC §8–§9** and root **README** for normative hosting rules.

---

## 3. Hashing boundary & manifest

v0.1 / v0.2 **SPEC:** `dataHash = SHA-256( canonical minified passport.json )` with **`humanId: null` in the hashed payload at mint**; post-mint exports may include the real `humanId` string — verifiers normalize for comparison (see **SPEC §11 / §15.2**).

**`.odp` manifest:** the bundle includes **`manifest.json`** for UX only (**not** a trust anchor). Reference shape: **SPEC §15.1.1** — implemented consistently in **`web/passport.html`** and **`tools/mint.py`**.

Older idea of a separate **`odp-manifest.json`** name is **not** used; the normative entry name inside the ZIP is **`manifest.json`**.

## 5. Open questions (not decisions)

- Verify UX: resolve `dataUrl` only from a folder pattern without reading chain — still a product choice.
- IDN / path encoding for URLs.
- IPFS / Arweave as first-class `dataUrl` schemes in a future spec revision.

---

## 6. `.odp` offline bundle — **implemented**

**Specified in [`SPEC.md`](../SPEC.md) §15.** ZIP-based **`.odp`** ships canonical **`passport.json`**, **`manifest.json`**, and optionally **`original/*`** / **`image/*`** for hash checks against the chain.

**Repository outputs:** after mint, use the **Passport** page download/share **or** **`python tools/mint.py`** — both emit the **same bundle layout** and reference **manifest** fields (**§15.1.1**).
