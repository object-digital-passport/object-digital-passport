# Идеи к v1.0

*Черновик направлений развития · не нормативный документ. Написан по-русски; английской версии нет.*

Этот файл — **набросок**, а не спецификация. Решения для стабильной линии **v1** фиксируются в **`SPEC.md`**, релизах и обсуждениях репозитория.

## Убрать или пересмотреть `freeze()` (v0.x)

Сейчас в референсном контракте есть **`freeze()`**: его может вызвать только **`deployer`**, и это **необратимо** блокирует **новые записи** во всём реестре (`notFrozen`), при этом чтение остаётся.

Для **v1** имеет смысл **не переносить эту модель как есть**. Причина простая: «заморозить весь реестр навсегда» — жёсткий рубильник для операторов и интеграторов: любой сценарий, где ещё нужны записи (хотя бы техподдержка, догоняющий минт, ручной фикс), становится невозможным без **нового адреса контракта**. Для долгоживущей продуктовой линии обычно хотят либо **мягкую миграцию** (новый реестр + чёткие правила сосуществования), либо **точечные политики**, а не один необратимый запрет на все записи в старом контракте. Формулировка в v1 может быть: отказ от глобального `freeze`, замена на документированный путь обновления протокола без «заморозки навсегда», либо ограниченный механизм, если он действительно нужен по аудиту.

## Расширение `passport.json` без смены адреса контракта

**Уже сейчас** эталонная модель такая: на цепи хранится **`dataHash` = SHA-256 канонического `passport.json`**. Контракту **не нужны отдельные поля** под каждый новый JSON-ключ: всё, что входит в правила канонизации в **`SPEC.md`**, автоматически попадает под этот якорь при **новом** минте.

Ограничение жёсткое: после минта **`dataHash` не меняется**. Значит для **уже выпущенного** паспорта нельзя добавить в тот же JSON новые **значимые** поля «в доверие», если они должны были бы изменить канонические байты: проверка перестанет совпадать с сетью. Варианты без нового контракта:

- **Новые паспорта** — обновляете SPEC (новые ключи, версия `"version"` в JSON), минт как раньше, тот же байткод.
- **Метаданные вне якоря** — например только в `manifest.json` бандла или в ключах, явно **исключённых** из канона в SPEC; так проще для UX и эволюции без смены протокола, но **не** опираются на `dataHash` (слабее с точки зрения «всё в одном доказательстве»).

Если позже понадобится **отдельное обновляемое обязательство** (второй документ, доп. слой атрибутов с отдельным хэшем) **без смены основного `dataHash`** — это уже проектное решение **следующей** версии контракта или вспомогательного реестра: в уже задеплоенный инстанс новые storage-слоты «задним числом» не добавить.

Итого: «расширяем JSON без переделки контракта» — **да для эволюции спецификации и новых выпусков**; **нет для произвольного роста якоря у существующей записи** без протокольного крюка (новый деплой / новый реестр).

## Префиксы профиля: **C**, **B**, **P**, **M**

Это **тип регистрации создателя** (первый символ **Profile ID**): художник/коллекционер (**C**), бренд (**B**), доказывающая институция (**P**), музей (**M**). В контракте они **зашиты в логике**, не в «произвольной таблице»:

- `registerCreator` принимает только байт, прошедший **`_isValidType`** — сейчас это жёсткое **ИЛИ** четырёх констант.
- От префикса зависят **лимиты минта** (C/B — помесячный потолок; P/M — без лимита в коде), **право подавать proof** (только P/M), отдельные проверки для **P-affiliation** и т.д.

**Новую букву профиля** (условный **«X»**) в том же задеплоенном контракте **не добавить конфигом**: нужны новый байткод и осмысленные правила — лимиты, какие функции доступны, надо ли требовать вайтлист/аттестацию off-chain. Это **новый деплой** (или следующая версия реестра), а не JSON.

Оффчейн можно описывать **подроли** внутри существующего профиля (метаданные, договоры), если не требуется отдельная **on-chain** ветка с новыми привилегиями.

## Типы паспорта: `objectType` on-chain и что такое `typeToExtension`

Здесь два разных слоя — их путать не стоит.

**1. Поле `objectType` в `Passport` (строка на цепи).** В **v0.3** ядро минтит только **`"physical"`** и **`"digital"`**. Отдельного «словаря подтипов» в ABI нет: если нужны **подклассы, отраслевые ярлыки, варианты НФТ** и т.п., их естественно вести **в `passport.json` + SPEC** (и в `dataHash`), оставаясь в одной из двух верхних веток on-chain. Так вы **не переделываете контракт**, пока хватает этой бинарной классификации на цепи.

Если продукту нужна **третья (и далее) обязательная ветка именно в поле записи** — например отдельная статистика/индексация по новой строке `objectType` в событиях и в storage — это уже **эволюция протокола**: новая версия контракта или миграция. Уже задеплоенный референсный инстанс сам по себе не «учит» новые значения строки.

**2. `typeToExtension` и `IODPExtension` — это не про C / B / P / M.** Буквы профиля и байт в **`typeToExtension`** — разные оси: первая задаётся при **`registerCreator`**, вторая — **код класса минта паспорта** (например байт **«V»** в тестах). В **v0.3** референсном контракте проводка **живая**: **`setMintExtension`** (только governance) заполняет слот; **`mintDigitalViaExtension`** и **`mintPhysicalViaExtension`** вызывают внешний **`validate` / `normalize`** и пишут тот же `Passport`, что и прямые **`mintDigital` / `mintPhysical`**. Примеры payload: **`chain/contracts/examples/ODPPassThroughDigitalExtension.sol`** (13-tuple), **`chain/contracts/examples/ODPPassThroughPhysicalExtension.sol`** (16-tuple); нормативно — **`SPEC.md`** и **[`ru/RELEASE_v0.3.md`](RELEASE_v0.3.md)**.

**Что это в одном предложении:** **подключаемая нормализация минта** (отдельный контракт на маршрут), а не способ «добавить шестую букву профиля без редеплоя».

**Ограничения и размер:** governance обязан регистрировать только проверенные расширения; слот **C/B/P/M** запрещён. Рост bytecode упирается в **EIP-170** — в **v0.3** часть read-функций и **`attestExternalDocument`** на основном реестре убраны; **якорь файлов по кошельку** вынесен в спутник **`ODPWalletDocumentAnchor`** (см. **`SPEC.md`**, **[`ru/RELEASE_v0.3.md`](RELEASE_v0.3.md)**).

Итого по типам паспорта/extension: **оффчейн таксономия и JSON** — без смены контракта; **новая буква профиля C/B/P/M** — отдельная версия протокола с явной политикой.

## Другие направления (кратко)

- **Стабильный SemVer и миграции:** чёткое обещание по совместимости `passport.json` и ABI между минорными версиями v1.x.
- **Расширяемость:** новые префиксы профиля — см. раздел про **C / B / P / M**; отдельные ветки минта через **`typeToExtension`** — см. раздел про **`objectType` и extension**; во v1 при необходимости зафиксировать governance подключения плагинов.
- **Верификация и UX:** единый сценарий «один QR / одна ссылка» для проверяющего без знания адресов реестров.
- **`odp://` как первый target stable-v1:** в текущем reference-потоке первый carrier-link intentionally указывает на GitHub-hosted `Verify`, потому что это самый стабильный общий entry point сегодня. Для **stable v1** первый target должен переключиться на `odp://...`, когда появится готовый resolver / app context, который надёжно откроет нужный verifier без web-only fallback логики.
- **Операторская прозрачность:** явные read API для крупных списков без RPC-перегруза (пагинация, индексация оффчейн при необходимости).
- **Поднять solc при следующей линии реестра (v0.7):** задеплоенный v0.6 собран **solc 0.8.20 + `--via-ir`**; из трёх известных багов этой версии два к коду неприменимы (не используются `.selector` и `assembly`), третий — `FullInlinerNonExpressionSplitArgumentEvaluationOrder` — исправлен в **0.8.21+**. Перекомпиляция сейчас не меняет уже задеплоенный байткод, поэтому обновление компилятора логично приурочить к следующему деплою. Разбор — в [`SECURITY.md`](SECURITY.md) (раздел про статический анализ).
