# ODP v0.5

*Plain-language summary of this version: [**v0.5 release note**](releases/v0.5.md). This page is the long-form detail behind it.*

ODP v0.5 makes the protocol more practical for real use. This line was shaped by real-world feedback and practical testing of ODP, with the goal of keeping the registry strict where authenticity must stay strict while making routine passport handling more usable.

## More practical passport lifecycle

The main v0.5 change is a clearer split between immutable passport data and selected mutable on-chain current-state fields. After minting, some operational fields no longer require re-minting just to stay current: status, location, rights notes, condition notes, and the current damage-history pointer can now be updated on-chain while the canonical hash-bound passport document remains stable.

This makes ODP better suited to real collections, archives, product records, and other workflows where the object itself remains the same but its current condition, handling context, or rights situation changes over time.

## Better object model

v0.5 also introduces a more practical object model built around `physical`, `digital`, and `mixed` objects. Instead of leaning on older, narrower category patterns, the line uses richer classification and state fields such as `objectType`, `status`, `contentClass`, and refinement tags, with `currentState` reserved for the parts that are expected to evolve.

This gives the registry a cleaner way to describe real objects that may have both physical and digital integrity surfaces, while staying explicit about what is hash-bound and what is operational state.

## Compact offline payloads

Alongside the canonical `.odpass` bundle, v0.5 adds support for a compact `odpOffline v0.1` payload for QR, NFC, and similar carrier scenarios. It can be anchored through the on-chain NDPP commitment slot when needed, without turning the main registry into a large public disclosure container.

The compact payload is an additional transport and disclosure layer, not a second source of truth. The canonical passport data still follows the anchored `passport.json` and `.odpass` flow tied to `dataHash`.

## Optional carriers, same trust model

NFC, QR, NDPP, and GS1 Digital Link remain optional carrier or entry layers in ODP v0.5. They can help users discover, carry, or preload passport data, but they do not replace the on-chain registry, the Passport ID, `.odpass`, or hash verification.

That distinction is deliberate: ODP can work with multiple presentation and transport layers, but authenticity still comes from the registry record plus verification of the canonical anchored bytes.

## Under the hood

The contract architecture was refined to stay deployable and practical for mainnet use. Validation and formatting logic were split more carefully between the main registry, a linked library, and paired optional satellites so the core system can remain within deployable bytecode limits while still supporting the broader v0.5 model.
