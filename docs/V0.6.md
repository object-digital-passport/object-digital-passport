# ODP v0.6

ODP v0.6 is the "honest trust" line: it keeps the v0.5 on-chain shape (`CONTRACT_VERSION` byte **6** at mint) and focuses on making the protocol's guarantees match reality — plus first-class support for the Object ID documentation checklist.

## Object ID compatibility profile

`passport.json` gains an optional `objectId` block with `subject` and `distinguishingFeatures` — the two [Object ID](https://icom.museum/en/resources/standards-guidelines/objectid/) checklist categories the schema previously lacked. Together with `title`, `authorship`, `creationDate`, `physical.*`, and a now-mandatory photograph (under the profile), a passport covers all nine Object ID categories: one document serves both **authenticity** (hash anchors, seals, institutional proofs) and **theft documentation / recovery** (police, insurers, INTERPOL-style workflows).

The profile also defines a **publish-on-incident** privacy model: keep the `.odpass` private (empty `dataUrl`), release it after a theft — the pre-incident on-chain hashes and mint timestamp prove the description was not written after the fact. See [`OBJECTID_PROFILE.md`](OBJECTID_PROFILE.md).

## Honest NFC assurance matrix

SPEC §6 now defines seal verification **profiles** with an explicit assurance matrix:

- **Profile A** (published EV2 key, the legacy flow) is normatively a **presence / key-match indicator**. A published symmetric key cannot prove a tag is original — anyone can provision a blank NTAG 424 DNA with it. Verifiers must not display "authentic" from this check (`SEAL_NFC_KEY_MATCH`; `SEAL_NFC_AUTHENTIC` is a deprecated alias).
- **Profile B** (`odp-ntag424-sdm-issuer-v1`, new) is the **clone-resistant** option: the SDM key stays secret with the issuer, each tap emits a fresh CMAC plus a monotonic read counter, and verification goes through the issuer's endpoint (`seal.nfc.verifyUrl`). On-chain `nfcPublicKey` stores a `keccak256` commitment to the key — no bytecode change needed.
- **Profile C** (per-chip asymmetric keys) is reserved for a future line.

## State privacy rules

SPEC §9 adds normative privacy rules for mutable on-chain state: no addresses, storage facilities, coordinates, courier details, or personal data — these fields are public forever. A controlled location vocabulary (`with_creator`, `in_storage`, `on_loan`, …) is recommended, and mint/update UIs must warn about permanence. A hash-pointer state model is sketched for a future line in [`IDEAS_V1.md`](IDEAS_V1.md).

## Machine-readable schema and CI

`passport.json` is now validated by [`schema/passport-0.6.schema.json`](../schema/passport-0.6.schema.json) (JSON Schema draft 2020-12) with reference examples under `schema/examples/`. CI runs Hardhat tests, schema validation, and Slither on every push.

## Compatibility

v0.6 keeps the v0.5 `Passport` tuple and ABI shape; the new JSON fields are additive and only affect new mints. As with every 0.x line, a v0.6 deployment is a **separate registry** — existing v0.5 records do not migrate.
