# ODP v0.6 — the storage-model redesign

ODP v0.6 is a ground-up redesign of what a passport stores and where. It reframes the standard around the **Object ID identification principle** — the same categories museums and insurers use to identify an object (object type, materials & technique, measurements, inscriptions & markings, distinguishing features, title, subject, date/period, maker, plus photographs and a short description) — and makes those categories first-class in the data model rather than an optional add-on. Design rationale and the full field tables are in [`docs/REQUIREMENTS_FIELDS_V0.6.md`](REQUIREMENTS_FIELDS_V0.6.md); normative rules are in `SPEC.md`.

Each 0.x line is a separate registry. v0.6 mints packed `CONTRACT_VERSION = 6` and is **not** backward compatible with earlier deployments.

## A readable card, on-chain

Earlier lines kept names off-chain and stored only a numeric profile ID. v0.6 reverses that for the essentials: every passport now carries a small **card** directly on-chain — `title`, `authorName`, `shortDescription`, and `domain` — so the object is legible even without the `.odpass` file. The card is written once at mint and has **no edit path**: a typo or renaming means revoke and re-mint. It must match the same fields in `passport.json` byte-for-byte, and a verifier that finds any mismatch reports the passport as tampered, not merely "changed".

## One identification block: `anchors[]`

The scattered v0.5 fields for seals, extra images, materials, dimensions, and marks are replaced by a single, extensible `anchors[]` array in `passport.json`. Each anchor has a type (`photo`, `dimensions`, `materials`, `distinguishing_features`, `marks`, `file_hash`, `perceptual_hash`, `c2pa`, `nfc`, `numbered_seal`, `fingerprint`, `dna`, …), its data or hash, and how to verify it. The whole array is committed on-chain as a second hash, `anchorsHash`, plus a bitmask of the anchor types present, so the identification block can be checked on its own — for example from a compact offline carrier — without the full document.

The contract enforces a **hard identification minimum** at mint: a physical object must carry at least a photo, dimensions, materials, and distinguishing features (and an on-chain primary image hash); a digital object must carry an exact file hash. A passport without that minimum will not mint — because a passport without photos and measurements proves nothing about the object in front of you. A cryptographic seal (NFC / numbered) is now **optional** on top of that minimum rather than mandatory.

## History is append-only

v0.5 let owners overwrite current-state fields (status, location, rights, condition, damage pointer). v0.6 removes all of them. Everything mutable is now an **append-only event** recorded on-chain — status change, location, rights, condition, damage, restoration, or a custom note, each optionally anchoring a signed document by its hash. The current value of any aspect is simply the latest event of its kind; nothing is ever overwritten and no history is lost. Ownership transfers and institutional attestations sit in the same append-only layer.

Provenance in ODP therefore starts at registration. History **before** minting is deliberately not a structured part of the standard — the protocol cannot verify it, and pretending otherwise would suggest false assurance.

## Duplicates: reputation, not a verdict

Nothing stops someone from registering their own passport for a forgery or for someone else's object. v0.6 does not try to have the protocol decide which of two competing passports is "the real one", and it deliberately does **not** enforce global hash uniqueness (that only blocks exact copies while handing bad actors a first-to-register weapon). Instead the verifier surfaces the signals a human needs: registration time, the issuer's published identity, institutional attestations, and any active counterfeit-concern flag. The decision stays with people, informed by the record.

## What moved where

| v0.5 | v0.6 |
|---|---|
| numeric profile ID only, on-chain | + on-chain card: `title`, `authorName`, `shortDescription`, `domain` |
| `sealType` / `sealHash` / `nfcPublicKey` / `nfcModel` | `nfc` / `numbered_seal` anchors |
| `imageHash2/3`, `imageUrl2/3` | `photo` anchors (no fixed limit) |
| `currentState.*` + four overwriting setters | append-only `recordPassportEvent` |
| `auxCommitment*` (COA pointer) | attestation `documentHash`, or a document anchor |
| `ndppCommitment*` | offline carriers verify against `dataHash` / `anchorsHash` directly |
| `physical.seal` / `image` / `images` in JSON | `anchors[]` |

Profiles (C/B/P/M), monthly mint caps, mint-agent delegation, the relations / proof / counterfeit-concern satellites, revocation, ownership transfer, and URL updates are unchanged in model.

## Under the hood

The reference registry, its linked library, and the paired satellites were rewritten for the 0.6 model. Removing six overwriting functions and a large slice of the struct more than pays for the new card and anchor fields: the main contract now compiles to **13,309 bytes** against the 24,576-byte EIP-170 limit — roughly half the budget free for future protocol work (e.g. optional author attestation). The reference mint CLI (`chain/tools/mint.py`) and the web creator / verify / manage flows build and check the v0.6 shape end-to-end.

The 0.x line also carries a deployer-only **`freeze()`** safety hatch: it irreversibly stops all writes to a registry (reads keep working) so an abandoned experimental deployment cannot accumulate new records. It is an alpha-line guard only and is planned for **removal in v1**, where registries must live without any privileged switch.
